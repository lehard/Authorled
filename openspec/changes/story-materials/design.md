# Design: материалы истории в заметках

## Context

Мотивация — `proposal.md`, требования — дельты в `specs/`.

Что уже есть и на что опирается решение:
- `core/files.py`: `check_upload` проверяет размер, тип по расширению и содержимому, ClamAV и извлекает текст; `store_file` пишет `files` (с `text_content`) и `file_contents` в одной транзакции. Назначения — `chat` (с `session_id`) и `import`; ограничения в базе: `purpose_known`, `session_for_chat`.
- `core/notes.py`: заметка — `title`, `body`, `revision`, мягкое удаление `deleted_at`, удаление навсегда только из корзины.
- `GET /api/v1/projects/{id}/notes` отдаёт заметки с полными текстами; фронтенд держит их в `ProjectContext`, `NoteDoc` правит `body` в `GrowingTextarea`.
- Контекст чата обрезает открытый документ до 20 000 знаков (`docContext.ts`, `MAX_CHARS`).
- Соавтор: `list_story_notes` (начало текста 200 знаков), `read_story_note` (весь текст), `read_chat_file` (только файл этой беседы); меняющие инструменты оборачиваются подтверждением (`_confirmed`).
- Биллинг: тарифы в `billing/plans.toml`, все поля обязательны; `check_limit` находит действующую подписку и продлевает выданную. Ядро биллинг не вызывает, стыкует слой приложения.
- Id файлов чата живут только в ходе, где файл приложен: история беседы хранит имена («Файлы: …»), а id уходят соавтору контекстом этого хода.

## Goals / Non-Goals

**Goals:**
- Один путь «файл → заметка с оригиналом» в ядре, общий для маршрута загрузки, маршрута «из файла беседы» и инструмента соавтора.
- Предел места проверяется в той же транзакции, что и запись, без гонки двух загрузок.
- Длинный материал не ломает ни контекст соавтора, ни экран.

**Non-Goals:**
- Фоновая обработка и статусы файлов: всё в запросе, как сейчас (анти-паттерн 13, исключение для загрузок).
- Отдельная таблица материалов или общий «файловый менеджер».

## Decisions

1. **Оригинал — строка `files` с `purpose` `note`, заметка ссылается на неё `notes.file_id`.**
   Миграция `0014`: `purpose_known` расширяется до `('chat', 'import', 'note')`; `session_for_chat` не меняется (у `note` беседы нет); `notes.file_id uuid NULL REFERENCES files(id)` без `ON DELETE` (NO ACTION) и `UNIQUE`.
   NO ACTION, а не RESTRICT: при удалении истории каскад удаляет и заметки, и файлы одним оператором, а NO ACTION проверяет ссылку в конце оператора и не мешает каскаду. Прямое удаление файла под заметкой база отклоняет.
   Альтернатива — ссылка из `files` на заметку (`files.note_id`): отвергнута, потому что файл беседы и оригинал заметки тогда различались бы не назначением, а набором ссылок, и проверка «оригинал не удаляется отдельно» стала бы сложнее.

2. **Из файла беседы — копия, а не общая ссылка.**
   `POST /api/v1/files/{id}/note` и инструмент соавтора создают новую строку `files` (`purpose` `note`) с теми же байтами, текстом, `sha256` и именем. Файл беседы живёт своей жизнью (его удаляет `DELETE /files/{id}`), а оригинал заметки — жизнью заметки. Цена — двойное хранение одного файла; ради простой модели владения это приемлемо, и в предел места копия входит честно.

3. **Одна операция ядра для заметки из файла.**
   `core/notes.py` (или `core/materials.py`, если файл заметок разрастётся) получает `create_note_from_file(connection, project_id, user_id, checked, limit_bytes)`: проверяет историю (`ensure_project_open`), длину текста (500 000 знаков, константа ядра), блокирует строку пользователя (`SELECT … FOR UPDATE` в `users`), считает занятое место (`sum(size_bytes)` по `files` с `purpose` `note` и `uploaded_by` = пользователь, все истории, корзина включена), отказывает `TooLarge` с занятым и пределом в МБ, затем пишет файл (`store_file` с `purpose` `note`) и заметку. Маршрут загрузки получает `CheckedFile` из `check_upload(name, "note", data)`; маршрут и инструмент «из беседы» строят `CheckedFile` из сохранённого файла беседы без повторной проверки ClamAV и разбора — файл уже прошёл их при загрузке.
   В `ALLOWED` появляется `note` с тем же списком, что у `chat`.
   Блокировка строки пользователя сериализует только загрузки одного пользователя; альтернатива — advisory lock — даёт то же, но менее заметна при чтении кода.

4. **Предел места даёт биллинг, проверяет ядро, стыкует приложение.**
   Поле `storage_mb` (int ≥ 1) в `Plan` и `plans.toml` (`beta` — 500). Новая операция `billing.storage_limit(user_id, at) -> int` (байты) в своей транзакции: `current_subscription` с продлением выданной подписки, как в `check_limit`, затем `plans().get(...)`. Маршруты и инструмент соавтора вызывают её до транзакции ядра и передают число в ядро. Ошибки биллинга маршрут переводит явно: `SubscriptionEnded` → `Problem(403, …)` с концом периода; `NoSubscription` и `UnknownPlan` не перехватываются (`500`, ошибка конфигурации видна в логе). Ядро по-прежнему не знает биллинг (`check_billing_boundary.sh`).
   Код ответа при нехватке места — `413`, как у слишком большого файла: оба отказа — «не помещается», фронтенд показывает `detail`.

5. **Удаление и корзина.**
   `trash_note`/`restore_note` не трогают файл. `delete_note` удаляет заметку и затем её файл в одной транзакции. `files.delete_file` для `purpose` `note` отвечает `Conflict` («Оригинал удаляется вместе с заметкой») до попытки удаления. «Очистить корзину» драфта уже удаляет заметки из корзины через ядро — переводится на ту же операцию, чтобы удалялись и оригиналы. Удаление истории — каскадом базы.

6. **Ответ заметки.**
   `NoteOut.file: NoteFileOut | None` (`id`, `name`, `media_type`, `size_bytes`); `Note` ядра получает `file` тем же видом, список заметок — одним запросом с `LEFT JOIN files`. Скачивание — существующий `GET /api/v1/files/{id}/content` (доступ проверяется по истории файла, оригинал в корзине скачивается).

7. **Соавтор.**
   `list_story_notes` добавляет `file` (имя или `null`) и `length`. `read_story_note(note_id, part=1)` режет `body` на части по 20 000 знаков (та же величина, что `MAX_CHARS` контекста чата) и отдаёт `part`, `parts`, `body`; часть вне диапазона — `Refusal`. Новый инструмент `save_chat_file_to_notes(file_id)` в списке меняющих (`_confirmed`), проверка «файл этой беседы» — как у `read_chat_file`; место — `billing.storage_limit` по пользователю запуска (как хуки соавтора находят пользователя ядра). В промпт (`agno/skills/coauthor/SKILL.md`) — две строки: длинную заметку читать частями, файл сохранять в заметки только по просьбе автора. Подпись действия в чате (`web/src/screens/project/chat/actions.ts`) — «Сохранить файл в заметки».

8. **Фронтенд.**
   `Note` получает `file: NoteFile | null`; `fixtures` всегда даёт `null` и отказывает в загрузке, как с другими файлами. Загрузка идёт через `useStoryFiles` новыми операциями (`noteFromUpload`, `noteFromChatFile`), которые возвращают заметку; после неё обновляются заметки проекта и открывается новая заметка. `NoteDoc` показывает над листом строку оригинала с «Скачать оригинал» (ссылка на `/files/{id}/content` через `apiClient` с токеном). Чип файла в поле чата получает меню с «В заметки».

## Risks / Trade-offs

- [Список заметок отдаёт полные тексты; десяток материалов по 500 000 знаков — несколько мегабайт] → предел длины текста; если список станет медленным, отдельный change отдаёт в списке начало текста, а полный — по заметке.
- [`GrowingTextarea` на сотнях тысяч знаков может тормозить] → проверить на тексте 500 000 знаков при приёмке (задача в `tasks.md`); если тормозит — режим просмотра отдельным change.
- [База растёт от оригиналов в `file_contents`, копия из беседы удваивает файл] → предел места по тарифу; объектное хранилище — отдельное решение.
- [Id файла чата известен соавтору только в ход приложения] → в промпте: если автор просит сохранить файл из прошлого сообщения, соавтор просит приложить его снова.
- [Гонка двух загрузок одного пользователя] → блокировка строки пользователя в транзакции записи.

## Migration Plan

1. Миграция `0014_note_files`: ограничение `purpose_known`, колонка `notes.file_id` с внешним ключом и уникальностью. Данные не меняются, у всех заметок `file_id` пустой.
2. `plans.toml` с `storage_mb` выходит в том же релизе, что и код, который его читает: без поля API не стартует.
3. Откат: миграции только вперёд; откат кода без отката схемы безопасен, пока не появилось заметок с оригиналом (старый код не знает `purpose` `note`, но и не читает такие строки). После появления таких заметок откат кода требует отдельной миграции.

## Open Questions

- Нет. Предел места на бете (500 МБ) и название раздела («Заметки») взяты по рекомендации из интента; их можно поменять без изменения подхода.
