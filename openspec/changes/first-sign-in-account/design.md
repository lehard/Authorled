# Design

## Context

Мотивация в `proposal.md`. Сейчас `RequireAuth` в `web/src/app/RefineRoot.tsx` проверяет только токен и сразу рендерит `SignedIn`, а тот открывает `<Outlet />`. Экран полки запрашивает истории сразу, а аккаунт запрашивают `useAccountTheme` и `UserMenu` через `useGetIdentity`. Эти запросы идут параллельно. Ядро создаёт запись в `users` только в `GET /api/v1/me`, а `GET /api/v1/projects` без неё отвечает `404` по спеке `api/stories`.

`getMe` вызывается и при источнике `fixtures`, но экраны с демо-данными сейчас от него не зависят. У фронтенда нет модульных тестов, поэтому поведение проверяется в браузере и по логам API.

Отказы продуктовых маршрутов проходят через `problem_response` в `agno/app/api/problems.py` и идут без `Cache-Control`. Chromium считает ответ `410` без этого заголовка свежим без срока. В локальной проверке `writer@authorled.test` с верным токеном получил из кэша `410` предыдущего пользователя, запрос до API не дошёл, а с `cache: "no-store"` тот же токен получил `200`.

## Goals / Non-Goals

**Goals:**

- Один порядок загрузки для всех экранов за входом, без правок в самих экранах.
- Явный отказ, когда аккаунт получить нельзя, и выход из этого состояния.

**Non-Goals:**

- Новый кэш аккаунта: используется уже существующий кэш identity в Refine.
- Изменение логики `useAccount`, `UserMenu` и `SettingsScreen`.

## Decisions

### 1. Ждать аккаунт в `SignedIn`, а не на экранах

`SignedIn` получает источник данных и при `api` рендерит `<Outlet />` только когда `useAccount()` вернул данные. Все адреса за входом проходят через этот компонент, поэтому порядок один для полки, корзины, настроек и истории.

Отвергнуто:
- Создавать аккаунт на стороне ядра в маршрутах историй: меняет контракт `api/stories` и размывает правило, что аккаунт создаётся только в `GET /api/v1/me`.
- Повторять запрос историй на `404`: скрывает ошибку и противоречит запрету на запасные пути.
- Вызывать `getMe` в `authProvider.check`: проверка входа работает и на `/auth/callback`, и её сбой означал бы «не удалось проверить вход», хотя Authentik отвечает.

### 2. Блокировать только при отсутствии данных

Условия проверяются в таком порядке: есть `data` — открыть экраны; есть `error` — показать причину; иначе — экран ожидания. Поэтому сбой фонового обновления, когда `data` уже есть, не закрывает экраны.

### 3. Источник данных передаётся через `RequireAuth`

`createRouter(dataSource)` уже знает источник и передаёт его в `RefineRoot`. Тем же способом он передаётся в `<RequireAuth dataSource={dataSource} />` и дальше в `SignedIn`. При `fixtures` `SignedIn` ведёт себя как сейчас: `useAccountTheme` и `<Outlet />` без ожидания. Отдельный контекст ради одного значения не нужен.

### 4. Экран сбоя повторяет существующий

Используется `MessageScreen` с `error.message`: `AccountError` уже содержит текст для человека. Кнопки: «Повторить» (`refetch` из `useAccount`) и «Выйти» (`useLogout`). «Выйти» нужна, потому что `UserMenu` на этом экране нет, а при `410` или отозванном доступе без неё человек застрянет. Ошибка выхода показывается на этом же экране, как в `UserMenu`.

Экран ожидания: `MessageScreen` с `loading`, текст «Загружаем аккаунт…».

### 5. Запрет кэша ставит сервер в `problem_response`

`problem_response` добавляет `Cache-Control: no-store` ко всем отказам. Это одно место для всех продуктовых маршрутов, и статусы с телами ответов не меняются. Ответы Agno этот код не проходят и остаются как есть.

Отвергнуто: `cache: "no-store"` в `fetch` в `meApi.ts` и `apiClient.ts`. Правка нужна в двух местах, новый запрос легко забыть, а другие клиенты API защиты не получат.

## Risks / Trade-offs

- Заголовок не исправит ответ, который браузер уже закэшировал. На сервере таких ответов нет: удалённых аккаунтов там не было.

- Если API недоступен, при `api` закрыты все экраны за входом, включая `/settings`. Они и так не могут работать без API, а причина и «Повторить» показываются, как требует «Данные аккаунта из API».
- Вход ждёт на один запрос дольше. Запрос лёгкий, а без него экраны всё равно не работают.
- Модульных тестов нет: регрессию не поймает `validate.sh`, поэтому порядок запросов проверяется по логам API вручную.
