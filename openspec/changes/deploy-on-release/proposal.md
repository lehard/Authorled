# Proposal

## Why

Продукт выходит на тестирование на своём сервере. Выкладка должна идти сама из GitHub, но только когда владелец выпускает версию: не каждый пуш в `main` готов к показу (`business-intents/deploy-on-release.md`). Сейчас в репозитории нет ни деплоя, ни описания выкладки фронтенда и обратного прокси.

## What Changes

- Публикация релиза GitHub с тегом из `main` запускает деплой. Обычные пуши в `main` сервер не меняют. Тег не из `main` останавливает деплой с ошибкой.
- Перед деплоем проходит та же проверка, что в CI. Фронтенд собирается в GitHub Actions с настройками продакшена и отправляется на сервер.
- Workflow подключается к серверу отдельным пользователем `deploy`. Одновременно идёт один деплой.
- На сервере: резервная копия базы, переключение кода на тег, сборка и запуск стека, обновление настройки Caddy. Хранятся последние 10 копий.
- Настройка Caddy лежит в репозитории: фронтенд, `/os/` на API и три пути Authentik на домене продукта, отдельный домен Authentik.
- После деплоя проверяются публичный `/health` и отказ `/agents` без токена. Сбой делает запуск красным, автоматического отката нет.
- Откат: ручной запуск workflow с тегом прошлого релиза.
- `AUTHENTIK_LISTEN__TRUSTED_PROXY_CIDRS` начинает доходить до контейнеров Authentik: README велит её задать, но `auth/compose.yaml` её не передаёт.
- Деплой не загружает демо-контент и не создаёт пользователей разработки: сервер начинается с пустых данных, новые пользователи не видят тестовых историй.
- README и скилл `deploy-platform` описывают выпуск релиза, откат и настройку сервера.

## Scope

- `.github/workflows/`: новый workflow деплоя, вызов проверки из `validate.yml`.
- `deploy/`: скрипт деплоя и настройка Caddy.
- `auth/compose.yaml`, `compose.prod.yaml`: настройка доверенного прокси.
- `README.md`, `.agents/skills/deploy-platform/SKILL.md`, `example.env`.
- Разовая подготовка сервера и настроек GitHub, описанная в README.

## Non-goals

- Деплой на каждый пуш, стенд staging, несколько серверов.
- Деплой без простоя и автоматический откат.
- Отдельный ручной путь первого деплоя: первая выкладка идёт первым релизом.
- Мониторинг, алерты, копии базы вне сервера.
- Образы в реестре: образы собираются на сервере.
- Белый список пользователей: это change по интенту `test-access-allowlist`.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `runtime`: добавляются требования к деплою по релизу, резервной копии, обратному прокси, проверке после деплоя и чистым данным сервера; «Production-override» требует настройку доверенного прокси.

## Impact

- Новые секреты и переменные в GitHub Environment `production`.
- На сервере появляются пользователь `deploy` с доступом к Docker и каталог приложения.
- Поведение API, фронтенда и схемы базы не меняется.
- Первому релизу нужны влитый в `main` код, SMTP для кодов входа, открытый порт 587 и DNS домена продукта на новый сервер.

## Принятый риск: 152-ФЗ

`openspec/context/05-security-and-compliance.md` требует хранить ПДн в РФ, а сервер стоит в Финляндии. Владелец принял этот риск на время закрытого тестирования 2026-11-06, он записан в контекст-пак. Перед открытым запуском сервер переносится в РФ.
