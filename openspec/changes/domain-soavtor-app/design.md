# Design

## Context

- Адреса продукта записаны в трёх местах, в коде ядра и фронтенда их нет:
  - `deploy/Caddyfile` — имена хостов прямо в файле;
  - env сервера `/etc/authorled/authorled.env`: `AGENTOS_URL`, `AUTH_BRAND_DOMAIN`, `AUTH_ISSUER`, `AUTH_FRONTEND_REDIRECT_URI`, `AUTH_FRONTEND_LOGOUT_URI`, `AUTHENTIK_COOKIE_DOMAIN`, `AUTHENTIK_EMAIL__FROM`;
  - переменные окружения `production` в GitHub: `PUBLIC_URL`, `AUTH_ISSUER`, `AUTH_FRONTEND_REDIRECT_URI`, `AUTH_FRONTEND_LOGOUT_URI`. От них зависят сборка фронтенда и проверка после деплоя.
- Blueprints ссылаются на env через `!Env`:
  - адреса возврата и выхода — `20-oidc.yaml`;
  - бренд, который ищется по `domain: !Env AUTH_BRAND_DOMAIN`, — `30-authentication-flow.yaml`.
- Authentik применяет файл blueprint заново, только когда меняется его содержимое. На сервере все `custom/*` применены 2026-11-06 в 17:20–18:38, а контейнеры Authentik перезапущены позже и ничего не применили. Значит, смена env без явного применения не дойдёт ни до адресов возврата OIDC, ни до бренда.
- `deploy/deploy.sh` делает `docker compose up -d --build`. Контейнер, у которого изменился env, пересоздаётся; при обычном перезапуске (`restart: unless-stopped`) остаётся env на момент создания. Поэтому env на сервере можно поменять до релиза: до пересоздания он не действует.
- DNS готов: в зоне `soavtor.app` на сервер указывают `@`, `www`, `app`, `auth`; записи Resend на месте, домен в Resend проверен (владелец, 2026-11-08).

## Goals / Non-Goals

**Goals:**
- Один релиз переводит сервис, вход и письма на новые адреса.
- Смена адресов в env доходит до Authentik без ручных команд на сервере, сейчас и в следующий раз.

**Non-Goals:**
- Делать адреса в `Caddyfile` настраиваемыми через env.
- Автоматически менять env сервера или переменные GitHub из репозитория.

## Decisions

1. **Имена хостов остаются прямо в `deploy/Caddyfile`.**
   - Блок `app.soavtor.app` повторяет нынешний блок `coauthor.glavai.ru`, только в `header_up Host` стоит `auth.soavtor.app`.
   - Блок `auth.soavtor.app` повторяет нынешний `auth.coauthor.glavai.ru`.
   - Переадресации пишутся директивой `redir`:
     - `coauthor.glavai.ru` → `https://app.soavtor.app{uri} permanent`;
     - `www.soavtor.app` → `https://soavtor.app{uri} permanent`;
     - `soavtor.app` → `https://app.soavtor.app{uri} 302`.

     `{uri}` несёт путь вместе с параметрами.
   - Блок `auth.coauthor.glavai.ru` удаляется целиком.
   - *Альтернатива:* плейсхолдеры `{$APP_DOMAIN}`. Отклонена: Caddy запускается systemd вне compose и env продукта не читает, а нынешний файл уже держит имена прямо в тексте.
2. **Корень временно переадресует на сервис, с путём и кодом 302.** 302 браузеры не запоминают, и когда сайт из `product-site` займёт корень, старый ответ ему не помешает. Путь сохраняется, чтобы `soavtor.app/login` тоже вёл куда надо.
3. **Деплой применяет все blueprints из `auth/blueprints/`.** После `up -d --build` скрипт:
   - ждёт, пока сервер и worker Authentik станут здоровыми (`up -d --wait authentik-server authentik-worker`);
   - выполняет `exec -T authentik-worker ak apply_blueprint` для `/blueprints/custom/*.yaml` по порядку имён.

   Если код выхода ненулевой, деплой останавливается с именем файла. Применять blueprints повторно безопасно: они описаны через `identifiers`, поэтому повторное применение ничего не дублирует.
   - *Альтернатива 1:* разовая ручная команда на сервере. Отклонена: следующая смена env опять тихо не применится, а спека `auth` требует конфигурации без ручных шагов.
   - *Альтернатива 2:* менять файл blueprint, чтобы сменился хеш. Отклонена: это обход, а не правило.
4. **Старый бренд `auth.coauthor.glavai.ru` остаётся в базе до проверки.** Blueprint создаёт новый бренд, потому что ищет бренд по домену; старый он не трогает. После проверки входа владелец удаляет старый бренд в админке Authentik. Это разовый шаг, автоматизировать его не нужно.
5. **Старые токены не переводятся.**
   - Сменился издатель, поэтому API отвечает на старый токен `401`.
   - У фронтенда новый origin, поэтому в его хранилище токенов нет, и пользователь попадает на вход.
   - Пользователей нет, поэтому отдельный путь миграции не нужен.

## Risks / Trade-offs

- [Сертификаты не выпустятся, если DNS ещё не виден Let's Encrypt] → релиз только после того, как публичный DNS отвечает для `@`, `www`, `app`, `auth`; Caddy повторяет попытки сам.
- [Env сервера и переменные GitHub расходятся, адрес возврата не совпадёт, вход ломается] → оба меняются одним шагом прямо перед публикацией релиза; после деплоя проверяется вход.
- [`ak apply_blueprint` при ошибке завершается с кодом 0, и сбой не виден] → задача проверяет код выхода на заведомо неверном blueprint локально. Если код 0, деплой должен останавливаться иначе; менять подход до реализации — через `/opsx:update`.
- [Authentik ещё мигрирует после пересоздания, `apply_blueprint` падает] → перед применением ждём `--wait` здоровья обоих контейнеров.
- [MCP-коннекторы со старым адресом перестают работать] → переподключить после релиза; записано в проверку.

## Migration Plan

Каждый шаг на сервере и в GitHub делается только после подтверждения владельца в чате.

1. Влить change в `main`.
2. Проверить публичный DNS для `soavtor.app`, `www`, `app`, `auth`.
3. Записать старые значения 7 строк env и 4 переменных GitHub в `tmp/VERIFY.md`. Они не секретные, по ним делается откат.
4. Заменить 4 переменные окружения `production` в GitHub.
5. Заменить 7 строк в `/etc/authorled/authorled.env`.
6. Опубликовать релиз. Деплой:
   - пересоздаёт API и Authentik с новым env;
   - применяет blueprints;
   - перезагружает Caddy, тот получает сертификаты;
   - проверяет `https://app.soavtor.app/os/health`.
7. Проверить вживую:
   - вход кодом с `noreply@soavtor.app`;
   - соавтор;
   - переадресации;
   - отказ старому домену Authentik;
   - MCP.
8. Удалить старый бренд в Authentik и старый домен в Resend.

**Откат:** вернуть старые значения env и переменных GitHub и вручную запустить деплой прошлого тега. В нём старый `Caddyfile`, деплой пересоздаст контейнеры со старым env. Blueprints прошлый тег сам не применит, поэтому `ak apply_blueprint` для `20-oidc.yaml` и `30-authentication-flow.yaml` нужно запустить вручную, с подтверждением владельца.
