# Design

## Context

Причины отказов и доказательства — `proposal.md` и `business-intents/coauthor-tool-contracts.md`. Что есть сейчас:

- Agno 3.1.10 строит JSON Schema инструмента по аннотациям Python (`Function.from_callable`), а описания параметров берёт из раздела `Args` docstring. `dict[str, Any]` превращается в `additionalProperties: {"type": "object", "properties": {}, "additionalProperties": false}`. Проверено локально: `dict[str, str]` даёт `additionalProperties: {"type": "string"}`, `Literal["main", "secondary", "episodic"]` — `enum`.
- Список инструментов соавтора статический (`COAUTHOR_TOOLS`): AgentOS 3.1.10 отказывает в инструментах, построенных на каждый запуск.
- Ядро проверяет поля моделями pydantic в строгом режиме (`core/fields.py`), `validate_fields` поднимает `Invalid` по первой ошибке. `Invalid.field` используют тесты, маршруты отдают только текст (`problems.py`).
- Подписи полей по-русски есть только во фронтенде (`web/src/data/profiles.ts`); в ядре — только ключи (`CHARACTER_PROFILE` и др.).
- Запускатель замера качества (`agno/evals/coauthor/run.py`, `user.py`) уже умеет запускать копию соавтора с сессией в памяти и вызывающим вне HTTP, но привязан к своему пользователю и не продолжает запуск после паузы.
- Ядро копирует драфт (`core/drafts.create_draft`: документы и текст сценария без рецензирования), числа драфтов в истории не ограничивает.

## Goals / Non-Goals

**Goals:**
- Модель видит в схеме ровно то, что примет ядро: строки, перечисление роли, имена полей вида.
- Одна попытка исправления после отказа, если модель всё же ошиблась.
- Повторяемый замер, который видит ошибки после «Разрешить».

**Non-Goals:**
- Менять модель соавтора, режимы, паузу подтверждения или AG-UI.
- Делать подписи полей общими для фронтенда и ядра.

## Decisions

### 1. Типы параметров вместо словаря «что угодно»

`create_story_document`: `role: Literal["main", "secondary", "episodic"] | None`, `fields: dict[str, str] | None`. `update_story_document`: то же для роли, `fields: dict[str, str | None] | None` (null убирает поле). Ядро по-прежнему проверяет всё само: схема — подсказка модели, а не проверка. Ядро требует роль при создании персонажа и локации и отказывает в ней у мира (`core/documents.py`, `_role`); описание `role` говорит это прямо: в прогоне 2026-11-09 модель создала локацию без роли и получила отказ.

Альтернативы:
- **Модель pydantic с полями профиля** (объединение трёх видов). Схема точнее, но `anyOf` из трёх больших объектов DeepSeek читает хуже, а вид документа всё равно передаётся отдельно; ядро проверяет вид и так.
- **Отдельные инструменты на вид** (`create_character` с 33 параметрами и т. д.): инструментов становится 17 вместо 12, а это признак возврата к оркестратору (`coauthor-quality-eval`); отвергнуто в интенте.

### 2. Список полей в описании инструмента строится из ядра

В `core/fields.py` рядом с кортежами полей — пояснения по-русски для каждого поля каждого вида (2–4 слова, по подписям `profiles.ts`) и функция, которая собирает из них текст «персонаж: personality — характер; …». Описание инструментов создания и изменения документа собирается из этого текста при импорте модуля инструментов. Поле без пояснения или пояснение поля, которого нет у вида, — ошибка при импорте: API не стартует (без запасного текста).

Текст полей идёт в основное описание инструмента, а не в `Args`, чтобы не зависеть от того, как Agno разбирает многострочные описания параметров. Что именно увидит модель, проверяет pytest по `Function.from_callable(...).to_dict()`.

У сценария в описании только строковые поля (`logline`, `synopsis`); `show` и `title_page` не упоминаются.

Альтернатива — держать пояснения только во фронтенде и копировать список в docstring руками: разойдётся при первом новом поле. Подписи фронтенда и пояснения ядра — разные тексты для разных читателей, их совпадение не требуется.

### 3. Отказ ядра называет все ошибки

`validate_fields` собирает все ошибки pydantic и строит одно сообщение в порядке полей запроса:
- `extra_forbidden` — «Поля «X» нет у документа этого вида. Поля персонажа: …»;
- `string_type` — «Поле «X»: ожидается строка.»;
- `literal_error` — «Поле «X»: допустимые значения — …» (из `expected` ошибки);
- `bool_type` — «Поле «X»: ожидается да или нет.»;
- `missing` — «Поле «X» обязательно.»;
- `model_type` / `dict_type` — «Поле «X»: ожидается объект.»

Тип ошибки, которого нет в этой таблице, — `RuntimeError` с его именем: это ошибка кода, а не ввода, и тест на все поля всех видов не даёт ей появиться незамеченной. `Invalid.field` остаётся путём первой ошибки — существующие тесты и маршруты не меняются. Список допустимых полей вида дописывается один раз в конце сообщения, даже если неизвестных полей несколько.

Значения к нужному типу не приводятся (`{"value": "…"}` не разворачивается): это был бы fallback, маскирующий неверный вызов.

### 4. Правило в промпте

В раздел «Действия в истории» `agno/skills/coauthor/SKILL.md`: если инструмент отказал из-за полей, исправь вызов по причине из отказа и повтори один раз; сведения профиля клади в поля профиля, а не в описание. Без примера JSON, чтобы промпт не стал второй схемой.

### 5. Замер действий

- **Где.** В `agno/evals/coauthor/` рядом с замером качества: набор `actions.toml`, разбор и проверки `actions.py`, подкоманды `python -m evals.coauthor actions-setup` и `actions-run --all | --sample N`. Пользователь и вызывающий из `user.py` и `run.py` получают субъект параметром, чтобы у замера действий был свой пользователь `coauthor-actions-eval` с копией демо-историй; замер качества работает как прежде. Эта правка трогает файлы `coauthor-quality-eval`, поэтому группа замера начинается только после того, как тот change закоммичен и архивирован.
- **Свежий драфт.** Для каждой просьбы ядро копирует открытый драфт демо-истории (`create_draft`, имя `замер <id> <время>`); беседа — `<projectId>:<newDraftId>:<uuid>`. Документы и текст сценария независимы, комментарии к копии не переносятся. Заметки общие для истории, а копия драфта их не отделяет: без восстановления прогон оставлял свои заметки следующему, а переименование ломало более поздние просьбы. Поэтому перед каждой просьбой замер возвращает заметки истории к демо-состоянию: демо-заметки сопоставляются по порядку создания (`setup` создаёт их в порядке `demo.json`) с проверкой начала текста и получают название, текст и состояние корзины из `demo.json`; остальные уходят в корзину (`core.notes.trash_note`, без жёсткого удаления). Расхождение, которое нельзя сопоставить, — ошибка замера, а не просьбы. После восстановления замер сравнивает список заметок до и после просьбы и учитывает только новые и изменённые. Драфты и заметки замера остаются в локальной базе пользователя замера (жёсткого удаления нет).
- **Продолжение после паузы.** Пока запуск на паузе, замер подтверждает каждое активное требование (`RunRequirement.confirm()`) и вызывает `acontinue_run` с той же сессией в памяти, как чат в режиме `auto`. Не больше 6 продолжений на просьбу; дальше — ошибка просьбы.
- **Проверки.** По записанным вызовам (имя, аргументы, ответ инструмента) и по состоянию драфта после запуска: отказы «Отказ: …», попытки до первого успеха (больше двух — провал), ожидаемый инструмент, заполненные ожидаемые поля (непустые строки) и признак «сведения в `summary`»: ожидаемые поля пусты, а `summary` длиннее 300 знаков. Изменения без просьбы — любые документы и заметки, кроме ожидаемых.
- **Набор.** Около 60 просьб пишет Claude (сессия Claude Code) по документам демо-историй (`web/src/data/demo.json`): по 10–12 на персонажа, локацию, мир, изменение документа, заметки и комментарий, плюс 6–8 без действия. Ожидаемые поля — только те, о которых просьба говорит прямо. Загрузка набора проверяет инструменты и поля по `core/fields.py` до вызова модели.
- **Без судьи.** Всё проверяемое здесь — факты ядра; качество текста оценивает замер качества.

Альтернатива — дописать продолжение после паузы в замер качества: смешает два вопроса (качество ответа и исправность действий) и изменит уже согласованный change другой сессии.

## Risks / Trade-offs

- [Описание полей удлиняет каждый запрос соавтора] → Пояснения по 2–4 слова; цена запроса до и после — в отчёте замера и `tmp/VERIFY.md`.
- [DeepSeek игнорирует схему] → Подробный отказ даёт исправиться за ход; замер покажет долю.
- [Пересечение с `coauthor-quality-eval`] → Группа замера начинается после его архива; до этого — только ядро, инструменты и промпт.
- [Порог «сведения в `summary`» (300 знаков) условный] → Провалы по полям читаются глазами; порог правится по первому прогону.
- [Подробные отказы видит и автор в маршрутах] → Текст по-русски и короче списка подписей на экране; фронтенд показывает `detail` как есть.

## Migration Plan

Миграций нет. Выкатывается обычным релизом: схема и промпт меняются при старте API. Откат — предыдущий релиз; данные не меняются.
