# Spec Delta

## Purpose

Оплата подписки на платный тариф через интернет-эквайринг Точки: оформление, подтверждение оплаты запросом к Точке, отмена, неудачное списание, конец оплаченного периода и история платежей. Тарифы, подписки и лимит описаны в спеке подписок из change `usage-limits`.

## ADDED Requirements

### Requirement: Состояние тарифа
`GET /api/v1/billing` MUST отвечать для владельца токена: тариф и его название, использованная доля лимита, конец текущего периода, источник подписки, дата следующего списания (только у действующей оплаченной подписки), состояние оформления (`none`, `pending`, `active`, `cancelled`, `failed`), платные тарифы, которые можно купить, и последние платежи. В запросе MUST NOT быть идентификатора пользователя.

#### Scenario: Бесплатный тариф
- GIVEN у пользователя бесплатная подписка и нет оформлений
- WHEN он запрашивает `GET /api/v1/billing`
- THEN ответ MUST содержать его тариф, долю лимита и конец периода, состояние `none`, список платных тарифов и пустой список платежей
- AND дата следующего списания MUST отсутствовать

#### Scenario: Оплаченная подписка
- GIVEN подписка пользователя оплачена через Точку и не отменена
- WHEN он запрашивает `GET /api/v1/billing`
- THEN ответ MUST содержать платный тариф, состояние `active`, дату следующего списания и платёж с суммой и оплаченным периодом

### Requirement: Оформление подписки
`POST /api/v1/billing/checkout` с телом `{"plan": "<код>"}` MUST создавать в Точке подписку с ежемесячным списанием и чеком на почту аккаунта и возвращать ссылку на оплату. Сумма и название позиции чека MUST браться из тарифа. Тариф MUST быть в файле тарифов с ценой больше 0 и признаком «можно купить». Тариф пользователя до оплаты MUST NOT меняться.

#### Scenario: Ссылка на оплату
- GIVEN у пользователя бесплатная подписка, а тариф `pro` можно купить
- WHEN он отправляет `POST /api/v1/billing/checkout` с `{"plan": "pro"}`
- THEN ответ MUST содержать ссылку на страницу оплаты Точки
- AND `GET /api/v1/billing` MUST показывать прежний тариф и состояние `pending`

#### Scenario: Повторное нажатие
- GIVEN у пользователя есть неоплаченное оформление тарифа `pro`, и его ссылка ещё действует
- WHEN он снова отправляет `POST /api/v1/billing/checkout` с `{"plan": "pro"}`
- THEN ответ MUST содержать ту же ссылку, а вторая подписка в Точке MUST NOT создаваться

#### Scenario: Тариф нельзя купить
- GIVEN тариф `beta` с ценой 0
- WHEN пользователь отправляет `POST /api/v1/billing/checkout` с `{"plan": "beta"}`
- THEN ответ MUST быть `422` с полем `plan`

#### Scenario: Уже оплачено
- GIVEN подписка пользователя оплачена через Точку и не отменена
- WHEN он отправляет `POST /api/v1/billing/checkout`
- THEN ответ MUST быть `409`

#### Scenario: Точка недоступна при оформлении
- GIVEN API Точки не отвечает
- WHEN пользователь отправляет `POST /api/v1/billing/checkout`
- THEN ответ MUST быть `503` с причиной, и оформление MUST NOT сохраняться

### Requirement: Подтверждение оплаты только ответом Точки
Подписку на платный тариф MUST переводить или продлевать только операция, которую API Точки вернуло в статусе `APPROVED`. У операции MUST быть наш код клиента, номер заказа одного из наших оформлений, сумма, равная цене тарифа этого оформления, и списание с номером. Подтверждённая оплата MUST давать платный тариф на месяц от времени оплаты. Если условие не выполнено, MUST NOT меняться ничего, а в лог MUST попадать идентификатор операции и причина.

#### Scenario: Первая оплата
- GIVEN пользователь оформил тариф `pro` и оплатил его на странице Точки
- WHEN ядро подтверждает операцию, а Точка отвечает `APPROVED` с нашей суммой и номером заказа
- THEN подписка MUST перейти на `pro` с периодом в месяц от времени оплаты, а лимит MUST браться из `pro`
- AND в истории платежей MUST появиться платёж с суммой и периодом

#### Scenario: Операция не оплачена
- GIVEN Точка отвечает по операции статусом `CREATED`
- WHEN ядро подтверждает операцию
- THEN подписка MUST NOT меняться

#### Scenario: Чужая операция
- GIVEN Точка отвечает `APPROVED`, но номер заказа не принадлежит ни одному нашему оформлению
- WHEN ядро подтверждает операцию
- THEN подписка MUST NOT меняться, а в логе MUST быть идентификатор операции

#### Scenario: Сумма не совпадает
- GIVEN Точка отвечает `APPROVED` с суммой меньше цены тарифа оформления
- WHEN ядро подтверждает операцию
- THEN подписка MUST NOT меняться

#### Scenario: Неизвестный статус
- GIVEN Точка отвечает статусом, которого нет в её перечне
- WHEN ядро подтверждает операцию
- THEN подтверждение MUST завершиться ошибкой с этим статусом, а тариф MUST NOT назначаться

### Requirement: Платёж засчитывается один раз
Каждое списание Точки MUST засчитываться не больше одного раза, сколько бы раз о нём ни сообщили: повторный вебхук, повторная проверка со страницы возврата, сверка в конце периода. Повтор MUST NOT продлевать подписку.

#### Scenario: Повторное уведомление
- GIVEN оплата уже засчитана, подписка продлена до 7 декабря
- WHEN Точка присылает то же уведомление ещё раз
- THEN конец периода MUST остаться 7 декабря, а в истории MUST остаться один платёж

#### Scenario: Уведомление и возврат одновременно
- GIVEN пользователь вернулся на сайт, и одновременно пришло уведомление об этой оплате
- WHEN обе проверки подтверждают одну операцию
- THEN в истории MUST быть один платёж, а период MUST продлиться один раз

### Requirement: Очередное списание
Каждое ежемесячное списание Точки по действующей подписке после подтверждения MUST продлевать платную подписку на следующий месяц от конца текущего периода, если оплата пришла до его конца, и на месяц от времени оплаты, если после.

#### Scenario: Списание в срок
- GIVEN подписка `pro` оплачена до 7 декабря
- WHEN 7 декабря Точка списывает оплату, и ядро её подтверждает
- THEN подписка MUST продлиться до 7 января, а в истории MUST быть два платежа

### Requirement: Уведомления Точки
`POST /api/v1/billing/tochka/webhook` MUST принимать уведомления `acquiringInternetPayment` без токена пользователя. Тело MUST быть JWT, подписанным ключом Точки (RS256). Маршрут MUST подтверждать операцию из уведомления запросом к API Точки и MUST NOT менять тариф по данным тела. Ответы: `200` — операция подтверждена, уже засчитана или не наша; `400` — подпись или тело неверны; `503` — Точка не ответила.

#### Scenario: Подписанное уведомление об оплате
- GIVEN пользователь оплатил оформление, и Точка подтверждает операцию
- WHEN приходит подписанное уведомление с этой операцией
- THEN ответ MUST быть `200`, а подписка MUST перейти на оплаченный тариф

#### Scenario: Поддельное уведомление
- GIVEN тело подписано не ключом Точки
- WHEN оно приходит на маршрут уведомлений
- THEN ответ MUST быть `400`, к API Точки MUST NOT обращаться, а тариф MUST NOT меняться

#### Scenario: Подпись верна, оплаты нет
- GIVEN уведомление подписано ключом Точки, но Точка отвечает по операции статусом `EXPIRED`
- WHEN оно приходит на маршрут уведомлений
- THEN ответ MUST быть `200`, а тариф MUST NOT меняться

#### Scenario: Точка недоступна при уведомлении
- GIVEN API Точки не отвечает
- WHEN приходит подписанное уведомление
- THEN ответ MUST быть `503`, чтобы Точка повторила уведомление

### Requirement: Проверка оплаты после возврата
`POST /api/v1/billing/check` MUST подтверждать открытое оформление владельца токена запросом к API Точки и возвращать то же состояние, что `GET /api/v1/billing`. Без открытого оформления MUST возвращаться текущее состояние без запроса к Точке.

#### Scenario: Вебхук ещё не пришёл
- GIVEN пользователь оплатил и вернулся раньше уведомления Точки
- WHEN страница возврата отправляет `POST /api/v1/billing/check`
- THEN ответ MUST показывать оплаченный тариф и состояние `active`

### Requirement: Отмена подписки
`POST /api/v1/billing/cancel` MUST отключать автосписание подписки в Точке, а затем помечать подписку отменённой. Оплаченный тариф MUST действовать до конца периода, после него пользователь MUST перейти на бесплатный тариф. Если Точка не подтвердила отмену, MUST возвращаться ошибка, а подписка MUST NOT помечаться отменённой.

#### Scenario: Отмена
- GIVEN подписка `pro` оплачена до 7 декабря
- WHEN пользователь отправляет `POST /api/v1/billing/cancel`
- THEN Точка MUST получить отмену подписки, а `GET /api/v1/billing` MUST показывать `pro` до 7 декабря, состояние `cancelled` и без даты следующего списания

#### Scenario: После конца отменённой подписки
- GIVEN подписка `pro` отменена и оплачена до 7 декабря
- WHEN после 7 декабря пользователь обращается к соавтору или к странице «Тариф»
- THEN подписка MUST быть на бесплатном тарифе с новым периодом, а лимит MUST браться из бесплатного тарифа

#### Scenario: Нечего отменять
- GIVEN у пользователя бесплатная подписка
- WHEN он отправляет `POST /api/v1/billing/cancel`
- THEN ответ MUST быть `409`

### Requirement: Конец оплаченного периода без оплаты
Когда период неотменённой платной подписки кончился, а засчитанного списания на следующий период нет, ядро MUST один раз спросить Точку об операции подписки и засчитать найденные списания. Если списаний нет, подписка MUST перейти на бесплатный тариф с отметкой «оплата не прошла». Если Точка не ответила, обращение MUST завершиться ошибкой, а тариф MUST NOT меняться.

#### Scenario: Неудачное списание
- GIVEN подписка `pro` оплачена до 7 декабря, а 7 декабря Точка не смогла списать оплату
- WHEN после 7 декабря пользователь открывает страницу «Тариф»
- THEN подписка MUST быть на бесплатном тарифе, а `GET /api/v1/billing` MUST показывать состояние `failed`

#### Scenario: Оплата пришла позже
- GIVEN подписка перешла на бесплатный тариф с отметкой «оплата не прошла»
- WHEN Точка списывает оплату по той же подписке, и ядро её подтверждает
- THEN подписка MUST вернуться на платный тариф с периодом в месяц от времени оплаты

#### Scenario: Точка недоступна в конце периода
- GIVEN период платной подписки кончился, а API Точки не отвечает
- WHEN пользователь обращается к странице «Тариф»
- THEN ответ MUST быть `503` с причиной, а тариф MUST NOT меняться

### Requirement: Оплатить снова
После неудачного списания `POST /api/v1/billing/checkout` MUST создавать новое оформление. Прежнюю подписку в Точке ядро MUST отменить до этого, если её статус в Точке это допускает.

#### Scenario: Новая попытка
- GIVEN подписка в состоянии `failed`, а прежняя подписка в Точке в статусе `PastDue`
- WHEN пользователь нажимает «Оплатить снова»
- THEN прежняя подписка MUST быть отменена в Точке, и ответ MUST содержать новую ссылку на оплату

### Requirement: Доступ к маршрутам оплаты
Маршруты `/api/v1/billing`, `/checkout`, `/check` и `/cancel` MUST требовать действующий токен, как `/api/v1/me`, и MUST работать только с подпиской владельца токена (`sub`). Маршрут уведомлений MUST NOT требовать токен пользователя. Других маршрутов без токена эта функция MUST NOT добавлять.

#### Scenario: Без токена
- GIVEN запрос без токена
- WHEN он отправляется на `GET /api/v1/billing`
- THEN ответ MUST быть `401`

#### Scenario: Другой пользователь
- GIVEN у пользователя A оплачена подписка
- WHEN пользователь B запрашивает `GET /api/v1/billing`
- THEN ответ MUST содержать только подписку и платежи B

### Requirement: Данные карты не хранятся
Ядро MUST NOT получать, хранить и писать в логи номер карты, маскированный номер, токен карты и платёжную систему. В истории платежей MUST храниться только идентификаторы операции и списания Точки, сумма, время оплаты и оплаченный период.

#### Scenario: Уведомление с данными карты
- GIVEN уведомление Точки содержит `maskedPan`, `cardType` и `tokenCardId`
- WHEN ядро его обрабатывает
- THEN эти значения MUST NOT попадать в таблицы ядра и логи
