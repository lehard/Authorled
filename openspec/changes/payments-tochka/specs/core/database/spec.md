## ADDED Requirements

### Requirement: Таблица оформлений оплаты
Схема `authorled` MUST содержать таблицу `billing_checkouts`: одно оформление подписки в Точке. Колонки: пользователь (ссылка на `users.id`), код тарифа, сумма, идентификатор подписки Точки, ссылка на оплату, состояние (`created`, `active`, `cancelled`, `failed`, `expired`), время создания, истечения ссылки и отмены. Номер заказа для Точки MUST быть `id` оформления. Колонок с данными карты MUST NOT быть.

#### Scenario: Состав колонок
- GIVEN все миграции применены
- WHEN перечисляются колонки `authorled.billing_checkouts`
- THEN MUST присутствовать колонки, перечисленные в требовании, и MUST NOT присутствовать колонки с номером, маской или токеном карты

#### Scenario: Подписка Точки одна на оформление
- GIVEN оформление с идентификатором подписки Точки уже есть
- WHEN сохраняется второе оформление с тем же идентификатором
- THEN база MUST отклонить запись

### Requirement: Таблица платежей
Схема `authorled` MUST содержать таблицу `payments`: засчитанные списания Точки. Колонки: оформление, пользователь, идентификатор операции Точки, номер списания Точки, сумма, время оплаты, начало и конец оплаченного периода, время записи. Пара «операция, списание» MUST быть уникальной. Удаление пользователя MUST NOT удалять платежи каскадом.

#### Scenario: Повтор списания
- GIVEN платёж с операцией `op-1` и списанием `ord-1` уже записан
- WHEN записывается ещё один платёж с теми же `op-1` и `ord-1`
- THEN база MUST отклонить запись

#### Scenario: Состав колонок
- GIVEN все миграции применены
- WHEN перечисляются колонки `authorled.payments`
- THEN MUST присутствовать колонки, перечисленные в требовании, и MUST NOT присутствовать колонки с данными карты
