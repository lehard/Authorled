# Design

## Context

Мотивация в `proposal.md`, поведение в дельтах спек. Что важно для решения:

- Тарифы, подписки, периоды и лимит делает change `usage-limits`. Его контракт передан 2026-11-07, код ещё не влит, поэтому фаза 2 сверяет его с кодом:
  - Миграция `0009_subscriptions_usage` идёт после `0008_notes`. Наша миграция получает `down_revision = "0009_subscriptions_usage"`.
  - Таблица `authorled.subscriptions`:
    - поля `id`, `user_id`, `plan` (код из файла, не FK);
    - `source` с CHECK `('granted')`;
    - `status` с CHECK `('active','ended')`;
    - `started_at` (якорь периодов);
    - `period_start` и `period_end` — полуинтервал `[start, end)`;
    - `ended_at` есть тогда и только тогда, когда статус `ended`.
  - У пользователя одна подписка `active` (частичный уникальный индекс). Источник `tochka` добавляет наша миграция, расширяя CHECK.
  - Тарифы лежат в `agno/core/plans.toml`:
    - вверху `signup_plan`;
    - секции `[plans.<код>]` с полями `name`, `price_rub`, `period_months`, `limit_rub`, `purchasable`;
    - все поля обязательны, лишние запрещены.
  - Операции ядра получают `Connection` вызывающего:
    - `plans()` с методами `.get`, `.signup`, `.all()`;
    - `start_subscription(conn, user_id, plan, source, start)` закрывает действующую подписку и открывает новую;
    - `current_subscription(conn, user_id, now)` берёт подписку с `FOR UPDATE` и сама продлевает `granted`. Если источник другой и период истёк, она бросает `SubscriptionEnded`;
    - `next_period(conn, subscription_id)` сдвигает период на один вперёд;
    - `set_plan(conn, user_id, plan)`;
    - `period_spend` и `check_limit`.
- Ядро синхронное (SQLAlchemy Core, маршруты зовут его через `run_in_threadpool`), внешние сервисы ядро вызывает само: так сделан антивирус (`core/clamav.py`). Адреса и ключи — обязательные переменные окружения, проверка при старте в `app/main.py`.
- AgentOS проверяет JWT на всех маршрутах, кроме списка исключений. Agno 3.1.10 даёт для этого `Authorization(excluded_route_paths=...)` (`agno/os/config.py`), его задаёт `agno/app/auth/authorization.py`.
- Ответы ядра — `application/problem+json` только для своих исключений (`app/api/problems.py`).

### Что говорит документация Точки (проверено 2026-11-07)

Основной источник — OpenAPI Точки: https://enter.tochka.com/doc/openapi/swagger.json. Страницы ниже — от https://developers.tochka.com/docs/tochka-api/.

1. **Адреса.** Боевой адрес `https://enter.tochka.com/uapi/`, тестовый `https://enter.tochka.com/sandbox/v2/` (`servers` в OpenAPI). Методы эквайринга лежат под `acquiring/v1.0/`. Сертификат `enter.tochka.com` выпущен Russian Trusted Sub CA Минцифры, поэтому с обычным набором certifi соединение не проверяется (проверено: `CERTIFICATE_VERIFY_FAILED`). С `agno/litellm/certs/ca-bundle.pem` (certifi + Russian Trusted Root и Sub CA) проверяется и отвечает. Страница: `certificate`.
2. **Авторизация.** Для своей интеграции используется JWT-ключ из интернет-банка (Сервисы → Интеграции и API), заголовок `Authorization: Bearer <ключ>`. Ключ не обновляется сам, его перевыпускают вручную; права меняются только перевыпуском. Нужны права `MakeAcquiringOperation`, `ReadAcquiringData`, `ReadCustomerData`. OAuth 2.0 нужен площадкам, где платят друг другу, нам он не нужен. Страницы: `algoritm-raboty-s-jwt-tokenom`, `faq`.
3. **`customerCode` и `merchantId`.** `customerCode` (9 символов) берётся из `GET /open-banking/v1.0/customers`, запись с `customerType: "Business"`. `merchantId` (15 цифр) — торговая точка из `GET /acquiring/v1.0/retailers?customerCode=`. Рабочая точка имеет `status: REG` и `isActive: true`. Документация советует всегда передавать `merchantId`. Страница: `opisanie-metodov/podpiski-rekurrentnye-platezhi/`.
4. **Подписка с чеком.** `POST /acquiring/v1.0/subscriptions_with_receipt` с телом `{"Data": {...}}`. Обязательные поля: `customerCode`, `amount`, `purpose` (1–140 символов), `Client.email` (на него приходит чек), `Items[]` (`name`, `amount`, `quantity`; также `vatType`, `paymentMethod`, `paymentObject`, `measure`). Необязательные: `merchantId`, `redirectUrl`, `failRedirectUrl`, `paymentLinkId` (1–45 символов, повтор отклоняется), `taxSystemCode`, `Options` и `recurring`.
   - `Options {period: Day|Month|Year, trancheCount, daysInPeriod}` создаёт подписку с графиком. Для `Month` предел — 84 списания. Вместе с `recurring` передавать нельзя.
   - Ответ: `Data.operationId` (идентификатор подписки), `Data.paymentLink`, `status: CREATED`.
   - Ссылка живёт 168 часов, после открытия на оплату даётся час. Подписки принимают только карты.
   - Страницы: `api/create-subscription-with-receipt-...`, `opisanie-metodov/podpiski-rekurrentnye-platezhi/s-fiskalizaciej`.
5. **Регулярные списания.** Подписку с графиком (`Options`) Точка списывает сама. Подписка без графика (`recurring: true`) списывается вызовом `POST /acquiring/v1.0/subscriptions/{operationId}/charge` с суммой; ответ — только `result: true`. Страница: `.../rabota-s-podpiskami-bez-grafika-spisania`.
6. **Отмена и статус подписки.** `POST /acquiring/v1.0/subscriptions/{operationId}/status` с `{"Data":{"status":"Cancelled"}}`, ответ `Data.result`. Работает только для подписок с графиком. `GET` того же адреса возвращает `Active | Cancelled | Completed | Expired | Failed | PastDue | Preparing | Refused | Rejected | Suspended | Trial`; значения статусов в документации не описаны. Подписку нельзя продлить, а возврат по ней делается только в интернет-банке.
7. **Операция.** `GET /acquiring/v1.0/payments/{operationId}` возвращает `Data.Operation[]` с полями `status`, `amount`, `customerCode`, `merchantId`, `paymentLinkId`, `paidAt` и `Order[] {orderId, type: approval|refund|authorized, amount, time}`.
   - Статусы: `CREATED, APPROVED, ON-REFUND, REFUNDED, EXPIRED, REFUNDED_PARTIALLY, AUTHORIZED, WAIT_FULL_PAYMENT`. Описаны только два: `APPROVED` («деньги списаны, оплата завершена») и `AUTHORIZED` (заморожены при двухэтапной оплате).
   - Создаёт ли очередное списание по подписке новую операцию или новый `Order` в той же, документация не говорит. В реестр платежей списания по подпискам не попадают.
8. **Вебхук `acquiringInternetPayment`.** Приходит POST с `Content-Type: text/plain`. Тело — JWT, подписанный RS256, без `exp` и `kid`.
   - Открытый ключ (JWK) опубликован на https://enter.tochka.com/doc/openapi/static/keys/public. Пример тела со страницы вебхука проверяется этим ключом (проверено). В Java-примере на той же странице другой ключ, это расхождение документации.
   - Поля: `webhookType`, `operationId`, `paymentLinkId`, `status` (`AUTHORIZED | APPROVED`), `amount` (строка, в REST — число), `customerCode`, `merchantId`, `purpose`, `paymentType`, `consumerId`.
   - Приходят только успешные операции, обычно через 5–10 секунд. Любой ответ кроме 200 Точка повторяет 30 раз с интервалом 10 секунд.
   - Регистрация: `PUT /webhook/v1.0/{client_id}` с `{"webhooksList":["acquiringInternetPayment"],"url":"https://..."}`. При регистрации Точка шлёт тестовый вебхук и не сохраняет адрес, если он не ответил 200. Только HTTPS на порту 443, один адрес на `client_id`.
   - Страница: `opisanie-metodov/vebhuki/acquiringInternetPayment`.
9. **Тестовая среда.** Адрес `https://enter.tochka.com/sandbox/v2`, ключ `sandbox.jwt.token`, `customerCode` `1234567ab`, `merchantId` `200000000001097`.
   - Ответы фиксированные и не зависят от запроса. Оплатить ссылку нельзя, вебхуков нет. Страница: `pesochnica`.
   - Проверено 2026-11-07 клиентом `core/tochka.py`:
     - создание подписки с чеком отвечает 200 со ссылкой;
     - статус подписки — `Active`;
     - операция — заготовка `APPROVED` с пустым `Order` и без `paymentLinkId` и `paidAt`;
     - отмена — 424 `Sandbox mock not found`.
   - Тестовая среда проверяет поля запроса: `http` в адресах возврата и почту на зарезервированном домене (`.test`) она отклоняет с 400. Ответ без токена приходит не в документированной форме, а как `{"message": "The access token is missing"}`.
   - Значит, тестовая среда проверяет только форму запросов и разбор ответов. Оплату, вебхук и очередное списание можно проверить только на настоящей Точке после подключения эквайринга.
10. **Чек ИП.**
    - `taxSystemCode`: `osn, usn_income, usn_income_outcome, esn, patent`.
    - `vatType`: `none, vat0, vat5, vat7, vat10, vat22, vat105, vat107, vat110, vat122`.
    - `paymentMethod`: `full_payment, full_prepayment`.
    - `paymentObject`: `goods, service, work`.
    - `measure`: по умолчанию `шт.`.
    - Как выбрать значения для ИП, документация не говорит. Это решение владельца (Open Questions). Чек оформляет партнёр Точки, выбранный при подключении.
11. **Ошибки.** Ответы 400, 403, 404, 424 и 500 приходят в виде `{"code","id","message","Errors":[{"errorCode","message","url"}]}`. 403 приходит при неверном `customerCode`, нехватке прав или удалённом ключе. Ограничений частоты и ключа идемпотентности для этих методов нет; от двойного создания защищает уникальный `paymentLinkId`.

## Goals / Non-Goals

**Goals:**
- Тариф меняет только операция, которую подтвердил ответ API Точки. Тело вебхука и возврат пользователя — лишь повод спросить Точку.
- Один и тот же платёж засчитывается один раз, сколько бы раз и какими путями о нём ни сообщили.
- Всё, что не удалось проверить без настоящей Точки, вынесено в явные проверки перед запуском продаж.

**Non-Goals:**
- Регистрация вебхука из кода. Адрес один на ключ, регистрирует его владелец при подключении (`PUT /webhook/v1.0/{client_id}`), команда записана в README.
- Чтение `customerCode` и `merchantId` из API при старте: это настройки сервера.
- Подписки без графика и свой планировщик списаний.

## Decisions

1. **Подписка с графиком: `Options {period: Month, trancheCount: 84}`.** Точка сама списывает раз в месяц, отмена — `Cancelled` через API. Так и написано в интенте («Точка каждый месяц списывает», «ядро отключает автосписание в Точке»).
   - Альтернатива: подписка без графика (`recurring: true`). Даты списаний были бы наши, но понадобился бы свой планировщик. Отменить такую подписку в Точке нельзя, можно только перестать списывать. Ответ `charge` не даёт идентификатора списания.
   - После 84 списаний (7 лет) подписка в Точке завершится. Пользователь увидит «Оплатить снова», как после неудачного списания.

2. **Клиент Точки — `agno/core/tochka.py`, без базы и без Agno.**
   - Методы: создать подписку с чеком, отменить подписку, прочитать статус подписки, прочитать операцию, проверить подпись вебхука.
   - Запросы через `httpx` (уже стоит как зависимость Agno, объявляется явно в `pyproject.toml`) с `verify=agno/litellm/certs/ca-bundle.pem`.
   - Ответ проверяется по схеме: нет обязательного поля или пришёл неизвестный статус — `TochkaError` с названием поля или статуса. Сетевая ошибка — `TochkaUnavailable`.
   - Тесты подменяют транспорт `httpx.MockTransport` и не ходят в сеть.

3. **Настройки — обязательные переменные окружения без значений по умолчанию:**
   - `TOCHKA_API_URL` — боевой или тестовый адрес, из двух известных. Другое значение — ошибка: ключ не должен уйти на чужой адрес.
   - `TOCHKA_JWT` — секрет.
   - `TOCHKA_CUSTOMER_CODE` — 9 символов.
   - `TOCHKA_MERCHANT_ID` — 15 цифр.
   - `TOCHKA_TAX_SYSTEM`, `TOCHKA_VAT_TYPE`, `TOCHKA_PAYMENT_METHOD` — значения из перечней Точки.
   - `TOCHKA_REDIRECT_URL`, `TOCHKA_FAIL_REDIRECT_URL` — https-адреса страниц возврата. Точка отклоняет `http` даже в тестовой среде (проверено), поэтому в разработке там стоят адреса сайта: оплатить в тестовой среде всё равно нельзя.

   Нет переменной или значение неверное — старт API падает с её именем. В разработке `.env` получает тестовую среду: значения из документации публичные, но в `example.env` они лежат закомментированными, как другие настройки. Реквизиты чека — не секрет, но это свойства ИП, а не тарифа, поэтому они живут в настройках сервера, а не в файле тарифов.
   - Альтернатива: реквизиты чека в файле тарифов. Тогда файл, которым владеет `usage-limits`, получил бы сведения о продавце, которые одинаковы у всех тарифов.

4. **Ключ подписи вебхука — файл в репозитории `agno/core/tochka_webhook_key.json`** (JWK с https://enter.tochka.com/doc/openapi/static/keys/public).
   - Тест проверяет пример тела из документации этим ключом, а поддельное тело отклоняет. Ключ публичный, а загрузка по сети при каждом старте сделала бы запуск API зависимым от сайта документации.
   - Если Точка сменит ключ, вебхуки начнут отклоняться с 400. Оплата всё равно подтвердится запросом при возврате пользователя и при сверке в конце периода (решение 7). Ключ обновляется релизом.
   - Альтернатива: читать ключ по адресу при старте, как советует документация. Отклонена: старт API зависел бы от внешнего сайта.

5. **Вебхук никогда не меняет тариф сам.**
   - `POST /api/v1/billing/tochka/webhook` исключён из проверки токена в `excluded_route_paths`. Маршрут проверяет подпись JWT и берёт из тела только `operationId`, а затем зовёт ту же операцию подтверждения, что и страница возврата.
   - Подтверждение читает `GET /payments/{operationId}` и засчитывает операцию, только если всё сходится:
     - `status == APPROVED`;
     - `customerCode` наш;
     - `paymentLinkId` совпадает с нашим оформлением;
     - сумма равна цене тарифа этого оформления;
     - есть `Order` типа `approval`.
   - Иначе ничего не меняется, а в лог пишется идентификатор операции и причина.
   - Ответ маршрута — 200, когда операция подтверждена, уже засчитана или не наша. 400 — при неверной подписи или теле. 503 — когда Точка недоступна, тогда она повторит вебхук.

6. **Один платёж — одна запись: ключ `(operation_id, order_id)`.** У каждого засчитанного списания есть `Order` типа `approval` со своим `orderId`, уникальный индекс не даёт засчитать его дважды.
   - Так работает при обоих вариантах, которые документация оставляет открытыми: очередное списание — новая операция с одним `approval` или новый `approval` в той же операции подписки.
   - Повторный вебхук, повторный опрос страницы возврата и сверка натыкаются на индекс и ничего не меняют.

7. **Сверка в конце оплаченного периода.** Когда период платной подписки кончился, а засчитанного списания на следующий нет, ядро один раз спрашивает Точку об операции подписки и засчитывает новые `approval`.
   - Сверку запускает `SubscriptionEnded` из `current_subscription`: его ловят операция `billing.settle_ended` и места, где подписку читают (pre-hook соавтора, `GET /billing`). Это происходит при первом обращении после конца периода, отдельного планировщика нет. Ошибка не глотается: после сверки подписка читается заново, а если сверка не удалась, обращение падает с её ошибкой.
   - Что делает сверка:
     - оформление отменено — `start_subscription(бесплатный тариф, 'granted', start=period_end)`;
     - не отменено, у Точки есть новое списание — `next_period`;
     - не отменено, списания нет — тот же бесплатный тариф, оформление получает `failed`.
   - «Бесплатный тариф» здесь и в спеках — это `signup_plan` из `plans.toml`, тот же, что получает новый пользователь. Отдельного ключа `free_plan` нет: решение 2026-11-07, переданное родительской сессией. К старту продаж владелец сменит `signup_plan` с `beta` на бесплатный тариф, его код и лимит тоже решает владелец.
   - Бесплатный тариф начинается с конца оплаченного периода, а не с текущего момента. Дальше `current_subscription` сама продлевает его до сегодняшнего периода.
   - Первая оплата и оплата после перехода на бесплатный тариф вызывают `start_subscription(тариф, 'tochka', start=paid_at)`. Очередное списание в срок вызывает `next_period`.
   - Новая подписка обнуляет расход: он считается по подписке. Поэтому после оплаты лимит платного тарифа начинается с нуля.
   - Если списания нет, подписка переходит на бесплатный тариф. Если она не была отменена, на ней ставится отметка «оплата не прошла».
   - Если Точка недоступна, обращение завершается явной ошибкой «не удалось проверить оплату», а тариф не меняется: это не fallback, решения без ответа Точки нет.
   - Если оплата придёт позже, вебхук вернёт платный тариф с периодом от даты оплаты.

8. **Данные ядра** (точные колонки — в фазе 2, по контракту подписок `usage-limits`):
   - `billing_checkouts` — одно оформление в Точке. Поля: пользователь, тариф, сумма, наш `payment_link_id` (UUID, он же `id`), `operation_id` подписки Точки, ссылка на оплату, статус (`created`, `active`, `cancelled`, `failed`, `expired`), время создания, отмены и истечения ссылки.
   - `payments` — засчитанные списания. Поля: оформление, пользователь, `operation_id`, `order_id`, сумма, время оплаты, оплаченный период; уникальный ключ `(operation_id, order_id)`.
   - Данных карты, `maskedPan` и `tokenCardId` в таблицах нет. В логах — только идентификаторы.
   - Таблица `subscriptions` получает источник `tochka`, а оформление — ссылку на свою подписку (`subscription_id`). Флагов отмены и автопродления у подписки нет: отмена и неудачное списание — это состояние оформления.
   - При старте у тарифов с `purchasable = true` проверяется, что `period_months = 1` и `price_rub > 0`. Подписка в Точке ежемесячная, и другой период с ней не сойдётся.

9. **Маршруты под `/api/v1/billing`:**
   - `GET /billing` — тариф, доля лимита, конец периода, дата следующего списания, состояние оформления, платные тарифы для покупки, последние платежи.
   - `POST /billing/checkout` с `{plan}` — создаёт оформление и отдаёт ссылку. Если открытое оформление того же тарифа ещё живо, отдаёт его ссылку и не создаёт второе в Точке.
   - `POST /billing/check` — страница возврата и кнопка «Проверить оплату» подтверждают открытое оформление.
   - `POST /billing/cancel` — отменяет подписку в Точке, затем помечает оформление отменённым. Тариф остаётся до конца периода.

   Маршруты пользователя работают только со своей записью (как `/me`) и получают scope автора. Запрос «Оформить» при действующей платной подписке отклоняется с 409.

10. **«Оплатить снова»** — новое оформление. Старую подписку в Точке ядро перед этим отменяет, если её статус ещё позволяет отмену (`Active`, `PastDue`, `Suspended`), чтобы Точка не списала по ней позже.

11. **Страница «Тариф» в `/settings`** и страницы возврата `/settings/billing/return` (`redirectUrl`) и `/settings/billing/fail` (`failRedirectUrl`).
    - Возврат после оплаты вызывает `POST /billing/check` до подтверждения, не дольше двух минут, затем предлагает «Проверить ещё раз».
    - Неудачный возврат (`failRedirectUrl`) показывает «Оплата не прошла» и «Оплатить снова».
    - Продуктовой логики на фронтенде нет: что показать, решает ответ `GET /billing`.

## Risks / Trade-offs

- [Тестовая среда не проводит оплату и не шлёт вебхуки] → тесты ядра подменяют клиента Точки, клиент проверяется на подменённом HTTP и против тестовой среды (форма запросов). Оплата, чек, вебхук и очередное списание проверяются вживую после подключения эквайринга. Это отдельный пункт `tmp/VERIFY.md` и условие начала продаж.
- [Документация не говорит, как помечено очередное списание по подписке с графиком] → решение 6 работает при обоих вариантах. Если вживую окажется иначе (нет `Order` или нет `paymentLinkId` у очередной операции), подтверждение явно откажет с названием поля. Тогда change правится через `/opsx:update`.
- [Значения статусов подписки не описаны] → ядро опирается на статус операции и `Order`, а статус подписки читает только для решения 10. Неизвестное значение — явная ошибка.
- [Списание приходит позже конца периода] → пользователь ненадолго видит бесплатный тариф и «оплата не прошла», после вебхука тариф вернётся. Принимается.
- [Точка недоступна в момент сверки] → соавтор и страница «Тариф» отвечают ошибкой, пока Точка не ответит. Это выбор «без fallback». Альтернатива — льготный срок, но это решение владельца.
- [JWT-ключ Точки истекает и перевыпускается вручную; при перевыпуске меняется `client_id` и слетает вебхук] → 403 от Точки пишется в лог как ошибка настройки. В README описан порядок перевыпуска: новый ключ в env, повторная регистрация вебхука.
- [Сертификат Минцифры] → используется уже собранный `ca-bundle.pem`. Его пересборка (`build_ca_bundle.sh`) затрагивает и API.
- [Почта уходит в Точку и к партнёру по чекам] → строка в `05-security-and-compliance.md`, текст политики ПДн готовит владелец.

## Migration Plan

1. Фаза 1: клиент и его тесты, этот change. Файлов `usage-limits` не трогаем.
2. Фаза 2, после влития `usage-limits`: миграция с `down_revision = "0009_subscriptions_usage"` (одна голова), таблицы, источник `tochka`, маршруты, веб, тесты на базе.
3. Выкладка: заполнить переменные `TOCHKA_*` в `/etc/authorled/authorled.env` до релиза, иначе API не стартует. До подключения эквайринга на сервере остаётся тестовая среда, а платные тарифы в файле тарифов не продаются: «можно купить» = нет.
4. Подключение (владелец): заявка, партнёр по чекам, JWT-ключ с правами, регистрация вебхука на `https://coauthor.glavai.ru/api/v1/billing/tochka/webhook`, боевые значения в env, проверка вживую по `tmp/VERIFY.md`.
5. Откат: релиз назад. Таблицы платежей остаются, миграции только вперёд.

## Open Questions

Ответы ждём от владельца, они меняют данные и настройки, а не устройство:

- Платные тарифы: сколько, код, название, цена и лимит у каждого.
- Код и лимит бесплатного тарифа, который станет `signup_plan` к старту продаж. Решено: после конца оплаты пользователь переходит на `signup_plan`, отдельного ключа нет.
- Система налогообложения ИП, НДС и признак способа расчёта (`full_prepayment` или `full_payment`) для чека.
