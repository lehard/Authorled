# Proposal: eval соавтора запускается от имени проверенного пользователя разработки

Бизнес-интент: `business-intents/eval-verified-caller.md` (вариант А согласован владельцем 2026-11-08).

## Why

С коммита `c7558fc` хук лимита соавтора `check_usage_limit` берёт автора из `run_principal`, а тот требует проверенного пользователя из токена. `python -m evals` запускает агента напрямую, без HTTP-запроса. Поэтому проверенного пользователя в запуске нет, и случай `coauthor_uses_context` падает с «Не удалось проверить лимит соавтора» ещё до вызова модели. Значит, поведение соавтора сейчас нельзя проверить ни одним кейсом. Ослаблять проверку лимита ради eval нельзя. Нужно, чтобы eval передавал настоящего проверенного пользователя тем же штатным способом Agno, каким его передаёт HTTP-слой.

## What Changes

- `./scripts/dev.sh auth-users` дополнительно создаёт или обновляет у `writer@authorled.test` пароль приложения Authentik из нового секрета `.env` `AUTH_DEV_WRITER_TOKEN`. Без секрета команда завершается ошибкой с его именем.
- Модуль `auth` (`agno/app/auth/`) получает функцию для доверенного кода на Python, только при `RUNTIME_ENV=dev`. Она получает токен `writer` у локального Authentik (`client_credentials` с паролем приложения) и проверяет его так же, как API: ключи `JWT_JWKS_FILE`, алгоритм `RS256`, издатель `AUTH_ISSUER`, аудитория `AUTH_FRONTEND_CLIENT_ID`, срок, claim `groups`. Возвращает она полномочия запуска Agno (`RunAuthorization`) с данными этого токена, почту и имя. Запрос к Authentik и чтение токена остаются внутри модуля: проверка границ `check_auth_boundary.sh` охватывает и `agno/evals/`.
- Случай `coauthor_uses_context` выполняется от имени `writer`:
  - перед запуском случай берёт удостоверение у этой функции;
  - создаёт аккаунт `writer` в ядре путём первого входа, если аккаунта нет;
  - запускает агента внутри `authorization_scope` Agno.

  Если чего-то нет или проверка не прошла, случай падает и называет причину. Пользователя по умолчанию или запуска без пользователя нет.
- Хуки лимита и журнала, `run_principal` и остальные случаи (`smoke`) не меняются. Случаи OS Manager по-прежнему идут без пользователя.

Расхождение с интентом. В интенте записано «проверенный пользователь передаётся всем случаям», «до первого случая». При проработке выяснилось, что это сломало бы `smoke`. Agno включает проверку прав для инструментов OS Manager, как только у запуска есть пользователь, а у группы `screenwriters` нет прав на OS Manager. Поэтому пользователь задаётся только случаям соавтора, а ошибка получения токена роняет случай соавтора, а не весь прогон. Тогда `--tag smoke` не зависит от Authentik и секрета.

## Capabilities

### New Capabilities
- нет.

### Modified Capabilities
- `runtime`: новое требование «Eval соавтора от имени пользователя разработки» — случай `coauthor_uses_context` (тег `coauthor`) выполняется от имени проверенного `writer`; отказы без секрета, без Authentik, вне `dev`; `smoke` от этого не зависит. «Evals» — фраза «по умолчанию устанавливать `RUNTIME_ENV=dev`» заменяется на то, что делает код: `RUNTIME_ENV` (`dev` или `prd`) обязателен, без значения по умолчанию (решение владельца 2026-11-08: спеку под код). Код здесь не меняется; ту же фразу в `AGENTS.md` правим вместе со спекой.
- `auth`: «Пользователи для разработки» — пароль приложения `writer` из `AUTH_DEV_WRITER_TOKEN`; новое требование «Полномочия запуска для доверенного кода» — модуль сам получает и проверяет токен `writer` и отдаёт полномочия запуска (код вне `agno/app/auth/` не обращается к Authentik и не читает токен).

## Scope

- `auth/blueprints-dev/dev-users.yaml` и шаг `auth-users` в `scripts/dev.sh`: пароль приложения `writer`.
- `example.env`: `AUTH_DEV_WRITER_TOKEN` в блоке «Development only».
- `agno/app/auth/`: проверка токена и сборка `RunAuthorization` для доверенного кода.
- `agno/evals/`: получение токена `writer`, аккаунт в ядре, `setup` и `teardown` случая соавтора.
- Мастер-спеки `runtime` и `auth`, README (раздел про evals), `tmp/VERIFY.md`.

## Non-goals

- Менять или отключать хуки лимита и журнала, вводить «режим тестов» в `run_principal`.
- Собирать проверенного пользователя из настройки без токена (вариант Б интента, отклонён).
- Запускать eval через HTTP API своим раннером, менять `Case` или раннер Agno.
- Передавать пользователя случаям OS Manager или давать eval права администратора.
- Запускать eval соавтора в контейнере API: оттуда адрес Authentik из `AUTH_ISSUER` (`localhost:9000`) недоступен, и случай падает с явной ошибкой. Eval соавтора запускается на хосте.
- Eval на сервере, с токенами production; отдельный пользователь или тариф для eval.

## Impact

- Разработка: `python -m evals --tag coauthor` снова доходит до модели. Ему нужен локальный стенд с Authentik, `./scripts/dev.sh auth-users` и `AUTH_DEV_WRITER_TOKEN` в `.env`. Eval тратит лимит `writer` и пишет расход в журнал.
- `--tag smoke` ведёт себя как сейчас.
- Production: не затрагивается. `compose.yaml` и `compose.prod.yaml` новый секрет не требуют, blueprint пользователей разработки применяет только `auth-users` при `RUNTIME_ENV=dev`.
- Зависимостей не добавляется: запрос токена к Authentik делается стандартной библиотекой Python (`urllib.request`).
