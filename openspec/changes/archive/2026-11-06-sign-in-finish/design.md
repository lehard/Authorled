# Design

## Context

Мотивация в `proposal.md`, поведение в дельте спеки. Что важно для решения:

- `RequireAuth` открывает `/login` с заменой записи, а `signIn` вызывает `signinRedirect` с настройкой по умолчанию, то есть `location.assign`. Поэтому `/login` остаётся в истории, и браузер может сохранить страницу в памяти.
- `signinRedirect` завершается по событию `pageshow`. При возврате из памяти обещание выполняется, а экран остаётся в стадии `finishing`: дальше ему идти некуда.
- Эффект проверки сессии в `LoginScreen` ставит `cancelled`, но проверяет его только перед `setChecking`. В `StrictMode` оба запуска получают общий `flow.start()` и оба вызывают `signIn`.
- Ошибка `page` выводится под карточкой, а карточка стадии `finishing` остаётся спиннером. Кнопка там одна, «Начать заново», она возвращает к почте. При готовой сессии шаг почты отвечает «В Authentik уже есть вход: обновите страницу».
- Автотестов экранов в `web/` нет: проверка идёт в браузере.

## Goals / Non-Goals

**Goals:**
- Закрыть воспроизведённое зависание и любую другую причину бесконечного «Входим…».

**Non-Goals:**
- Менять поток входа и хранение токенов.
- Ставить предел на «Проверяем вход…» (см. Risks).

## Decisions

1. **Переход с заменой записи.** `signinRedirect({ state, redirectMethod: "replace" })`. Запись `/login` заменяется, затем `/auth/callback` заменяется адресом возврата. Возвращаться некуда.
   Альтернатива: перезагружать страницу по `pageshow` с `persisted`. Тогда `/login` останется в истории, и «Назад» будет перебрасывать автора вперёд, не давая уйти из приложения.

2. **Один предел в `userManager.ts`.** Постоянная `SIGN_IN_TIMEOUT_MS = 20_000` и текст причины рядом. Таймер живёт в эффекте экрана: в `LoginScreen` пока стадия `finishing`, в `CallbackScreen` пока нет ошибки. Запрос таймер не прерывает: если вход успеет завершиться позже, страница уйдёт сама.

3. **Сбой на `/login` показывается вместо спиннера.** Стадия `finishing` с ошибкой `page` рисует «Не удалось войти», причину и «Попробовать снова»; общий блок ошибки в этой стадии не выводится. Этот же вид получает сбой самого `signIn`, который сейчас показывается рядом со спиннером.

4. **«Попробовать снова» перезагружает страницу на `/login`.** Перезагрузка заново проходит проверку: есть токены — идём дальше, есть сессия — новый переход, нет сессии — форма. Адрес возврата остаётся в `returnTo`.
   Альтернатива: `restart()`. Он ведёт к почте и упирается в отказ при готовой сессии.
   На `/auth/callback` код уже нельзя использовать повторно, поэтому кнопка, как и сейчас, ведёт на `/login`; меняется только её подпись. Адрес возврата там не сохраняется, автор попадает на полку.

5. **Отменённый запуск останавливается.** В эффекте после `await flow.current.start()` стоит проверка `cancelled` до `setStage` и `signIn`. Второй запуск эффекта получает тот же результат и идёт дальше один.

## Risks / Trade-offs

- [«Проверяем вход…» тоже может ждать бесконечно, если Authentik молчит] → вне этого change, на экране ждут ответа запроса, а не перехода. Если понадобится, тот же приём применяется отдельно.
- [Если после выхода открыть адрес поверх `/login` и войти, «Назад» покажет старую форму почты] → принято владельцем 2026-11-06: случай редкий, ничего не зависает, а перезагрузка при возврате перебрасывала бы автора вперёд.
- [Вход дольше 20 секунд покажет ошибку, хотя мог бы завершиться] → страница всё равно уйдёт сама, если переход случится.
- [Режим разработки и сборка ведут себя по-разному: `StrictMode` дублирует эффекты только в разработке] → проверка на обоих.
- [Проверка на сборке требует порт 5173: на него зарегистрирован адрес возврата] → сервер разработки на время останавливается и потом возвращается.
