# Spec Delta

## Purpose
Тарифы и цены моделей как данные, подписка пользователя на тариф с периодом и лимитом, журнал расхода соавтора в рублях, проверка лимита и команды администратора по расходу. Всё это принадлежит модулю биллинга (`billing/module`). Оплата и платные тарифы (`payments-tochka`) строятся поверх этих правил.

## ADDED Requirements

### Requirement: Тарифы как данные
Тарифы MUST задаваться файлом данных биллинга, а не кодом. У тарифа MUST быть код (`[a-z0-9-]+`), название, цена в рублях за период, длина периода в месяцах (не меньше 1), лимит расхода в рублях за период и признак «можно купить»; все поля обязательны, другие поля MUST отклоняться. Файл MUST называть тариф новых аккаунтов, и он MUST быть в списке тарифов. В поставке MUST быть тариф `beta`: 0 ₽, период 1 месяц, лимит 500 ₽, купить нельзя; он же тариф новых аккаунтов. Ошибка в файле MUST останавливать старт API с ошибкой, называющей файл и поле.

#### Scenario: Тариф beta
- GIVEN файл тарифов из поставки
- WHEN API стартует
- THEN тариф `beta` MUST иметь цену 0 ₽, период 1 месяц, лимит 500 ₽, признак «можно купить» = нет, и он MUST быть тарифом новых аккаунтов

#### Scenario: Поле пропущено
- GIVEN в тарифе нет лимита
- WHEN API стартует
- THEN старт MUST завершиться ошибкой, называющей тариф и поле

#### Scenario: Тариф новых аккаунтов не из списка
- GIVEN файл называет тарифом новых аккаунтов `trial`, а такого тарифа в нём нет
- WHEN API стартует
- THEN старт MUST завершиться ошибкой, называющей `trial`

### Requirement: Цены моделей как данные
Цена псевдонима модели LiteLLM MUST задаваться файлом данных биллинга: рубли за миллион токенов входа, входа из кэша и выхода, все неотрицательные и обязательные. Если у модели соавтора нет цены, API MUST NOT стартовать, а ошибка MUST называть модель. Стоимость запуска MUST считаться так: (вход − вход из кэша) × цена входа + вход из кэша × цена кэша + выход × цена выхода, делённое на миллион; токены входа включают токены из кэша. Стоимость LiteLLM в долларах MUST храниться только для сверки и MUST NOT влиять на расход.

#### Scenario: Расчёт стоимости
- GIVEN цена модели 30 ₽ вход, 0,6 ₽ кэш, 120 ₽ выход за миллион
- WHEN запуск потратил 10 000 токенов входа, из них 4 000 из кэша, и 2 000 токенов выхода
- THEN стоимость MUST быть 0,4224 ₽

#### Scenario: Модели нет в файле цен
- GIVEN у модели соавтора нет строки в файле цен
- WHEN API стартует
- THEN старт MUST завершиться ошибкой, называющей эту модель

### Requirement: Подписка пользователя
У каждого пользователя MUST быть ровно одна действующая подписка: тариф, начало подписки, начало и конец текущего периода, статус (`active` или `ended`), источник. Единственный источник сейчас — `granted` («выдана», бесплатно для пользователя). Вторая действующая подписка того же пользователя MUST отклоняться базой. Новая подписка MUST заканчивать прежнюю действующую, а закончившиеся MUST оставаться в истории. Первый период длится столько месяцев, сколько у тарифа, от начала подписки; день месяца MUST прижиматься к последнему дню короткого месяца и возвращаться к своему дню в длинном.

#### Scenario: Подписка от 31 января
- GIVEN подписка на месячный тариф началась 31 января в 10:00 UTC
- WHEN наступают следующие периоды
- THEN они MUST кончаться 28 (или 29) февраля, 31 марта и 30 апреля в 10:00 UTC

#### Scenario: Вторая действующая подписка
- GIVEN у пользователя есть действующая подписка
- WHEN в базу вставляется вторая действующая подписка этого пользователя
- THEN база MUST отклонить вставку

### Requirement: Продление выданной подписки
Расход MUST считаться за текущий период подписки, а не за календарный месяц. Когда период выданной подписки кончился, при следующем обращении биллинг MUST сдвинуть период вперёд, пока он не накроет текущий момент, и расход нового периода MUST начинаться с нуля. Подписку другого источника с истёкшим периодом биллинг MUST NOT продлевать само: обращение MUST завершаться явной ошибкой.

#### Scenario: Конец периода
- GIVEN выданная подписка с периодом 7 ноября — 7 декабря и расходом 500 ₽
- WHEN 8 декабря автор пишет соавтору
- THEN период MUST стать 7 декабря — 7 января, расход MUST быть 0 ₽, и соавтор MUST ответить

#### Scenario: Пропущенные месяцы
- GIVEN выданная подписка с периодом, кончившимся три месяца назад
- WHEN автор пишет соавтору
- THEN текущий период MUST содержать текущий момент, и подписка MUST остаться одной строкой

### Requirement: Журнал расхода соавтора
После каждого запуска соавтора биллинг MUST записывать в журнал по каждой модели запуска: пользователя, подписку, запуск, беседу, агента, модель, статус запуска, токены входа, входа из кэша и выхода, стоимость в рублях, стоимость LiteLLM в долларах (если есть) и время начала запуска. Повторная запись того же запуска и модели MUST NOT создавать вторую строку. Упавшие и отменённые запуски беседы, у которых есть токены, MUST дописываться в журнал при следующем запуске той же беседы. Завершённый запуск без токенов модели MUST давать явную ошибку записи. В журнале MUST NOT быть текста произведений и почты.

#### Scenario: Одна запись на запуск
- GIVEN автор отправил соавтору сообщение, и запуск завершился
- WHEN post-hook записывает запуск второй раз
- THEN в журнале MUST быть ровно одна строка этого запуска с токенами и стоимостью в рублях

#### Scenario: Отменённый запуск
- GIVEN автор остановил ответ после вызова модели, и запуск сохранён отменённым с токенами
- WHEN автор пишет в ту же беседу снова
- THEN отменённый запуск MUST появиться в журнале со статусом `cancelled` до проверки лимита

### Requirement: Проверка лимита до запуска
До вызова модели соавтор MUST сравнивать расход за текущий период подписки с лимитом тарифа. Если расход не меньше лимита, запуск MUST завершаться отказом без вызова модели с сообщением «Лимит соавтора на этот период исчерпан. Он обновится <день и месяц конца периода по Москве>.» и признаком причины `usage_limit_reached` и датой обновления в данных события ошибки. Если период подписки, которая не продлевается сама, кончился, запуск MUST завершаться отказом с признаком `subscription_ended`, идентификатором подписки, тарифом и концом периода. Если нет аккаунта, действующей подписки, тариф подписки не из файла или проверка не удалась по другой причине, запуск MUST завершаться отказом с признаком `usage_check_failed`, а не запускаться без лимита.

#### Scenario: Лимит исчерпан
- GIVEN расход за период 7 ноября — 7 декабря достиг 500 ₽ при лимите 500 ₽
- WHEN автор пишет соавтору
- THEN модель MUST NOT вызываться, а событие ошибки запуска MUST содержать «Лимит соавтора на этот период исчерпан. Он обновится 7 декабря.»

#### Scenario: Неизвестный тариф
- GIVEN действующая подписка пользователя ссылается на тариф `old`, которого нет в файле
- WHEN автор пишет соавтору
- THEN запуск MUST завершиться отказом с признаком `usage_check_failed`, а в логе MUST быть названо `old`

#### Scenario: Подписка закончилась
- GIVEN период подписки, которая не продлевается сама, кончился
- WHEN автор пишет соавтору
- THEN модель MUST NOT вызываться, а данные события ошибки MUST содержать признак `subscription_ended` и идентификатор подписки

#### Scenario: Нет подписки
- GIVEN у пользователя нет действующей подписки
- WHEN автор пишет соавтору
- THEN запуск MUST завершиться отказом с признаком `usage_check_failed`, модель MUST NOT вызываться

### Requirement: Смена тарифа
Смена тарифа MUST менять только тариф действующей подписки: начало и конец периода и накопленный расход MUST сохраняться, лимит MUST сразу браться из нового тарифа. Тариф не из файла MUST отклоняться ошибкой, называющей его.

#### Scenario: Тариф с большим лимитом
- GIVEN расход пользователя 500 ₽ на тарифе `beta`, и в файле есть тариф `beta-plus` с лимитом 1500 ₽
- WHEN администратор переводит его на `beta-plus`
- THEN следующий запрос к соавтору MUST пройти, а период MUST остаться прежним

### Requirement: Команды администратора
Скрипт администратора MUST требовать цель (`local` или `prod`) и выполнять команды в контейнере API через операции биллинга, а почты MUST брать у ядра:
- `report` — по каждому неудалённому пользователю почта, тариф, начало и конец текущего периода, число запусков, токены (вход, кэш, выход), расход в рублях, лимит, остаток и сумма LiteLLM в долларах за период;
- `set-plan <почта> <тариф>` — смена тарифа пользователя с этой почтой.
Если неудалённых пользователей с почтой нет или их больше одного, `set-plan` MUST завершаться ошибкой и ничего не менять. Других ручных настроек лимита MUST NOT быть.

#### Scenario: Отчёт
- GIVEN у пользователя за период два запуска соавтора
- WHEN администратор выполняет `report`
- THEN строка пользователя MUST показывать его почту, 2 запуска, сумму их токенов и расход, а остаток MUST быть лимитом минус расход

#### Scenario: Неизвестная почта
- GIVEN нет пользователя с почтой `nobody@example.com`
- WHEN администратор выполняет `set-plan nobody@example.com beta`
- THEN команда MUST завершиться ненулевым кодом с сообщением о почте

#### Scenario: Удалённый пользователь не в отчёте
- GIVEN аккаунт пользователя удалён (`deleted_at` заполнено), а его подписка и журнал остались в биллинге
- WHEN администратор выполняет `report`
- THEN строки этого пользователя в отчёте MUST NOT быть

### Requirement: Подписка при входе
Подписку на тариф новых аккаунтов MUST выдавать биллинг по идентификатору пользователя ядра, когда пользователь входит в сервис. Подписка MUST выдаваться только пользователю, у которого в биллинге нет ни одной подписки, ни действующей, ни закончившейся; иначе выдача MUST ничего не менять. Биллинг MUST NOT выдавать подписку сам при проверке лимита или записи расхода: пользователь без действующей подписки получает отказ проверки лимита.

#### Scenario: Первый вход
- GIVEN у пользователя ядра нет подписки
- WHEN он входит в сервис
- THEN у него MUST появиться одна действующая подписка `beta` с источником `granted` и периодом в месяц от времени создания аккаунта

#### Scenario: Повторный вход
- GIVEN у пользователя есть действующая подписка `beta-plus`, на которую его перевёл администратор
- WHEN он входит снова
- THEN у него MUST остаться ровно одна действующая подписка `beta-plus` с прежним периодом

#### Scenario: Подписка закончилась
- GIVEN у пользователя есть только закончившаяся подписка
- WHEN он входит снова
- THEN новая подписка MUST NOT появиться

#### Scenario: Подписки не выдано
- GIVEN аккаунт создан, а выдача подписки не выполнилась
- WHEN автор пишет соавтору до следующего входа
- THEN запуск MUST завершиться отказом с признаком `usage_check_failed` без вызова модели
