# Spec Delta

## Purpose
Граница модуля биллинга внутри модульного монолита: его код, публичный интерфейс, данные в своей схеме и своя цепочка миграций. Модуль устроен так, чтобы потом его можно было вынести в отдельный сервис, не меняя вызывающий код.

## ADDED Requirements

### Requirement: Граница модуля биллинга
Код биллинга MUST лежать в своём модуле `billing/` бэкенда и MUST NOT зависеть от ядра, слоя приложения, агентов, команд администратора и фреймворка Agno. Другие модули MUST обращаться к биллингу только через его публичный интерфейс и MUST NOT импортировать его внутренние части. Ядро MUST NOT вызывать биллинг; связывает их слой приложения.

#### Scenario: Чистая граница
- GIVEN код репозитория соблюдает границу биллинга
- WHEN выполняется `./scripts/validate.sh`
- THEN проверка границы биллинга MUST пройти

#### Scenario: Биллинг импортирует ядро
- GIVEN модуль внутри `billing/` импортирует модуль ядра
- WHEN выполняется проверка границы биллинга
- THEN проверка MUST завершиться ненулевым кодом и назвать файл и импорт

#### Scenario: Внутренний модуль снаружи
- GIVEN код вне `billing/` импортирует внутренний модуль биллинга, а не его публичный интерфейс
- WHEN выполняется проверка границы биллинга
- THEN проверка MUST завершиться ненулевым кодом и назвать файл и импорт

#### Scenario: Ядро вызывает биллинг
- GIVEN модуль ядра импортирует биллинг
- WHEN выполняется проверка границы биллинга
- THEN проверка MUST завершиться ненулевым кодом и назвать файл

#### Scenario: Рабочие копии агентов
- GIVEN в `.claude/worktrees/<имя>/` лежит копия репозитория с нарушением границы, а в файлах репозитория нарушений нет
- WHEN выполняется проверка границы биллинга
- THEN проверка MUST пройти

### Requirement: Интерфейс биллинга
Публичный интерфейс биллинга MUST давать операции: выдать подписку при входе, проверить лимит, записать расход запусков, найти беседу запуска пользователя, построить отчёт по расходу и сменить тариф. Операции MUST принимать и возвращать простые значения (идентификаторы, числа, строки, время, неизменяемые записи) и MUST NOT принимать соединение с базой. Каждая операция MUST выполняться в своей транзакции: при ошибке её изменения MUST NOT сохраняться.

#### Scenario: Ошибка посреди записи расхода
- GIVEN запись расхода двух запусков, второй из которых нарушает ограничение журнала
- WHEN вызывается операция записи расхода
- THEN операция MUST завершиться ошибкой
- AND в журнале MUST NOT появиться строки ни одного из двух запусков

#### Scenario: Пользователь в отчёте по идентификатору
- GIVEN у пользователя есть подписка и расход
- WHEN вызывается операция отчёта
- THEN строка отчёта MUST называть пользователя его идентификатором ядра и MUST NOT содержать почты

#### Scenario: Беседа чужого запуска
- GIVEN в журнале есть запуск `r1` пользователя А
- WHEN беседу запуска `r1` ищут для пользователя Б
- THEN операция MUST завершиться отказом «запуск не найден», как для несуществующего запуска

### Requirement: Схема данных биллинга
Данные биллинга MUST храниться в схеме `billing` общей базы, отдельно от схем `authorled`, `ai`, `authentik` и `public`. Владельцем схемы MUST быть роль `agentos`; схему MUST создавать идемпотентный шаг инициализации базы до миграций. Таблицы биллинга MUST NOT иметь внешних ключей на таблицы других схем: пользователь связан с биллингом по значению своего идентификатора. Ядро MUST NOT читать и менять схему `billing`, биллинг — другие схемы.

#### Scenario: Чистая база
- GIVEN база без схемы `billing`
- WHEN выполняется шаг инициализации
- THEN схема `billing` MUST существовать и принадлежать роли `agentos`

#### Scenario: Повторная инициализация
- GIVEN схема `billing` с таблицами и данными
- WHEN шаг инициализации выполняется ещё раз
- THEN он MUST завершиться успешно, а таблицы и данные схемы `billing` MUST остаться без изменений

#### Scenario: Нет связей с другими схемами
- GIVEN все миграции применены
- WHEN перечисляются внешние ключи таблиц схемы `billing`
- THEN ни один из них MUST NOT ссылаться на таблицу вне схемы `billing`

### Requirement: Таблица подписок биллинга
Схема `billing` MUST содержать таблицу `subscriptions`:
- `id` — `uuid`, первичный ключ;
- `user_id` — обязательный `uuid` пользователя ядра, без внешнего ключа;
- `plan` — непустой код тарифа из файла тарифов (не внешний ключ);
- `source` — `granted`, другое база отклоняет;
- `status` — `active` или `ended`, другое база отклоняет;
- `started_at`, `period_start`, `period_end` — обязательные времена с поясом, `period_end` позже `period_start`;
- `ended_at` — заполнено тогда и только тогда, когда `status` = `ended`;
- `created_at`, `updated_at` — по умолчанию время вставки.
У пользователя MUST быть не больше одной строки со `status` = `active`.

#### Scenario: Период наоборот
- GIVEN пользователь без подписок
- WHEN вставляется подписка с `period_end` раньше `period_start`
- THEN база MUST отклонить вставку

#### Scenario: Закончившаяся без времени
- GIVEN действующая подписка
- WHEN ей ставится `status` = `ended` без `ended_at`
- THEN база MUST отклонить запись

#### Scenario: Вторая действующая подписка
- GIVEN у пользователя есть действующая подписка
- WHEN вставляется вторая действующая подписка этого пользователя
- THEN база MUST отклонить вставку

### Requirement: Таблица журнала расхода биллинга
Схема `billing` MUST содержать таблицу `usage_records`, одна строка на запуск и модель:
- `id` — `uuid`, первичный ключ;
- `user_id` — обязательный `uuid` пользователя ядра, без внешнего ключа; `subscription_id` — ссылка на `billing.subscriptions.id`, удаление подписки с расходом база отклоняет;
- `run_id`, `session_id`, `agent_id`, `model` — непустой текст;
- `run_status` — `completed`, `error` или `cancelled`;
- `input_tokens`, `cache_read_tokens`, `output_tokens` — неотрицательные целые, кэш не больше входа;
- `cost_rub` — неотрицательное, шесть знаков; `provider_cost_usd` — такое же или пусто;
- `occurred_at`, `created_at`.
Пара `run_id`, `model` MUST быть уникальной.

#### Scenario: Повтор запуска
- GIVEN в журнале есть строка запуска `r1` модели `deepseek-fast`
- WHEN вставляется вторая строка `r1` и `deepseek-fast`
- THEN база MUST отклонить вставку

#### Scenario: Кэш больше входа
- GIVEN подписка пользователя
- WHEN вставляется строка с `cache_read_tokens` больше `input_tokens`
- THEN база MUST отклонить вставку

#### Scenario: Подписка с расходом
- GIVEN у подписки есть строки журнала
- WHEN подписка удаляется
- THEN база MUST отклонить удаление

### Requirement: Миграции биллинга
Структура схемы `billing` MUST меняться только своей цепочкой миграций, отдельной от цепочки ядра. Миграции MUST идти только вперёд, у цепочки MUST быть ровно одна голова, журнал применённых миграций MUST храниться в схеме `billing`. Шаг миграций MUST применять сначала цепочку ядра, потом цепочку биллинга; ошибка любой из них MUST завершать шаг ненулевым кодом с названием миграции, и API MUST NOT стартовать. Тесты на чистой базе MUST применять обе цепочки.

#### Scenario: Чистая база
- GIVEN база после шага инициализации без таблиц
- WHEN выполняется шаг миграций
- THEN обе цепочки MUST примениться, а журналы в схемах `authorled` и `billing` MUST указывать на последние миграции своих цепочек

#### Scenario: Повторный шаг
- GIVEN все миграции обеих цепочек применены
- WHEN шаг миграций выполняется ещё раз
- THEN он MUST завершиться успешно без изменений в базе

#### Scenario: Ошибка миграции биллинга
- GIVEN миграция биллинга, которая завершается ошибкой
- WHEN выполняется `docker compose up`
- THEN шаг миграций MUST завершиться ненулевым кодом, а API MUST NOT стартовать

#### Scenario: Две головы у цепочки биллинга
- GIVEN в цепочке миграций биллинга две головы
- WHEN выполняется `./scripts/validate.sh`
- THEN проверка MUST завершиться ненулевым кодом с сообщением, называющим головы

#### Scenario: Описание таблиц совпадает с базой
- GIVEN все миграции применены
- WHEN описание таблиц биллинга в коде сравнивается со схемой `billing`
- THEN расхождений MUST NOT быть

### Requirement: Перенос данных биллинга из схемы ядра
Первая миграция биллинга MUST перенести таблицы `subscriptions` и `usage_records` со всеми строками из схемы `authorled` в схему `billing` и снять их внешние ключи на `authorled.users`. После неё в схеме `authorled` MUST NOT оставаться этих таблиц. Идентификаторы подписок и строк журнала MUST сохраняться. Это единственная миграция биллинга, которой разрешено менять объекты схемы `authorled`.

#### Scenario: Подписки и журнал на месте
- GIVEN в `authorled.subscriptions` три подписки, а в `authorled.usage_records` пять строк
- WHEN применяется миграция переноса
- THEN в `billing.subscriptions` MUST быть те же три подписки с теми же `id`, а в `billing.usage_records` — те же пять строк
- AND таблиц `subscriptions` и `usage_records` в схеме `authorled` MUST NOT быть

#### Scenario: Соавтор после переноса
- GIVEN у пользователя был расход 120 ₽ за текущий период до переноса
- WHEN после переноса он пишет соавтору
- THEN проверка лимита MUST учесть эти 120 ₽
