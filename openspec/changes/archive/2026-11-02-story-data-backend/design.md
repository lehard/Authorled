# Design: данные истории в ядре

## Context

Мотивация — `proposal.md`, требования — `specs/`. Что есть сейчас:

- Ядро `agno/core/` — независимый от Agno код с собственным пулом (`core.engine.get_engine()`, синхронный SQLAlchemy Core), таблицы описаны в `core/tables.py` и создаются ручными миграциями Alembic (`0001`, `0002`). Тесты — pytest на `ai_test` с откатом транзакции (`tests/conftest.py`).
- Свои маршруты — `agno/app/api/`: роутер `me.py`, ошибки `Problem` → `application/problem+json`, тело читается и проверяется вручную (ошибки валидации FastAPI ушли бы в обработчик Agno), синхронные операции ядра — через `run_in_threadpool`. `attach_api` ставит роутеры перед корневым MCP-монтированием.
- Модуль `auth`: `Principal` (`user_id` = `sub`), `can_access_project(principal, project_id)` с источником `ProjectAccessSource`, который должно зарегистрировать ядро; сейчас он не зарегистрирован, и вызов падает `ProjectAccessNotConfigured`.
- Соавтор — `agno/agents/coauthor.py` без инструментов, промпт из `agno/skills/coauthor/SKILL.md` (change `agent-prompts-as-skills`, 10/11 задач). Беседа — сессия Agno с id `<projectId>:<uuid>`, `user_id` запуска — `sub` токена.
- Формат текста — JSON ProseMirror из `web/src/editor/schema/index.ts` и `elements.ts`: 14 типов абзацев, `pageBreak`, метки `bold|italic|underline|textColor|highlight|comment|suggestion`; у `sceneHeading` атрибуты `alt`, `day`, `color`, `tags`, `uid` пока нет.
- Импорт Fountain и FDX есть только в браузере (`web/src/editor/importers/`). `python-docx`, `pypdf`, `lxml`, `python-multipart` уже стоят. ClamAV в compose нет.

## Goals / Non-Goals

**Goals:**
- Ядро — единственный источник истины об истории; маршруты и инструменты соавтора вызывают одни и те же операции ядра.
- Каждый отказ явный: неверные данные, конфликт ревизий, недоступный антивирус, непонятный файл.
- Схема данных переживает следующий change (`story-data-web`) без миграций.

**Non-Goals:**
- Асинхронный SQLAlchemy, очередь Agno для загрузок, SSE-события об изменениях.
- Общая библиотека схемы текста для Python и TypeScript: схема дублируется и сверяется тестом на образцах.

## Decisions

### 1. Модули ядра
`core/tables.py` пополняется таблицами, операции раскладываются по модулям: `projects.py` (истории и доступ), `documents.py` (документы, поля по видам, порядок, корзина), `texts.py` (проверка формата, ревизии, драфты), `review.py` (комментарии, предложения), `files.py` (загрузка, типы, извлечение текста), `clamav.py` (клиент), `importers/` (`fountain.py`, `fdx.py`, `plain.py` для DOCX/TXT, общий `screenplay.py` — сборка документа, `uid`, персонажи и локации). Ошибки ядра — свои исключения (`NotFound`, `Conflict`, `Invalid`, `Locked`, `ScannerUnavailable`); маршруты переводят их в `Problem`. Почему не один модуль `stories.py`: файлы и импорт тянут разбор форматов и сеть, им не место рядом с CRUD.

### 2. Одна таблица `documents` с `fields` JSONB
Поля по видам описываются в ядре моделями Pydantic (`extra="forbid"`, все поля строковые и необязательные, кроме структурных у сценария: `show` — словарь булевых по частям, `title_page` — объект). Профиль STARC повторяет `PROFILE` макета v2 (`web/src/data/profiles.ts`). База проверяет только то, что от вида не зависит (CHECK на `kind`, `role` по виду, `jsonb_typeof(fields) = 'object'`, частичный уникальный индекс `script`). `PATCH` сливает переданные ключи `fields` с сохранёнными и проверяет результат целиком. Альтернатива — таблица на вид: 5 почти одинаковых таблиц, 5 наборов маршрутов, корзина и дерево собираются объединением.

### 3. Текст целиком с ревизией
`screenplay_texts.revision` и `documents.revision` — оптимистическая блокировка: `UPDATE … WHERE revision = :expected RETURNING`; ноль строк — `409`. `If-Match` несёт число ревизии (без кавычек ETag); отсутствие — `428`. Ответы `GET` отдают ревизию и в теле, и в `ETag`. Проверка текста — рекурсивный обход JSON по таблице типов и меток (не ProseMirror: на Python его нет); список типов — константа ядра, тест сверяет её с `ELEMENTS` фронтенда разбором `elements.ts` регулярным выражением. Альтернатива — хранение по сценам: сложнее, а выгоды для одного автора нет.

### 4. Доступ
Ядро даёт `ProjectAccess` с методом `can_access(principal, project_id)`: истина, если история существует и её `owner_id` — пользователь с `auth_subject = principal.user_id` (история в корзине тоже доступна — иначе её не восстановить). `app/main.py` регистрирует его через `set_project_access_source` при старте; ядро не импортирует `app.auth`, протокол утиный. Маршрут сначала находит `project_id` ресурса (документ, ветка, предложение, файл), затем вызывает `can_access_project`; нет ресурса или нет доступа — одинаковый `404`. Для создания истории маршрут находит `users.id` по `sub`; записи нет — `404` с отсылкой к `GET /api/v1/me` (как `PATCH /me`).

### 5. Инструменты соавтора — функции Agno внутри процесса
Инструменты — Python-функции (`agno/agents/coauthor_tools.py`) с параметром `run_context: RunContext`, которые вызывают те же операции ядра. История — из `run_context.session_id` (префикс до `:` — UUID истории, иначе отказ); вызывающий — `Principal`, который строит новая функция модуля `auth` `run_principal(run_context)` из `run_context.authorization.context` (`principal_id`, `claims.groups`); без авторизации в запуске — ошибка, а не пропуск проверки. Далее — `can_access_project`. Ответы инструментов — компактный текст/JSON для модели; ошибки — строка отказа с причиной (модель должна их видеть), не исключение, роняющее ход. Почему не отдельный MCP-сервер ядра: агент живёт в том же процессе, MCP добавил бы транспорт, авторизацию и сериализацию без выгоды; «MCP-инструменты ядра» из `03-architecture.md` понимаем как «инструменты, вызывающие ядро». Внешним MCP-клиентам инструменты ядра не публикуются.

### 6. Файлы: синхронный конвейер в запросе
Порядок: чтение потока multipart с лимитом 20 МБ (превышение — `413`, читаем не больше 20 МБ + 1 байт) → тип по расширению и сигнатуре (ZIP для DOCX, `%PDF`, XML для FDX, UTF-8 для текстовых) → ClamAV → извлечение текста → одна транзакция `files` + `file_contents`. Байты в `bytea` отдельной таблицей, чтобы метаданные читались без них. Альтернативы: очередь Agno со статусами (лишнее для файлов до 20 МБ, разбор быстрее сети), S3/том (второй источник данных и бэкапа на одном хосте).

### 7. Клиент ClamAV — свой, протокол `INSTREAM`
~40 строк на `socket`: `zINSTREAM\0`, куски с 4-байтной длиной, нулевой кусок, ответ `stream: OK` / `… FOUND`. Таймаут из кода, адрес из обязательных `CLAMAV_HOST`/`CLAMAV_PORT`: их проверяет старт API (как `JWT_JWKS_FILE`), без них API не запускается. Нет соединения, таймаут или неожиданный ответ — `ScannerUnavailable` → `503`. Пакеты `clamd`/`pyclamd` не берём: не поддерживаются годами. Образ — `clamav/clamav` с закреплённой версией (debian-вариант, чтобы ARM-хосты разработчиков работали), том для баз, healthcheck `clamdcheck`.

### 8. Импорт — один формат-посредник
Каждый разборщик выдаёт список `(тип абзаца, текст, параметры сцены)`; `screenplay.py` собирает из него документ редактора, выдаёт `uid` (`uuid4`) каждому заголовку сцены, проверяет результат той же проверкой текста и извлекает персонажей и локации по правилу «Найти всех персонажей в тексте» (`web/workspace`). Fountain переносится на Python с правил `web/src/editor/importers/fountain.ts` (`TAGS`, переходы, русские заголовки), FDX — по атрибуту `Type` абзацев и таблице `ELEMENTS[*].fdx`. DOCX — абзацы `python-docx` как строки Fountain; TXT — строки как Fountain (обе ветки — «рукопись без разметки»). STARC вынесен в change `starc-import` (2026-11-02): без образца файла разбор не начинается, а `.starc` здесь отклоняется как неподдерживаемый тип.

Импорт в существующую историю: текст заменяется с проверкой ревизии в той же транзакции, что и добавление персонажей и локаций. Новая история из файла: `POST /api/v1/projects` принимает сам файл в multipart (решение 2026-11-02: `file_id` при создании истории взять неоткуда — файлы загружаются в историю). Проверка файла (размер, тип, ClamAV, разбор) идёт до записи, затем история, сценарий, файл и документы — одна транзакция.

### 9. Удаление навсегда — каскады базы
`ON DELETE CASCADE` от `projects` к `documents`, `files`; от `documents` к `screenplay_texts`, `comment_threads`, `suggestions`; от веток к сообщениям; от `files` к `file_contents`. Ссылки на `users` — `RESTRICT`. Код удаляет одну строку, база — остальное; тест проверяет, что ничего не осталось.

### 10. Маршруты
Роутеры `app/api/projects.py`, `documents.py`, `review.py`, `files.py`, общий разбор тела и `If-Match` — `app/api/body.py` (вынос из `me.py` без изменения поведения `/me`). Multipart читается вручную через `request.form()` с лимитом, а не параметрами `UploadFile`, по той же причине, что и тело `PATCH /me`. Схемы ответов — Pydantic для OpenAPI.

## Risks / Trade-offs

- [Схема текста в двух языках расходится] → константа типов в ядре, тест сверяет её с `elements.ts`; образцы JSON из фикстур фронтенда проходят проверку ядра в тестах.
- [Fountain на Python расходится с экспортом редактора] → образцы, выгруженные экспортом редактора (`web/src/editor/exporters/fountain.ts`, `fdx.ts`), лежат в `agno/tests/fixtures/import/` и импортируются тестом с проверкой типов абзацев.
- [ClamAV тяжёлый и долго стартует (загрузка баз)] → healthcheck и `depends_on: service_healthy`; в `dev.sh test` ClamAV поднимается только для тестов файлов; память — в README.
- [Файл 20 МБ в памяти процесса] → допустимо при одном API и лимите 5 файлов в сообщении; поток ClamAV идёт кусками.
- [Инструменты соавтора увеличивают число вызовов модели] → инструменты читают компактно (сцена по `uid`, профиль без пустых полей).
- [Change `agent-prompts-as-skills` не заархивирован] → дельта `api/agents` построена на его версии требования «Соавтор»; перед `/opsx:apply` его нужно заархивировать (первая задача).

## Migration Plan

1. Миграции `0003_projects_documents`, `0004_screenplay_texts_review`, `0005_files` — только вперёд, на пустых таблицах; данных для переноса нет (истории живут во `fixtures`).
2. `.env`: новые обязательные `CLAMAV_HOST`, `CLAMAV_PORT` в `example.env`; без них API не стартует, ошибка называет переменную.
3. Production: `docker compose -f compose.yaml -f compose.prod.yaml up -d --build` поднимет `clamav`; проверка — загрузка EICAR (`422`) и TXT (`201`) запросом с токеном, запись в `tmp/VERIFY.md`.
4. Откат: схема только вперёд; при сбое — откат образа API, таблицы остаются пустыми и не мешают старому коду.
