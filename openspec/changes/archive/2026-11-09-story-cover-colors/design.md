# Design

## Context

- Обложка сейчас — флаг `Project.cover` модели экранов. Ядро его не хранит, `apiProvider.readProject` всегда пишет `false`, а `fixturesProvider` берёт его из `demo.json`. Стили `.book.art` и `.book-mini.art` в `web/src/screens/workspace.css` рисуют синий градиент из `--primary`, но включаются только флагом.
- `authorled.projects` (`agno/core/tables.py`) хранит `title`, `description`, `format` и времена. `core/projects.py` создаёт историю одним `insert`; импорт (`core/imports.py`) и загрузчик демо (`agno/demo/load.py`) зовут тот же `create_project`. `update_project` принимает только `title` и `description` и всегда ставит `updated_at = now()`.
- Маршрут `POST /api/v1/projects` уже отвечает `422` на неизвестное поле, так что `cover_color` при создании отклоняется без новой проверки.
- Тесты ядра идут в одной транзакции на тест (`agno/tests/conftest.py`), и загрузчик демо создаёт все истории в одной транзакции. У всех историй, созданных в одной транзакции, `now()` одинаковое.
- Полка сортируется по `updated_at` (`useProjects`); `fixturesProvider.update` для историй всегда ставит `updatedAt = now()`.
- В дизайн-системе уже есть шкалы `blue`, `teal`, `amber`, `crimson`, `plum`, `neutral` с вариантами для трёх тем; `check-contrast.ts` проверяет пары токенов по темам; экраны используют только семантические токены (`check_web_tokens.sh`).
- В меню карточки полки (`ShelfScreen`) есть «Переименовать» и «Удалить в корзину»; `dropdown-menu` из shadcn уже экспортирует `DropdownMenuSub` и `DropdownMenuRadioGroup`.

## Goals / Non-Goals

**Goals:**
- Палитра — одна точка правды в ядре (список значений и проверка), а клиент знает тот же список как тип и падает на незнакомом значении.
- Выбор цвета новой истории детерминирован и не зависит от того, в одной ли транзакции созданы истории.
- Смена цвета — то же изменение истории `PATCH`, без отдельного маршрута.

**Non-Goals:**
- Блокировка от одновременного создания двух историй одним автором: в редком случае они получат один цвет, и автор его поменяет.
- Перенос `.book`-стилей в дизайн-систему как компонента: они остаются поверхностями рабочего места в `workspace.css`.

## Decisions

1. **Колонка `cover_color text NOT NULL` с `CHECK (cover_color IN (...))`, без `server_default`.** Ядро всегда передаёт цвет при вставке, поэтому значение по умолчанию в базе скрывало бы ошибку кода. Альтернатива — `enum` PostgreSQL: менять его дольше, чем `CHECK`, а выигрыша нет; в схеме уже приняты `CHECK` (`format_known`).

2. **Палитра — кортеж `COVER_COLORS` в `core/tables.py` в порядке круга, рядом с ограничением, которое из него строится.** `core/projects.py` берёт его оттуда для проверки значения и выбора следующего цвета (в `projects.py` он дал бы циклический импорт: `projects.py` сам импортирует таблицы). Миграция держит свою копию списка, потому что миграции не импортируют код ядра, который потом может измениться.

3. **Следующий цвет считает ядро из последней созданной истории автора.** `create_project` читает `cover_color` истории автора с наибольшим `created_at` (равных времён у историй автора не бывает, см. решение 4), включая корзину; нет истории — `blue`; иначе следующий в `COVER_COLORS` по кругу. Альтернатива — номер по числу историй автора: он сбивается после «Удалить навсегда» и не учитывает цвет, который автор выбрал сам. Альтернатива — случайный цвет: соседние карточки могут совпасть, тесты недетерминированы. Логика на фронтенде запрещена (07-anti-patterns, п. 10).

4. **`created_at = clock_timestamp()` при вставке истории.** Иначе истории одной транзакции получают одинаковое `now()`, и «последняя созданная» не определена (тесты и загрузчик демо). Это остаётся временем создания, только с точностью до вставки, а не до начала транзакции. `server_default` колонки не меняется.

5. **`update_project` принимает `cover_color`; `updated_at` меняется, только если в изменениях есть `title` или `description`.** Цвет — оформление, а не правка истории, и полка не должна переставлять карточку. Альтернатива — отдельный маршрут `PUT /projects/{id}/cover`: лишняя поверхность API для одного поля.

6. **Ответы маршрутов получают поле из `ProjectOut`.** `Project` (dataclass ядра) получает `cover_color`, `ProjectOut` — тоже; `ListedProjectOut` и `CreatedProject` наследуют его. OpenAPI меняется само.

7. **Демо-цвета задаются явно.** `demo.json` вместо `cover` получает `coverColor` у каждой истории («Тихая вода» `blue`, «Последний паром» `teal`, «Без названия» `amber`). Загрузчик сразу после `create_project` вызывает `update_project(..., {"cover_color": ...})` — до того, как история уходит в корзину. Так источник `fixtures` и база показывают одно и то же, и загрузчик не зависит от круга.

8. **Токены: по три на цвет и тему** — `--cover-<c>-from`, `--cover-<c>-to`, `--cover-<c>-foreground`, где `<c>` из `blue`, `teal`, `amber`, `crimson`, `plum`, `graphite`. Они ссылаются на шаги шкал (слой 2 → слой 1). В светлых темах `from` — средний шаг шкалы, `to` — глубокий; в тёмной теме оба шага приглушённее, чтобы обложки не спорили с бумагой. `check-contrast.ts` получает пары `foreground`/`from` и `foreground`/`to` для каждого цвета (TEXT, 4,5:1). Альтернатива — `color-mix` из `--primary`, как сейчас: такой цвет нельзя проверить контрастом, и он один на все шесть.

9. **Стили обложки по атрибуту `data-cover`.** `.book` и `.book-mini` берут градиент из переменных `--cover-from`, `--cover-to`, `--cover-fg`, а правила `.book[data-cover="teal"]` (и для `.book-mini`) задают их из токенов цвета. Дуги остаются как у `.book.art`, их цвет — от `--cover-fg`. Классы `.art` уходят. Полка и навигатор ставят `data-cover={project.coverColor}`.

10. **Клиент: тип `CoverColor` и список `COVER_COLORS` с подписями в `model.ts`.** `readProject` проверяет значение по списку и бросает ошибку на незнакомом — экран полки показывает свою ошибку загрузки (`DataErrorScreen`). `apiProvider.update` переводит `coverColor` в `cover_color`. `fixturesProvider` назначает новой истории следующий цвет после последней в своём списке и не трогает `updatedAt`, если меняется только `coverColor`.

11. **Меню карточки: подменю «Цвет обложки» с `DropdownMenuRadioGroup`.** Шесть пунктов с кружком цвета (тот же `data-cover`) и подписью; значение — текущий цвет. Выбор зовёт `setCoverColor(id, color)` из `useStoryActions` через `useUpdate`, как переименование; Refine после ответа обновляет список и историю, поэтому навигатор меняется без своего кода. При отказе ядра запрос падает, данные не обновляются, обложка остаётся прежней — так же, как сейчас у «Удалить в корзину».

12. **Витрина** получает раздел «Обложки» с шестью обложками на поверхности полки.

## Risks / Trade-offs

- [Тёмная тема: яркие градиенты рядом со сценарием] → тёмные варианты берутся с приглушённых шагов шкал; проверка глазами в трёх темах — отдельная задача, не только контраст.
- [Графит сливается с панелью] → его `from` в светлых темах заметно темнее `--panel`, в тёмной — светлее; проверяется на витрине и на полке.
- [Одновременное создание двух историй одним автором даёт один цвет] → принимаем: редкий случай, цвет меняется в меню.
- [`clock_timestamp()` меняет `created_at` у историй из одной транзакции на доли секунды] → поле нигде не сравнивается с другими временами транзакции; список сортируется по `updated_at`.
- [Пример неизвестного поля в спеке использует `color`] → новое поле называется `cover_color`, сценарий остаётся верным.

## Migration Plan

- Миграция `0014_story_cover_colors` (до слияния с writing-goals — `0013`): добавить `cover_color` без `NOT NULL`; заполнить по каждому `owner_id` по кругу палитры в порядке `created_at, id` (`row_number() over (partition by owner_id order by created_at, id)`); поставить `NOT NULL` и `CHECK`. `downgrade` — `NotImplementedError`, как у остальных миграций схемы.
- Порядок выкладки обычный: `agentos-migrate` применяет миграцию до старта API; фронтенд выходит в том же релизе. Старый фронтенд с новым API работает (лишнее поле игнорируется), новый со старым API падает на отсутствии поля — релиз выкатывает их вместе.
- Откат: только новой миграцией вперёд (удалить колонку) вместе с откатом фронтенда.
