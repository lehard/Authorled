# Proposal

## Why

После релиза v0.1.2 владелец создал на сервере первую историю и увидел ошибку «Сервер вернул ревизию в неизвестном виде: ETag "2-gzip"», хотя история создалась. Обратный прокси сжимает ответы и дописывает `-gzip` к `ETag`, а ревизия истории передаётся в этом заголовке. Сжимаются ответы примерно от 512 байт, поэтому ломаются все запросы с ревизией и большим ответом: тестеры не смогут работать с историями. Интент: `business-intents/api-without-compression.md`.

## What Changes

- Обратный прокси сжимает только файлы фронтенда.
- Ответы API на `/os/*` и запросы к Authentik на домене продукта проходят без сжатия, поэтому `ETag` доходит до фронтенда в том виде, в каком его отправил API.
- В спеке `runtime` появляется требование: прокси не меняет `ETag` ответов API.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `runtime`: новое требование о том, что обратный прокси передаёт ответы API без сжатия и без изменения `ETag`.

## Scope

- `deploy/Caddyfile`, блок домена `coauthor.glavai.ru`.
- Проверка на сервере полного пути работы с историей и заметкой.

## Non-goals

- Формат ревизии, `ETag` и `If-Match` в API.
- `web/src/data/apiClient.ts`: неизвестная ревизия остаётся явной ошибкой, фронтенд не учится отрезать суффиксы.
- Сжатие ответов API другим способом.
- Защита от повторного создания истории после ошибки.
- Домен `auth.coauthor.glavai.ru`: там сжатия нет.
- Автоматическая проверка полного пути на сервере.

## Impact

- Код приложения и схема базы не меняются.
- Большие ответы API передаются без сжатия.
- `deploy/deploy.sh` применяет новый файл при релизе: проверяет его и перезагружает Caddy.
- Change `deploy-on-release` ещё не заархивирован и добавляет требование «Обратный прокси». Этот change его не правит, а добавляет отдельное требование, поэтому порядок архивации не важен.
- Шаг 4.3 change `first-sign-in-account` (удаление временного пользователя) выполняется после проверки на сервере.
