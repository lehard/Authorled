# Design: экраны истории на данных ядра

## Context

Мотивация — `proposal.md`, требования — `specs/`. Что есть:

- Экраны меняют данные только через Refine: `useList`/`useOne` в `web/src/data/hooks.ts` и `useCreate`/`useUpdate`/`useDelete` в действиях (`screens/shelf/storyActions.ts`, `screens/project/entityActions.ts`, `draftActions.ts`, `docs/useEditorComments.tsx`, `docs/useEditorSuggestions.tsx`, `screens/shared/useAutosave.ts`). Единственный провайдер — `fixturesProvider` (ресурсы `projects`, `scripts` с `id` = id истории, `characters`, `locations`, `worlds`, `comments`, `suggestions`, `drafts`; корзина — поле `deletedAt`; фильтры `eq`/`null`/`nnull`, списки целиком).
- Записи фронтенда (`web/src/data/model.ts`) по форме отличаются от ответов ядра: `Project.desc`, `Entity.one`/`long`/`ext`, сценарий с текстом в одной записи, комментарий — ветка с массивом `replies` и `email` для «своих».
- Клиент `/api/v1/me` (`account/meApi.ts`) ходит на `/os/` фронтенда с `Authorization` из `activeUser()` и читает `application/problem+json` — образец для клиента данных.
- Редактор: `uid` у заголовка сцены нет (`SceneParams`: `alt`, `day`, `color`, `tags`); операции над сценами вне редактора — JSON-функции `editor/scenes.ts`; импорт — `importFile` в `editor/index.ts` через `importers/fountain.ts` и `importers/fdx.ts`; `scripts/check-editor.ts` проверяет круг Fountain.
- Чат: своё поле ввода (`textarea`, `agent.addMessage`), контекст через `useAgentContext`, беседа — сессия Agno `<projectId>:<uuid>`.
- Ядро (архив `story-data-backend`): ресурсы и ревизии из спеки `api/stories`; новая история из файла — multipart `POST /api/v1/projects`; импорт — `POST /projects/{id}/import` с `If-Match`; соавтор читает файл беседы инструментом по id.

## Goals / Non-Goals

**Goals:** экраны работают одинаково на `fixtures` и `api` через одни и те же ресурсы; ни одна правка не перезаписывает чужую молча; фронтенд не содержит правил ядра, кроме формата текста редактора.

**Non-Goals:** кэш правок без сети, оптимистичные правки поверх конфликта, своё хранилище фронтенда, изменения ядра.

## Decisions

### 1. Провайдер `api` переводит ресурсы экранов, экраны почти не меняются
`data/apiProvider.ts` реализует `DataProvider` над клиентом `data/apiClient.ts` (`fetch` на `/os/api/v1/…`, токен из `activeUser()`, ответ `problem+json` → `HttpError` со `statusCode` и `message` = `detail`). Перевод ресурсов:
- `projects`: список — `GET /projects?trash=` по фильтру `deletedAt`; `create` — `POST /projects`; `update` с `title`/`desc` — `PATCH`, с `deletedAt` — `trash`/`restore`; `deleteOne` — `DELETE`.
- `scripts` (`id` = id истории): `getOne` — дерево документов (сценарий) и `GET …/text`; `update` разбивает значения на поля документа (`PATCH /documents/{id}`) и текст (`PUT …/text`).
- `characters`/`locations`/`worlds`: из дерева по виду; `one` ↔ `summary`, `long` ↔ `fields.description`, `ext` ↔ поля профиля, `age`/`gender`/`overview` ↔ `fields`; корзина — `trash`/`restore`; `deleteOne` — `DELETE`.
- `drafts`: дерево (`kind=draft`) и текст; `create` — `POST /projects/{id}/drafts` (копию без пометок делает ядро); `locked` ↔ `fields.locked`.
- `comments`, `comment-replies`, `suggestions` — решения 4 и 5.
Неподдержанный ресурс, фильтр или сортировка — исключение с именем, как у `fixtures`. Альтернатива — переписать экраны под форму ядра: больше правок, а `fixtures` пришлось бы тоже переписать.

### 2. Ревизии живут в провайдере, а не в записях экранов
Провайдер запоминает ревизию документа и текста из каждого ответа (`GET`, `PATCH`, `PUT`, импорт) в карте «id документа → ревизия» и подставляет её в `If-Match`. Экраны ревизий не видят. Карта сбрасывается для документа при «Открыть свежую версию» (повторное чтение). Почему не поле в модели: автосохранение шлёт частичные значения и не держит запись целиком; ревизия в провайдере повторяет поведение ETag и не протекает в экраны.

### 3. Конфликт — отдельный статус автосохранения
`useAutosave` получает статус `{ conflict: правка }` на `HttpError` 409: таймер останавливается, накопленные значения сохраняются в статусе. Компонент статуса показывает «История изменилась в другой вкладке», «Открыть свежую версию» (инвалидирует запрос записи и сбрасывает статус; правка остаётся в буфере «Скопировать») и «Скопировать мою правку» (значения правки текстом в буфер обмена; для текста сценария — абзацы через `paragraphs()`). Альтернатива — слияние правок: для текста целиком без серверной истории невозможно надёжно.

### 4. Комментарии — по сообщениям, «своё» решает ядро
Модель: `CommentMessage.email` → `own: boolean` (в `fixtures` `own` = почта сообщения совпадает с почтой вошедшего, проставляет провайдер). Ресурсы: `comments` (создать ветку с первым сообщением, `resolved`, удалить ветку) и `comment-replies` (`create` с `meta.threadId`, `update`/`deleteOne` по id сообщения). `useEditorComments` переходит с правки массива `replies` на эти операции. Удаление первого сообщения удаляет ветку и в `fixtures`, как в ядре. Ветки в `api` читаются по документу сценария (`GET /documents/{id}/comments`), в модели остаётся `projectId`.

### 5. Предложения: якорь в модели, метку ставит экран текста
Модель `Suggestion` получает `sceneUid` и `quote`. `docs/useEditorSuggestions.tsx` после загрузки текста и каждого обновления списка находит открытые предложения без метки, ищет в сцене с `uid` первое вхождение цитаты в одном абзаце (`editor/anchors.ts`, чистая функция над документом) и одной транзакцией ставит метки найденным; транзакция идёт в историю отмены как обычная правка и сохраняется автосохранением. Ненайденные идут в список «Нет места в тексте» (кнопка предложений: открытые в тексте и отдельный раздел ненайденных с «Отклонить»). Чат по окончании хода соавтора (`agent.subscribe`, событие конца хода) инвалидирует `suggestions`. В `fixtures` предложения уже с метками — путь тот же.

### 6. `uid` сцены — атрибут схемы, плагин и нормализация JSON
`SCENE_ATTRS.uid` (строка, по умолчанию пусто). Плагин `appendTransaction` выдаёт `crypto.randomUUID()` заголовкам без `uid` и повторам (вставка, разделение абзаца). `ensureSceneUids(doc)` в `editor/document.ts` делает то же для JSON и вызывается в `scenes.ts` (`addScene`, `moveScene`, `setSceneParams`, …) и при открытии документа без `uid` (данные примера). Экспортёры и печать атрибуты не пишут — проверяется в `check:editor`. Перестановка сцен переносит узлы с атрибутами, `uid` сохраняется сам.

### 7. Импорт и файлы — операции провайдера `custom`
Загрузка файла, импорт в историю и история из файла — `custom` провайдера (`useCustomMutation`): `upload` (multipart в `/projects/{id}/files`), `import` (`POST …/import` с ревизией текста из карты решения 2), `createFromFile` (multipart `POST /projects`). В `fixtures` `custom` отвечает ошибкой «недоступно с данными примера». Удаляются `editor/importers/` и `importFile`; ошибки разбора показывает экран из `detail` ядра. Диалог новой истории получает необязательное поле файла.

### 8. Файлы чата — своя полоса над полем, id в контексте AG-UI
Не используем вложения CopilotKit: они кладут файл частью сообщения (`document`), Agno передаёт его модели как `File`, а DeepSeek файлы не читает. Полоса вложений рядом с плашкой «Выделено» загружает файлы через `upload` (решение 7) с `session_id` беседы, показывает «проверяется», ошибку под полем и имя; отправка заблокирована, пока есть незавершённые загрузки. При отправке текст сообщения получает строку «Файлы: заметки.docx, …», а `useAgentContext` — запись «Файлы этого сообщения» с `id` и именем; соавтор читает их `read_chat_file`. Пустой текст с файлами допустим.

### 9. Образцы экспорта — общий источник для проверок
`scripts/check-editor.ts` строит документ со всеми 14 типами (тот же набор, что в `agno/tests/fixtures/import/all-types.*`), экспортирует Fountain и FDX и сравнивает с файлами образцов байт в байт; расхождение — ошибка с подсказкой команды пересоздания `npm run samples:export --prefix web`. Круг импорта в браузере уходит из `check:editor`, круг через ядро проверяют тесты `agno/tests/test_import.py` на этих образцах.

## Risks / Trade-offs

- [Два запроса на сценарий (дерево и текст) и дерево на каждый список сущностей] → Refine кэширует запросы; дерево одно на историю и переиспользуется всеми ресурсами через общий ключ запроса провайдера.
- [Метка предложения в тексте — правка автора без его действия] → так решено в интенте (якорь, метку ставит браузер); правка видна в истории отмены и отменяется ⌘Z, предложение тогда снова ставится при следующем открытии.
- [Строка «Файлы: …» видна в сообщении] → это и есть показ имён файлов по спеке; id в текст не попадают.
- [Расхождение формы данных при ошибке перевода] → провайдер проверяет обязательные поля ответов и падает с описанием, а не подставляет пустое.

## Migration Plan

1. `.env`: `VITE_DATA_SOURCE=api` для работы с ядром; `fixtures` для витрины.
2. Данные примера в ядро не переносятся; истории в `api` начинаются пустыми.
3. Откат — вернуть `VITE_DATA_SOURCE=fixtures`.
