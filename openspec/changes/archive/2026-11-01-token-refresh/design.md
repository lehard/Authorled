# Design

## Context

Мотивация — `proposal.md`, требования — `specs/`. Что есть сейчас:
- `web/src/auth/userManager.ts`: `UserManager` с `automaticSilentRenew: true`, токены в `sessionStorage` вкладки. `activeUser()` возвращает пользователя, а если токен истёк — сам вызывает `signinSilent()`.
- Кто зовёт `activeUser()`:
  - `authProvider.check` (через `RequireAuth`);
  - `LoginScreen` (проверка «уже вошли»);
  - `account/meApi.ts` (меню, `/settings`, identity Refine);
  - `screens/project/chat/api.ts` (`osFetch`).
- `oidc-client-ts` `3.5.0`:
  - `SilentRenewService` по событию «access token expiring» (таймер, за 60 с до истечения) вызывает `signinSilent()`;
  - если токен уже истёк при загрузке, таймер «expiring» отменяется, и библиотека не продлевает — это делает приложение;
  - одновременные `signinSilent()` библиотека не объединяет: каждый отправляет в `/application/o/token/` тот refresh token, что лежит в хранилище;
  - отказ сервера — `ErrorResponse` с полем `error` (`invalid_grant`), тайм-аут — `ErrorTimeout`, сеть — `TypeError` из `fetch`.
- Authentik `2026.8.5` (`providers/oauth2/views/token.py`): при `refresh_token_threshold = seconds=0` (по умолчанию, в `20-oidc.yaml` не задан) каждое продление выдаёт новый refresh token и отзывает старый; повторное использование — `invalid_grant` и событие `suspicious_request`.
- `RequireAuth` показывает «Не удалось проверить вход» на любую ошибку `check`, «Попробовать снова» — `refetch()`.

## Goals / Non-Goals

**Goals:**
- Один путь продления на вкладку, через который идут и таймер библиотеки, и запросы с истёкшим токеном.
- Отказ Authentik и сбой различаются по типу ошибки библиотеки, а не по тексту.
- Конец сессии сам приводит открытый экран на `/login`, даже если о нём узнал запрос меню или чата, а не проверка входа.

**Non-Goals:** см. `proposal.md`; дополнительно — без своего HTTP-клиента токенов: продление остаётся вызовом `signinSilent()` библиотеки.

## Decisions

### 1. Шлюз продления в `userManager.ts`
`renew()` хранит один `Promise` текущего продления на модуль (вкладку). Пока он не завершён, все вызовы получают его же; после завершения ссылка сбрасывается. `activeUser()`:
- нет пользователя → `null`;
- токен не истёк → пользователь;
- истёк → `renew()`.
- *Альтернатива — Web Locks между вкладками.* Вкладки держат разные копии токенов в `sessionStorage`, так что блокировка не спасает дублированную вкладку: её копия всё равно отозвана. Её восстанавливает решение 3.

### 2. Таймер библиотеки — через тот же шлюз
`automaticSilentRenew: false`. Вместо него `events.addAccessTokenExpiring(() => void renew()…)` — тот же таймер библиотеки за 60 с до истечения, но продление идёт через шлюз. Ошибку таймерного продления обрабатывает тот же разбор, что и решение 3.
- *Альтернатива — оставить `automaticSilentRenew` и только ждать его из приложения.* Библиотека не продлевает уже истёкший токен (загрузка после сна, `expiring` отменён), и её `signinSilent()` по таймеру всё равно может совпасть с нашим — именно эта гонка и случилась.
- Повтор при `ErrorTimeout` (у `SilentRenewService` — через 5 с) не переносим: тайм-аут — сбой (решение 3), и пользователь увидит причину при следующем запросе токена.

### 3. Разбор ошибки продления
В `renew()`:
- `ErrorResponse` с `error === "invalid_grant"` — конец сессии: `removeUser()` (токены вкладки удалены, библиотека поднимает `userUnloaded`), и `renew()` возвращает `null`;
- всё остальное (`ErrorResponse` с другим кодом, `ErrorTimeout`, сетевой `TypeError`) — сбой: ошибка пробрасывается как есть, токены не трогаем.

`null` из `activeUser()` уже означает «нет входа» для всех вызывающих: `check` → `authenticated: false` → `RequireAuth` открывает `/login?returnTo=…`, а `LoginScreen` идёт к `flow.start()` и при живой сессии Authentik берёт токены без формы.
- *Альтернатива — считать отказом любой `400`.* Слишком широко: `invalid_client` или `invalid_request` — ошибки конфигурации, их надо видеть, а не прятать за входом.

### 4. Конец сессии, о котором узнал не `check`
Если отказ получил запрос меню (`getMe`) или чата (`osFetch`), `RequireAuth` об этом не знает. Поэтому `RequireAuth` подписывается на `userManager().events.addUserUnloaded` и при событии делает `refetch()` проверки — та видит `null` и открывает `/login`.
- `getMe` и `osFetch` при `null` от `activeUser()` не показывают свой текст «Вход истёк»: они бросают ошибку, но экран уже уходит на `/login`. `identity` не повторяет запрос: `retry: false` уже стоит в `useGetIdentity`.
- Выход (`logout`) тоже вызывает `removeUser()` → `userUnloaded`; `refetch()` при этом безвреден: `logout` и так ведёт на `/login`.

### 5. Проверка без ожидания 10 минут
В Playwright истечение задаётся правкой `expires_at` пользователя в `sessionStorage` (ключ `oidc.user:<issuer>:<client>`) перед перезагрузкой — это то, что видит библиотека после сна вкладки. Дублированная вкладка — второй контекст со скопированным `sessionStorage`. Число обменов refresh token — по запросам к `/application/o/token/` в Playwright и по событиям `suspicious_request` в API событий Authentik (`/api/v3/events/events/?action=suspicious_request`) под админом.

## Risks / Trade-offs

- [Safari: таймеры фоновой вкладки] → решение 1 не зависит от таймера: истёкший токен продлевается при первом запросе после пробуждения. Автоматикой проверяется Chromium; Safari — ручная проверка владельцем (задача в tasks).
- [Две вкладки одного входа без дублирования] → у них разные цепочки токенов (каждая вошла сама), гонки нет.
- [Отказ продления в середине набора текста] → экран уходит на `/login`. Несохранённые правки зависят от автосохранения экрана; при живой сессии Authentik возврат мгновенный. Отдельно не решаем.

## Migration Plan

Только фронтенд: выкатывается сборкой `web/`. Вкладки, уже застрявшие с отозванным токеном, после обновления страницы попадут на `/login` и войдут без формы при живой сессии Authentik.
