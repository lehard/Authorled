# Design

## Context

Зачем это делается — proposal.md, раздел Why. Что есть сейчас:

- **Чат** (`web/src/screens/project/chat/CoauthorChat.tsx`). Пустая беседа показывает три вопроса из константы `SUGGESTIONS`, клик вызывает `send(text)`. У ответа есть только «Скопировать». Контекст (история, открытый документ, выделение) уходит в AG-UI через `useAgentContext` и `coauthorContext(data, selection)`, а не в текст сообщения.
- **Выделение.** `useSelectionIn` ловит `selectionchange` внутри `[data-chat-source]`, обрезает текст до 2000 символов и держит последнее непустое выделение, пока автор не нажмёт «Убрать». `ProjectScreen` передаёт его в `CoauthorChat`.
- **Меню выделения** — DOM-плагин ProseMirror (`web/src/editor/plugins/bubbleMenu.ts`): кнопки цвета и «Комментировать» через опцию редактора `onCommentRequest`. Компоненты React в нём не рендерятся.
- **Открыть чат из документа.** `ProjectContext.openChat` уже есть: им пользуется «Обсудить в чате» у предложения.
- **Запуски и беседы.** Беседа — сессия Agno `<история>:<драфт>:<uuid>`. Роутер AG-UI в Agno 3.1.10 берёт `run_id` из запроса клиента или создаёт его и отдаёт в событии `RUN_STARTED`. `GET /sessions/{id}/runs` возвращает `run_id` у каждого запуска, но `loadConversation` его сейчас не читает и строит id сообщений по номеру запуска.
- **Журнал расхода.** `record_usage` (post-hook соавтора) пишет строку `usage_records` с `run_id`, `session_id`, `agent_id` и `user_id` до конца запуска. Это единственная запись ядра, которая связывает запуск, беседу и пользователя.
- **Механизма оценок в Agno 3.1.10 нет**: в `agno/os` не нашлось ни маршрутов, ни таблиц для них, кроме интерфейса Slack.
- **Отчёты администратора** — `python -m admin <команда>` через `./scripts/usage.sh`, по образцу `beta-requests`.

## Goals / Non-Goals

**Goals:**
- Один список проверок для чата, кнопки «Проверки» и меню выделения.
- Проверка отправляется так же, как набранный вопрос: тот же `send`, тот же контекст и выделение. Отдельного пути к агенту нет.
- Оценка привязана к запуску Agno (`run_id`) и проверяется по журналу расхода в ядре, без чтения таблиц Agno из ядра.

**Non-Goals:**
- Менять способ передачи выделения в контекст и лимит в 2000 символов.
- Хранить проверки на сервере или настраивать их без релиза.
- Новая таблица беседы в ядре.

## Decisions

### 1. Проверки — модуль данных фронтенда
`web/src/screens/project/chat/checks.ts`: массив `{ id, label, request }` в фиксированном порядке. Его используют пустая беседа, кнопка «Проверки» (`DropdownMenu` shadcn у поля ввода) и меню выделения. Формулировки `request` из интента, голосом автора: например, «Где здесь вода? Назови одно–три места, которые можно сократить без потери смысла, и спроси меня о них.» Те же формулировки копируются в `quick_prompts` соавтора в `agno/app/config.yaml` для интерфейса AgentOS. Это копия, а не общий источник.
- *Альтернатива:* отдавать проверки с сервера (`GET /api/v1/...`). Отвергнута: лишний маршрут и запрос ради статичного списка. Менять формулировки без релиза владелец не просил.

### 2. Отправка проверки: «просьба в чат» через ProjectContext
В `ProjectContext` появляется `askCoauthor(text: string)`. `ProjectScreen` хранит ожидающую просьбу `{ id, text }` в состоянии, открывает чат (`foldChat(false)` или шторку) и передаёт просьбу в `CoauthorChat` пропом. `CoauthorChat` в эффекте вызывает `send(text)` и сообщает, что просьба принята; `id` защищает от повторной отправки при перерисовке. Если соавтор отвечает, просьба не создаётся: пункты меню выключены (`disabled`), а `askCoauthor` в это время бросает ошибку, потому что UI не должен был её вызвать.
- *Альтернатива:* событие DOM или глобальная шина. Отвергнута: `ProjectContext` уже связывает документ и чат (`openChat`).

### 3. «Соавтор» в меню выделения — кнопка DOM и меню React
Опция редактора `onCoauthorRequest?: (anchor: DOMRect) => void` по образцу `onCommentRequest` добавляет в `bubbleMenu.ts` кнопку «Соавтор» (иконка Sparkles и подпись, на узком экране только иконка). По `mousedown` с `preventDefault` плагин передаёт прямоугольник кнопки. Документ (`TextDoc`, поэпизодник) показывает `DropdownMenu` shadcn с виртуальной привязкой к этому прямоугольнику. Пункты — проверки из `checks.ts`, клик вызывает `askCoauthor(request)`. Выделение к этому моменту уже в состоянии `useSelectionIn`: `mousedown` с `preventDefault` не снимает выделение, а свёрнутое выделение хук игнорирует.
- *Альтернатива:* подменю целиком из DOM внутри плагина. Отвергнута: ручная доступность, клавиатура и токены дизайн-системы. У shadcn всё это уже есть.
- В запертом драфте кнопка остаётся: проверка ничего не меняет, а отказ `suggest_edit` в запертом драфте уже есть в ядре.

### 4. Сообщение проверки — текст просьбы, выделение в контексте
Сообщение автора — текст `request`. Выделенный фрагмент уходит в контекст AG-UI, как у набранного вопроса, и виден автору плашкой «Выделено» над полем до отправки. Решение сужает приёмку интента «в сообщении видны проверка и фрагмент»: фрагмент не дублируется в текст сообщения, иначе беседа раздувается выделениями до 2000 символов, а соавтор получает его дважды.

### 5. `run_id` у сообщений соавтора
- **Живой ответ.** В `runOrThrow` подписка ловит `onRunStartedEvent` и запоминает `event.runId` первого `RUN_STARTED` хода. Это id запуска Agno, и он же записан в журнал расхода. Ответ хода (его последнее сообщение `assistant` с текстом) получает этот `run_id` в карте `messageId → runId` в состоянии чата.
- **История.** `loadConversation` читает `run_id` из `/sessions/{id}/runs` и отдаёт его у сообщения соавтора.
- Кнопки оценки стоят только у последнего сообщения соавтора каждого запуска. У сообщения без `run_id` кнопок нет: молча оценку не ставим, но такого состояния быть не должно, и в консоль идёт ошибка.
- **Запуск с паузой подтверждения.** Agno продолжает тот же запуск (`find_resume_target_run_id`), и журнал пишет его `run_id`. А `RUN_STARTED` продолжения приходит с новым id клиента. Проверено 2026-11-09: в журнале `6162b4f2`, в `RUN_STARTED` продолжения `a98fd95e`, `PUT` оценки по нему отвечал 404. Поэтому ответ хода берёт `runId` первого `RUN_STARTED` хода. Если ход прервался несколько раз, все продолжения относятся к одному запуску. История (`/sessions/{id}/runs`) уже отдаёт id исходного запуска.

### 6. Хранение оценки — таблица ядра, снятие — пустое значение
`authorled.coauthor_feedback (id, user_id → users RESTRICT, run_id, session_id, value NULL | 'useful' | 'not_useful', created_at, updated_at)`, уникальность `(user_id, run_id)`. Миграция `0012_coauthor_feedback`, описание в `core/tables.py`.
- «Снять оценку» записывает `value = NULL`, а не удаляет строку: удаление записей ядра у нас мягкое (`04-engineering-standards.md`). Для отчёта при этом остаётся время последнего изменения.
- `session_id` копируется из журнала расхода при первой оценке, клиент его не присылает: беседа запуска — факт сервера.
- *Альтернатива:* хранить в Agno (метаданные запуска или сессии). Отвергнута: механизма нет, а данные продукта не держим в таблицах Agno (`07-anti-patterns.md`, п. 8).

### 7. Доступ — по журналу расхода и доступу к истории
`core/feedback.py`:
- `set_feedback(connection, user_id, run_id, value)` находит строку `usage_records` с `run_id`, `user_id` и `agent_id = 'coauthor'` (строк может быть несколько, по одной на модель; `session_id` у них один). Если строки нет — `NotFound("Ответ соавтора не найден.")`. Иначе делает upsert по `(user_id, run_id)` и возвращает запись.
- `clear_feedback` — то же с `NULL`, без ошибки, если оценки нет. Если запуска нет в журнале — `NotFound`.
- `session_feedback(connection, user_id, session_id)` возвращает строки с непустым `value`.

Маршруты `agno/app/api/feedback.py` (`PUT`, `DELETE /api/v1/coauthor-feedback/{run_id}`, `GET /api/v1/coauthor-feedback?session_id=`) берут вызывающего как другие маршруты (`body.py`: `caller_id`). Проект берётся из префикса `session_id` (из журнала или из запроса) и проверяется через `require_project` из `body.py` (поверх `can_access_project`). Нет доступа — тот же `404`, что и для чужого запуска, чтобы не выдавать, существует ли запуск. Неверная форма `session_id` в `GET` — `422`. Ошибки — `Problem` / `application/problem+json`. Маршруты подключаются в `attach_api` перед MCP (ADR-002).

### 8. Отчёт `coauthor-feedback`
Функция ядра `feedback_report(connection, since, limit=20)` возвращает счёт `useful` и `not_useful` с `updated_at >= since` и непустым значением, а также последние `not_useful` с почтой пользователя (join `users`), `session_id`, `run_id` и временем. `admin/__main__.py` печатает таблицу через `_print_table`, а если оценок нет — «Оценок нет.». `usage.sh` пропускает команду `coauthor-feedback` без аргументов. Окно — 30 дней от текущего UTC.

### 9. Промпт и эвалы
В `agno/skills/coauthor/SKILL.md` появляется раздел «Проверки наставника» с правилами из спеки `api/agents` и перечнем восьми проверок, чтобы соавтор узнавал их по формулировке. Эвалы — в замере соавтора `evals.coauthor`, а не в `agno/evals/cases.py`: там соавтор идёт без пользователя, и проверка лимита отказывает запуску (`input_check_error`, прогон 2026-11-09, модель не вызывалась). Восемь случаев лежат в своей части `checks` набора `demo` — `agno/evals/coauthor/cases/demo-checks.toml`, запуск `--part checks`. Части `work` и `holdout` не меняются: по ним меряют `coauthor-answer-rules` и `coauthor-tool-contracts`, и их отчёты остаются сравнимыми. Правило «все 12 доменов и все разделы» к части `checks` не относится.

Случай получает необязательное поле `open = { scene = N }`: открыт текст сценария, выделена сцена с этим номером. Номер сверяется с `web/src/data/demo.json`, как другие ссылки набора. `chat_context` собирает контекст как `docContext.ts`: «Открыт документ: Текст сценария.», абзацы драфта из ядра с метками элементов (до 20 000 символов), затем «Автор выделил фрагмент:» и абзацы сцены.

Восемь случаев: `message` — формулировка из `checks.ts` слово в слово, `place = "tihaya-voda"`, `open = { scene = 6 }` (сцена `water-6`, ночная кухня), `section = "single"`, `expect = ["wide-review"]`, `action = "none"`. Поле `open` добавляет судье строку ожидания: одно–три места с точной цитатой из выделенной сцены, объяснение, вопрос автору, нет переписанной сцены целиком. У «Противоречий» ещё: другие документы соавтор читает инструментами и не выдумывает их содержание. При `action = "none"` предложение правки засчитывается как лишнее действие — это строже спеки `api/agents`, где короткая правка предложением допустима. Так решено осознанно: проверка — разбор, а правку предложением проверяет живой прогон в задаче 6.3. Отчёт ложится в `tmp/coauthor-eval/`, итог записывается в `tmp/VERIFY.md`.

## Risks / Trade-offs

- [Соавтор всё равно переписывает фрагмент] → правила в промпте, восемь эвалов, разбор ответов с «Не то» через отчёт.
- [`run_id` продолжения после паузы не совпадает с журналом] → подтверждено 2026-11-09. Берётся первый `RUN_STARTED` хода, задача 5.2 проверяет это вживую.
- [Оценку нажали до записи журнала] → журнал пишет post-hook до конца запуска, а кнопки появляются только у законченного ответа. Если журнал отказал, запуск уже завершён `RUN_ERROR`, и законченного ответа нет.
- [Меню выделения на 375 px] → на узком экране «Соавтор» только иконкой; проверка в браузере на 375 px.
- [Слияние с `coauthor-tool-contracts`] → он тоже меняет `SKILL.md` и `api/agents`. Наши правки — новый раздел промпта и ADDED-требования, текст его требований не трогаем. При apply сначала прочитать актуальный `SKILL.md`.
- [Копия формулировок в `config.yaml`] → две копии могут разойтись. Это принято: `config.yaml` нужен только интерфейсу AgentOS для разработки.

## Migration Plan

- Миграция `0012_coauthor_feedback` только добавляет таблицу; шаг `agentos-migrate` применяет её до API, как остальные. Данные не переносятся.
- Откат — релизом предыдущей версии. Таблица остаётся и не мешает: миграции только вперёд.
- После выкладки — `./scripts/usage.sh prod coauthor-feedback` печатает «Оценок нет.» и завершается кодом `0`.
