# Design

## Context

Причины и объём — в `proposal.md`, требования — в `specs/`. Решение об устройстве — ADR-001 и `03-architecture.md` (обновлены 2026-10-26): Authentik — модуль репозитория, отдельные процессы, граница OIDC/JWT; бизнес-интент — `business-intents/authentik-identity-and-isolation.md`.

Что есть сейчас (проверено по коду и Agno 3.1.10):
- `app/main.py`: `AgentOS(..., user_isolation=True, user_directory=True, authorization=runtime_env != "dev")`. В `dev` авторизация выключена.
- Agno проверяет JWT своим middleware: ключи из статического PEM-ключа или файла JWKS (загрузки по URL нет); приложение принимает только файл `JWT_JWKS_FILE`, так как ключи Authentik публикуются в формате JWKS, `iss` проверяется, если задан `issuer`; `aud` проверяется по `audience`; `sub` попадает в `request.state.user_id`, scopes — в `request.state`. Объект `Authorization(jwks_file, issuer, audience, verify_audience, roles_claim, ...)` — актуальный способ настройки; `authorization_config` помечен устаревшим.
- Agno имеет собственные `/users*` (каталог пользователей, `disabled` как «выключатель» даже при действительном токене) и `/service-accounts` (токены `agno_pat_*` в БД AgentOS).
- `agentos-db` — `agnohq/pgvector:18` с загрузочным пользователем `ai` (суперпользователь), Agno пишет в схему `ai`.
- `scripts/mcp_check.sh` уже принимает `MCP_CHECK_TOKEN`; в `compose.yaml` нет обратного прокси, в `compose.prod.yaml` порты привязаны к `127.0.0.1`.

## Goals / Non-Goals

**Goals:**
- Модуль `auth` с проверяемыми границами; Agno остаётся владельцем проверки токенов и изоляции, модуль только настраивает и оборачивает.
- Воспроизводимый запуск Authentik «с нуля» (blueprints, схема, роль, ключи) без ручных шагов.
- Одинаковый путь авторизации в `dev` и `prd`.

**Non-Goals:**
- Ролевая модель проекта и таблицы членства (ядро); заменой или миграцией `/users*` и `/service-accounts` Agno не занимаемся.
- Обратный прокси и TLS как часть compose (см. D9).
- Высокая доступность и резервное копирование Authentik сверх общего бэкапа БД.

## Decisions

**D1. Модуль — два каталога и одно проверяемое правило.** Деплой-часть `modules/auth/` (compose-фрагмент не нужен как отдельный файл: сервисы объявляются в `compose.yaml`, их конфигурация и файлы лежат в `modules/auth/`), кодовая часть `app/auth/`. Правило границ проверяется скриптом `scripts/check_auth_boundary.sh` (поиск `jwt`, `authentik`, чтения claims вне `app/auth/`), который вызывает `validate.sh` и тем самым CI. *Альтернатива:* только договорённость в документации — отвергнута, правило без проверки не работает.

**D2. Authentik — три контейнера compose и закреплённая версия.** `authentik-server` и `authentik-worker` из одного образа `ghcr.io/goauthentik/server:<версия>`, команды `server` и `worker`; blueprints монтируются из `modules/auth/blueprints` в каталог пользовательских blueprints образа. Тег образа выбирается при apply из официальных релизов, проверяется на совместимость с PostgreSQL 18 и фиксируется в `compose.yaml` (тег `latest` запрещён). Первый администратор создаётся переменными начальной настройки Authentik (проверить имена на выбранной версии). Порты — `127.0.0.1`. *Альтернатива:* Helm/Kubernetes — вне модели деплоя проекта (Docker-хост).

**D3. Схема и роль создаёт `authentik-db-init`.** Одноразовый контейнер `postgres` выполняет идемпотентный SQL под загрузочным пользователем `ai`: создаёт роль Authentik с паролем из окружения, схему `authentik` (владелец — эта роль), задаёт ролевой `search_path = authentik`; прав на схему `ai` у роли нет по умолчанию. *Проверено на Authentik 2026.8.5 / PostgreSQL 18:* помимо схемы роли нужны `CREATE` на базу (Authentik создаёт пустую схему `template`; `CREATE SCHEMA IF NOT EXISTS` проверяет это право даже для существующей схемы) и `CREATE` на схему `public` (функции django-pgtrigger); без любого из них сервер не стартует. Таблицы остаются только в `authentik` (230 штук), в `public` и `template` таблиц нет. Суперпользователь не нужен. Запускается при каждом `up`, поэтому работает и на существующем томе, где `docker-entrypoint-initdb.d` не выполняется. `authentik-server` и `authentik-worker` ждут его успешного завершения. *Альтернатива:* скрипт в `docker-entrypoint-initdb.d` — не срабатывает на уже созданной базе; отвергнута.

**D4. Проверка токена — штатный `Authorization(...)` Agno, собираемый в `app/auth/`.** `app/auth` экспортирует функцию построения объекта `Authorization` с `jwks_file` из `JWT_JWKS_FILE`, `issuer` (адрес провайдера Authentik), `audience` (Client ID приложения), `verify_audience=True`, алгоритм RS256; `app/main.py` передаёт результат в `AgentOS(authorization=...)` без условия по `RUNTIME_ENV`. Все параметры читаются из обязательных переменных окружения; отсутствие любой — `RuntimeError` с именем переменной, без значений по умолчанию. *Альтернативы:* `authorization=True` с переменными `JWT_*` (устарело на пине, нет `issuer`); собственный middleware (запрещён: Agno владеет авторизацией).

**D5. Группы → права через `roles_claim="groups"` (проверено на пине).** `Authorization(roles_claim="groups")` читает роль из claim `groups`, который Authentik выдаёт в токене; `app/auth/` определяет роли `screenwriters`, `editors`, `admins` с набором scopes и `admin_scope` для `admins`. Так не нужен property mapping scopes в Authentik. Ограничение: включает управляемые роли Agno (таблицы в БД Agno, маршрут `/authz`) — принимаем, это штатный механизм пина. **Проверено (задача 1.2):** профиль-scope Authentik кладёт `groups` в токен; Agno по `roles_claim` определяет роль, возвращает `401` без токена, с подделанной подписью или чужим издателем, `403` без нужного scope, `200` при нём. Middleware кладёт в `request.state` `user_id` (= `sub`), `authenticated` и весь словарь `claims`; scopes роли в состояние не попадают, поэтому `Principal.scopes` модуль считает сам из той же таблицы `GROUP_SCOPES`. Код владеет ролями: `set_role_scopes` при каждом запуске заменяет сохранённое (штатный `define_role` не перезаписывает существующие роли), для этого `Authorization` получает общую БД. Таблицы ролей (`ai.agno_authz_*`) создаются в схеме `ai`; маршрут `/authz` с `roles_claim` не монтируется. Права групп консервативны: авторы получают только `config`, `sessions` и `memories` (по собственным данным), права запуска агентов не выдаются, пока нет продуктовых агентов (иначе автор через OS Manager или `claude-engineer` получил бы доступ к серверу); `plugins` — `config:read`, `sessions:read`; `admins` — `agent_os:admin`. Различие прав `editors` и `screenwriters` задаётся с ядром.

**D6. `Principal` строится из состояния запроса Agno.** `current_principal` читает `user_id`, группы и scopes из `request.state`, куда их кладёт middleware Agno после проверки токена; модуль не разбирает JWT повторно. Нет проверенного `user_id` → `401`, значения по умолчанию не подставляются. Чтение `request.state` — только внутри `app/auth/` (правило D1).

**D7. Интерфейс доступа к проекту — подключаемый источник.** `app/auth/` объявляет узкий интерфейс «источник ролей проекта» и функцию `can_access_project(principal, project_id)`. Пока источник не зарегистрирован ядром, вызов поднимает `ProjectAccessNotConfigured`; решение «разрешено» не выдаётся никогда. Хранения и ролей в этом change нет.

**D8. Ключи проверки — разовый контейнер `authentik-jwks-export`.** После `healthy` сервера контейнер (минимальный образ с `curl`) запрашивает открытые ключи провайдера (`/application/o/<slug>/jwks/`) и атомарно записывает файл в `modules/auth/jwks/jwks.json` (каталог в `.gitignore`). Провайдер создаётся blueprints уже после `healthy` сервера (первый запуск показал `404`), поэтому скрипт ждёт ключи до `AUTH_JWKS_WAIT_SECONDS` (180 с в compose) и затем завершается ненулевым кодом; пустой файл не пишется. Это ограниченное ожидание готовности, а не запасной режим. `agentos-api` стартует после его успешного завершения и монтирует файл только для чтения. Ротация: пересоздать ключ в Authentik, выполнить `docker compose run --rm authentik-jwks-export`, перезапустить `agentos-api` (middleware читает файл при старте). Подпись токенов — ключом Authentik (RS256), провайдер привязывается к нему в blueprint. *Альтернатива:* загрузка по URL — не поддерживается пином.

**D9. Публикация интерфейса: без прокси в compose.** Authentik слушает `127.0.0.1:9000`; обратный прокси и TLS — задача хоста (описывается в `deploy-platform` и README: домен Authentik, доверенные адреса прокси, заголовки). *Допущение:* прокси на Docker-хосте уже есть или ставится вне этого репозитория; проверка «админка только `admins`» и публикации на домене выполняется на стенде с прокси, локально проверяется доступность и политика доступа в самом Authentik. *Альтернатива:* контейнер прокси в compose — добавляет сервис и решение по сертификатам, которых сейчас нет.

**D9a. Токены сервисных учётных записей — тот же провайдер.** `client_credentials` включается в `grant_types` публичного провайдера (по умолчанию список пуст — отвергается даже `authorization_code`); токен сервисной записи имеет `aud` фронтенда и проходит ту же проверку. Издатель токена зависит от адреса, по которому клиент обратился к Authentik: `AUTH_ISSUER` должен совпадать с ним (`localhost` ≠ `127.0.0.1`).

**D9b. Blueprints независимы друг от друга, поток входа — на бренде домена.** Порядок применения blueprints (в том числе встроенных) не определён: blueprint, искавший стадии по умолчанию (`!Find`), на первом запуске падал и не повторялся. Поэтому `30-authentication-flow.yaml` определяет все свои стадии сам. Бренд по умолчанию (`authentik-default`) принадлежит встроенному blueprint и перезаписывался им; поэтому поток входа с обязательным вторым фактором привязан к собственному бренду с доменом `AUTH_BRAND_DOMAIN`, а бренд по умолчанию не трогается. Пользователь без второго фактора на домене продукта проходит настройку TOTP.

**D10. Авторизация везде.** `authorization` включена при любом `RUNTIME_ENV`; `dev` требует тот же `JWT_JWKS_FILE`. Для `curl`, `mcp_check.sh` (`MCP_CHECK_TOKEN`) и evals токен берётся у сервисной учётной записи Authentik, созданной blueprints для разработки.

**D11. Агентский каталог и сервисные учётные записи Agno не трогаем.** `user_directory=True` продолжает автоматически регистрировать пользователей по `sub`; `/service-accounts` и токены `agno_pat_*` остаются доступными. Плагины и средства разработки используют сервисные учётные записи Authentik (решение владельца). Совместное существование двух механизмов фиксируется как открытый вопрос.

## Risks / Trade-offs

- [Миграции Authentik требуют `CREATE` на базу и на схему `public`] → выдаются в `authentik-db-init` (D3); роль по-прежнему не суперпользователь и не читает схему `ai`. Роль с `CREATE` на базу может создавать произвольные схемы — принимаем; расширений PostgreSQL миграции не требуют.
- [Обратная изоляция не обеспечивается: загрузочный пользователь `ai` — суперпользователь и читает схему `authentik`] → принять; отдельная несуперпользовательская роль для Agno — отдельный change, меняет `DB_USER` и миграции.
- [Authentik не описывает общую базу с другими приложениями] → проверка состава таблиц по схемам и отказ в правах роли Authentik к `ai` входят в приёмку.
- [Выключатель каталога Agno (`disabled`) и отзыв пользователя в Authentik не связаны: токен действует до истечения срока] → короткий срок Access Token; синхронизация отзыва — отдельный change.
- [JWKS-файл устаревает при ротации, пока API не перезапущен] → ротация только через описанную процедуру; в приёмку входит проверка отклонения старых токенов после перезапуска.
- [Роли Agno (`roles_claim`) добавляют таблицы и `/authz`] → оценить на проверке D5; при неприемлемом составе — вариант B.
- [Dev с авторизацией замедляет ручную работу: нужен токен] → сервисная учётная запись разработки и описание получения токена в README.
- [Ресурсы хоста: ещё два контейнера Authentik] → учесть при выборе размера хоста; параметры памяти не фиксируем заранее.
- [Расхождения документации с кодом, найденные при подготовке: `overview` и `architecture` («Подключение к БД») описывают значения по умолчанию `RUNTIME_ENV=prd` и БД, которых в коде уже нет (удалены в рабочем дереве)] → не меняем здесь, их закрывает `remove-config-fallbacks`; формулировки в дельте `overview` сохранены без изменений за пределами авторизации.

## Migration Plan

1. Обновить `.env` по `example.env` (секретный ключ Authentik, пароль роли БД, начальный администратор, адреса).
2. `docker compose up -d --build`: создаются схема и роль, применяются миграции и blueprints Authentik, выгружаются ключи, стартует API.
3. Существующие данные Agno не затрагиваются; пользователей Agno, созданных в `dev` без Authentik, нужно пересоздать (их `user_id` не совпадёт с `sub`): локальная БД разработки пересоздаётся через `./scripts/dev.sh reset-db --yes` (эксплуатации не было).
4. Откат: удалить сервисы Authentik из `compose.yaml`, вернуть прежнее условие авторизации в `app/main.py`, `DROP SCHEMA authentik CASCADE` и удалить роль; данные Agno не затрагиваются.

## Open Questions

- Версия образа Authentik (выбирается при apply по официальным релизам и совместимости с PostgreSQL 18).
- Совместное существование `/users*` и `/service-accounts` Agno с пользователями и сервисными учётными записями Authentik: оставить оба набора или отключить `user_directory`/PAT после ядра.
- Доступ AgentOS UI (`os.agno.com`) в `prd`: прежнее требование «ключ создаётся на os.agno.com» из спеки `integrations` снято, так как проект принимает токены только Authentik; нужен ли UI вообще и как он получает токен — решить владельцу.
- Срок жизни Access Token и refresh, срок и выдача токенов сервисных учётных записей плагинов.
- Где хранятся роли в проекте и как соотносятся с группами Authentik — change ядра; не влияет на интерфейс D7.
- Обратный прокси: тип, домены, TLS (D9) — решается при деплое.
