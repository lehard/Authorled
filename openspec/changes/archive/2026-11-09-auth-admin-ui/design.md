# Design

## Context

Мотивация описана в `proposal.md`, требования — в дельте спеки `auth`.

Как Authentik 2026.8.5 применяет blueprints, проверено по исходникам в контейнере на проде:

- Задача `blueprints_discovery` запускается при старте и раз в час. Blueprint она применяет только тогда, когда хеш файла отличается от `last_applied_hash`. Значит, правку из админки откатывает не перезапуск, а релиз, который меняет файл. На проде группы последний раз применялись 6 ноября, потоки 8 ноября, в день правки их файла.
- Запись с существующим объектом сериализатор обновляет частично (`partial=True`). Меняются только поля из `attrs`, остальные остаются как были.
- Запись `state: created` при существующем объекте пропускается целиком, но объект всё равно попадает в результат, и `!KeyOf` на него работает.
- Выражение политики может создать событие. `ak_create_event(action, **kwargs)` записывает действие как `custom_<action>` и копирует в событие контекст политики, то есть почту и имя из формы. `Event.new(EventAction.CONFIGURATION_ERROR, app=..., message=...)` записывает настоящий `configuration_error`; без `app` он падает, потому что ищет имя модуля вызывающего кода (проверено на локальном стенде).

Сейчас каждый объект объявлен одной записью `present`. Список почт политика `authorled-email-not-registered` читает из `os.environ["AUTH_ALLOWED_EMAILS"]`. Шаг ввода считает эту политику без кэша (проверено в change `test-access-allowlist`).

## Goals / Non-Goals

**Goals:**

- Владелец задаётся для каждого поля, а не для объекта целиком: у одного потока заголовок принадлежит админке, а `designation` — репозиторию.
- Список почт меняется без перезапуска и без релиза.

**Non-Goals:**

- Защита полей админки от ошибок администратора: проверки репозитория их не видят.

## Decisions

**Две записи на объект со смешанными владельцами.** Первая запись `state: created` несёт все поля, нужные для создания, вместе с полями админки. Вторая запись `present` с теми же `identifiers` идёт сразу за ней и несёт только поля репозитория. На пустой схеме первая запись создаёт объект, вторая подтверждает поля репозитория. На существующем объекте первая пропускается, вторая восстанавливает поля репозитория и не трогает остальные, потому что обновление частичное. `id` для `!KeyOf` ставится на первую запись.

Так объявляются шесть объектов:

| Объект | Поля админки (запись `created`) | Поля репозитория (запись `present`) |
|---|---|---|
| Поток `authorled-authentication` | `name`, `title` | `designation`, `authentication` |
| Поток `authorled-enrollment` | `name`, `title` | `designation`, `authentication` |
| Поток `authorled-invalidation` | `name`, `title` | `designation` |
| Бренд `AUTH_BRAND_DOMAIN` | `branding_title` | `default`, `flow_authentication` |
| Шаг `authorled-authenticator-email-setup` | `subject` | `friendly_name`, `use_global_settings`, `token_expiry`, `template` |
| Шаг `authorled-authentication-password` | `failed_attempts_before_cancel` | `backends` |

Остальные записи не меняются.

Отвергнутые варианты:

- `state: created` на объект целиком: контракт (`designation`, срок кода, привязка бренда) перестал бы восстанавливаться.
- Убрать поля админки из blueprints совсем: на пустой схеме объект не создастся без обязательных `name` и `title`, а бренд и письмо получат значения по умолчанию из Authentik.

**Список в атрибуте группы `screenwriters`.** Атрибуты группы редактируются в админке как YAML (Directory → Groups → screenwriters → Attributes). Обе записи группы в blueprints объявляют её только по `identifiers`, а частичное обновление не трогает `attributes`. Отвергнутые варианты:

- Отдельная политика или правило, текст которого правит администратор: правка кода в админке рискованнее правки списка, и релиз перетёр бы такую политику.
- Атрибут бренда: бренд и так принадлежит двум владельцам, а список относится к тому, кто попадает в `screenwriters`.

**Проверка в существующей политике.** Политика `authorled-email-not-registered` находит группу `screenwriters` и читает `attributes["allowed_emails"]`. Если группы нет, атрибута нет или он не список строк, политика:

- создаёт событие `Event.new(EventAction.CONFIGURATION_ERROR, app="authorled-email-not-registered", message=...)` с текстом, который называет группу и атрибут, без данных формы;
- вызывает `ak_message("Регистрация временно недоступна.")`;
- возвращает `False`.

Так человек видит короткий отказ, а причина видна администратору в журнале событий. Это явный отказ, а не подстановка значения. Исключение из политики не бросаем: его текст Authentik показал бы человеку, а фронтенд вывел бы как «Authentik ответил: …». Порядок проверок такой: совпадение имени пользователя с почтой, затем исправность атрибута, затем вхождение в список, затем имя, затем занятая почта. Разбор строк как сейчас: обрезка пробелов, нижний регистр, пустые строки отбрасываются, `["*"]` открывает регистрацию всем.

**Экран регистрации не меняется.** Неизвестное сообщение фронтенд показывает как «Authentik ответил: Регистрация временно недоступна.». Для состояния, которое бывает только при ошибке настройки, этого хватает. Правка таблицы `KNOWN` в `web/src/auth/flow/flowClient.ts` вне scope.

**Локальный стенд.** `auth/blueprints-dev/dev-users.yaml` получает запись группы `screenwriters` с `attributes: {allowed_emails: ["*"]}`. Его применяет `./scripts/dev.sh auth-users`, а в прод этот файл не попадает. Атрибуты группы после этого заменяются целиком: на локальном стенде других атрибутов у неё нет.

**Удаление `AUTH_ALLOWED_EMAILS`.** Переменная убирается из окружения Authentik в `auth/compose.yaml` и из `example.env`, README, скиллов. `check_auth_boundary.sh` менять не нужно: повторные записи групп он сворачивает через `sort -u`.

## Risks / Trade-offs

- [Две записи с одними `identifiers` в одном файле — необычная форма blueprint] → На локальном стенде проверить пустую схему (`reset-db`) и повторное применение изменённого файла, прежде чем идти дальше.
- [Поля админки, которые уже есть на проде, больше не обновятся из репозитория] → Принято в интенте. README перечисляет эти поля.
- [Регистрация на проде закроется, если атрибут не заполнить до релиза] → Атрибут заполняется до выкладки, это шаг плана миграции. Старая политика его не читает, поэтому заполнять заранее безопасно.
- [Администратор сохранит атрибут строкой, а не списком] → Регистрация отказывает, в журнале видна причина. Формат с примером есть в README.
- [Откат на прошлый релиз требует `AUTH_ALLOWED_EMAILS` в `.env`] → Переменная удаляется с сервера только после проверки нового релиза.

## Migration Plan

1. До релиза на проде: в админке под `akadmin` записать в атрибуты группы `screenwriters` текущий список из `AUTH_ALLOWED_EMAILS`: `allowed_emails:` и почты по одной строкой, а `*` записать как `["*"]`.
2. Выпустить релиз из `main`, как описано в README («Deploy by release»).
3. Проверить на проде, что blueprints применились без ошибок (`status` экземпляров `successful`), заголовки потоков и бренда не изменились, почта из списка проходит шаг регистрации, а почта не из списка получает отказ.
4. Удалить `AUTH_ALLOWED_EMAILS` из `/etc/authorled/authorled.env` (с подтверждения владельца).

Откат: выпустить прошлый релиз, пока переменная ещё на сервере. Атрибут группы прошлой версии не мешает.
