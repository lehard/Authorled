# Proposal

## Why

Владелец хочет менять настройки входа и регистрации в админке Authentik (`https://auth.soavtor.app/if/admin/`) без релиза (`business-intents/auth-admin-ui.md`). Сейчас это не работает. Blueprints задают значения почти всех объектов, и релиз, который меняет файл blueprint, возвращает их к значениям из репозитория. А список приглашённых живёт в `AUTH_ALLOWED_EMAILS`, поэтому для нового бета-тестера нужно править файл на сервере и перезапускать Authentik.

## What Changes

- У каждой настройки Authentik один владелец.
  - **Репозиторий**: то, на что опирается код продукта. Это группы, OIDC-провайдер и приложение, поток выхода, состав и порядок шагов входа и регистрации, срок и шаблон кода, привязка потока входа к бренду, сервисные учётные записи. Blueprint применяет эти значения при каждом изменении файла.
  - **Админка**: заголовки потоков и бренда, тема письма с кодом, число неудачных попыток пароля. Blueprint задаёт их только при создании объекта и больше не трогает.
- Список разрешённых почт хранится в атрибуте `allowed_emails` группы `screenwriters`, и владелец меняет его в админке. Новое значение действует сразу, без перезапуска.
- Без атрибута или с неверным атрибутом регистрация отказывает: человек видит «Регистрация временно недоступна.», а в журнале Authentik появляется событие с причиной.
- **BREAKING**: настройка `AUTH_ALLOWED_EMAILS` удаляется. Перед релизом владелец переносит текущий список с сервера в атрибут, иначе регистрация закроется для всех. Вход уже зарегистрированных не меняется.
- На локальном стенде `./scripts/dev.sh auth-users` открывает регистрацию всем (`allowed_emails: ["*"]`).
- README получает раздел «Админка Authentik»: как войти под `akadmin`, что менять в админке, что откатит релиз, как открыть регистрацию тестеру.

## Scope

- `auth/blueprints/`: разделение объектов на поля репозитория и поля админки, правило регистрации читает атрибут группы.
- `auth/compose.yaml`, `example.env`: удаление `AUTH_ALLOWED_EMAILS`.
- `auth/blueprints-dev/dev-users.yaml`, `scripts/dev.sh`: открытая регистрация на локальном стенде.
- README, скиллы `setup-platform` и `deploy-platform`.
- Перенос списка на прод и удаление переменной из `/etc/authorled/authorled.env` при релизе.

## Non-goals

- Своя админка во фронтенде продукта.
- Приглашения Authentik по одноразовым ссылкам.
- Ограничение доступа к админке по IP или отдельный домен для неё.
- Управление из админки тем, что принадлежит репозиторию.
- Синхронизация правок из админки в репозиторий и отчёт о расхождениях.
- Перенос в админку SMTP и других настроек `AUTHENTIK_*` из окружения.
- Изменение экранов фронтенда: новый отказ показывается так же, как другие сообщения Authentik.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `auth`:
  - новое требование «Настройки админки» делит настройки между репозиторием и админкой;
  - «Конфигурация из blueprints» допускает второй ручной шаг на пустой схеме: заполнить список почт;
  - «Регистрация» берёт список из атрибута группы;
  - «Пользователи для разработки» открывают локальную регистрацию;
  - «Настройка разрешённых почт» заменяется требованием «Список разрешённых почт».

## Impact

- Код API, токены и контракт токена не меняются.
- Для объектов, которые уже есть на проде, поля админки после релиза остаются как есть. Их будущие правки в репозитории до прода не дойдут, дальше они меняются только в админке.
- Релиз требует ручного шага на сервере до выкладки: перенести список в атрибут.
- Реальные почты по-прежнему не попадают в репозиторий: они живут в базе Authentik.
