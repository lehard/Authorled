# Design

## Context

См. proposal.md — Why. Что есть сейчас и что показал код Authentik `2026.8.5` (контейнер `authentik-worker`, `/authentik/stages/…`):

- Поток входа `authorled-authentication` описан в `auth/blueprints/30-authentication-flow.yaml`: шаг почты (`pretend_user_exists: false`) → пароль, если задан → код (`authorled-authentication-mfa-validation`, при отсутствии устройства — настройка `authorled-authenticator-email-setup`) → вход. Блюпринты применяются в неопределённом порядке, поэтому поток входа ни на что вне своего файла не ссылается.
- Шаг письма `authentik_stages_email` подтверждает почту **ссылкой** (`FlowToken`, в письме длинный ключ), а не кодом.
- Шаг настройки устройства для почты (`authenticator_email`) шлёт 6-значный код и держит устройство в плане потока; `device.save()` выполняется только после верного кода, поэтому неподтверждённое устройство в базу не попадает. Но устройство привязано к пользователю, и сохранить его можно только у уже сохранённого пользователя. Повторный POST без кода отправляет письмо ещё раз.
- `user_write` создаёт пользователя из полей шага ввода (`ak-stage-prompt`): `username`, `email`, `name`, умеет группу (`create_users_group`) и неактивных пользователей.
- Фронтенд (`web/src/auth/flow/flowClient.ts`, `LoginScreen.tsx`) проходит шаги через `/api/v3/flows/executor/<slug>/` на своём адресе; неизвестная почта сейчас — `SignInError` у поля почты по тексту «Failed to authenticate.». «Отправить ещё раз» работает только на шаге проверки кода (`canResend()`), не на шаге настройки.

## Goals / Non-Goals

**Goals:**
- Регистрация кодом из письма на тех же механизмах, что вход, без шагов со ссылками и без своего кода на бэкенде.
- Ни одного неподтверждённого устройства для кода в базе.

**Non-Goals:**
- Подтверждение почты до создания пользователя (см. решение 2).
- Изменение входа для существующих пользователей.

## Decisions

1. **Поток регистрации в том же файле, что вход.** `30-authentication-flow.yaml` получает поток `authorled-enrollment` (designation `enrollment`, `authentication: require_unauthenticated`, заголовок «Регистрация в Authorled») и его шаги; шаг почты потока входа получает `enrollment_flow: !KeyOf flow-enrollment`. Так связь не зависит от порядка блюпринтов. Группа `screenwriters` объявляется в этом файле тем же `identifiers` (`name: screenwriters`) без своих атрибутов — запись идемпотентна и не спорит с `10-groups.yaml`.
   - Альтернатива: отдельный файл и `!Find` на поток входа. Отклонена: спека запрещает зависимость от порядка блюпринтов.

2. **Порядок шагов: ввод → создание → код → вход.**
   - `authorled-enrollment-prompt` (`ak-stage-prompt`): поля `email` (email, обязательное), `username` (text, обязательное: скрытые поля Authentik заполняет на сервере и не берёт значение из запроса), `name` (text, обязательное, «Имя и фамилия»); политика проверки `authorled-email-not-registered` (выражение без побочных эффектов): отказ «Аккаунт с такой почтой уже есть.», если пользователь с этой почтой есть (без учёта регистра), и отказ, если `username` не равен `email`;
   - `authorled-enrollment-write` (`user_write`): `user_creation_mode: always_create`, активный, тип `internal`, группа `screenwriters`;
   - шаг настройки кода — тот же `authorled-authenticator-email-setup` (`!KeyOf stage-email-setup`), чтобы устройство было того же шага, что проверяет вход;
   - шаг входа — тот же `authorled-authentication-login`.
   Пользователь создаётся до кода, потому что устройство можно сохранить только у сохранённого пользователя. Войти без кода нельзя: брошенная регистрация оставляет активного пользователя без устройства, и следующий вход идёт обычным путём — почта → настройка устройства с кодом → вход.
   - Альтернатива: неактивный пользователь до кода и активация после. Отклонена: в шагах Authentik нет активации без ссылки, а политика с побочным эффектом (`is_active = True` в выражении) — скрытая логика в конфигурации.
   - Альтернатива: шаг письма со ссылкой. Отклонена: владелец выбрал код, как при входе.

2a. **Шаг пароля — только при непустом пароле.** `user_write` создаёт пользователя с пустой строкой в поле пароля, а Django считает её пригодным паролем (`has_usable_password()` истинно), поэтому правило `authorled-user-has-password` показало бы зарегистрированному пользователю невыполнимый шаг пароля. Правило проверяет и непустой хэш: `bool(user.password) and user.has_usable_password()`. Пользователи с паролем (`writer`, `editor`, администратор) входят как раньше. Найдено при проверке 2026-11-01.

3. **Имя пользователя = почта.** Фронтенд отправляет `username` равным `email`; политика проверяет равенство. Вход по-прежнему по почте или имени пользователя.

4. **Фронтенд: поток регистрации — отдельный проход того же клиента.**
   - `identify()` различает неизвестную почту: шаг почты вернул ошибку «Failed to authenticate.» → новый шаг `"new-account"`, а не `SignInError`.
   - `register(email, name)`: сбрасывает незаконченный план (`/flows/-/cancel/`), запускает `/api/v3/flows/executor/authorled-enrollment/`, ждёт `ak-stage-prompt`, отправляет `{ component: "ak-stage-prompt", email, username: email, name }`; ответ `ak-stage-authenticator-email` → шаг `"code"`; ошибки полей `email` и `name` и ошибки политики (`non_field_errors`) — к полю почты или имени.
   - `ak-stage-prompt` добавляется в список известных шагов; неизвестный шаг остаётся явной ошибкой.
   - `canResend()` и `requestCode()` поддерживают и шаг настройки: повторный POST `{ component: "ak-stage-authenticator-email" }` без кода отправляет письмо снова. Это заодно включает «Отправить ещё раз» при первом входе пользователя без устройства.
   - После кода поток регистрации заканчивается `xak-flow-redirect`, дальше — получение токенов по OIDC, как после входа.

5. **Экраны (`LoginScreen.tsx`)** по макету v1 и дизайн-системе:
   - «Аккаунта ещё нет»: «Аккаунта с почтой <почта> ещё нет. Создадим его — пароль не нужен.», основная кнопка «Создать аккаунт», вторая «Другая почта»;
   - «Как вас зовут?»: поле «Имя и фамилия» (`autocomplete="name"`, пример «Например, Анна Северова»), «Дальше»; пустое — ошибка «Введите имя.» без запроса к Authentik;
   - «Подтвердите почту»: тот же компонент кода, код отправляется сам после шестой цифры, как при входе (отдельной кнопки нет), «Отправить ещё раз» через 60 секунд, «Другая почта»;
   - индикатор шагов регистрации из двух точек (имя, код), как `au-steps` макета; при входе его нет.

6. **TODO про неподтверждённое устройство.** По коду закреплённой версии устройство сохраняется только после верного кода. Проверка в задачах: бросить регистрацию и первый вход на шаге кода, затем войти — ошибки «The user already has an email address registered for MFA» быть не должно. Если она воспроизведётся, change останавливается и выносит причину владельцу.

## Risks / Trade-offs

- [Аккаунт создаётся до подтверждения почты] → чужой человек может занять почту и задать имя; войти без кода он не может, владелец почты войдёт по коду и поменяет имя в профиле (кабинет — отдельный интент). Принято для MVP.
- [Злоупотребления открытой регистрацией: рассылка кодов на чужие адреса] → ограничения Authentik на частоту писем и попытки кода; при необходимости — приглашения или капча отдельным решением.
- [Перечисление аккаунтов по экрану почты] → принято в интенте, как в макете v1.
- [Смена потока в одной сессии Authentik] → перед регистрацией незаконченный план сбрасывается; проверяется переходами «вход → регистрация → вход» в задачах.
- [Письмо регистрации с темой «Код для входа в Authorled»] → тот же шаг устройства, что у входа; для пользователя код — это вход в продукт. Отдельная тема — не в этом change.
- [Production без SMTP] → регистрация не завершится; проверяется вместе с почтой Authentik при деплое.

## Migration Plan

1. Блюпринт применяется при перезапуске `authentik-server` и `authentik-worker` (`docker compose up -d`); пользователи и вход не меняются.
2. Откат: прежний `30-authentication-flow.yaml` убирает связь `enrollment_flow`; поток регистрации и созданные пользователи остаются в базе (удаляются вручную, если нужно).
