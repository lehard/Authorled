# Proposal

## Why

На время тестирования сервер должен быть доступен только людям, которых назвал владелец (`business-intents/test-access-allowlist.md`). Спека `auth` сейчас требует обратного: регистрация открыта всем, поэтому зарегистрироваться сможет любой, кто найдёт адрес.

## What Changes

- Новая обязательная настройка `AUTH_ALLOWED_EMAILS`: почты через запятую без учёта регистра или `*`, что открывает регистрацию всем.
- Поток `authorled-enrollment` отказывает почте не из списка: пользователь не создаётся, письмо не отправляется.
- Экран регистрации показывает понятный отказ.
- Без настройки стек не запускается, ошибка называет её.
- Чтобы изменить список, владелец меняет настройку и пересоздаёт контейнеры Authentik. Новый релиз не нужен.
- **BREAKING** для локальных стендов: в `.env` нужно добавить `AUTH_ALLOWED_EMAILS=*`.

## Scope

- `auth/blueprints/30-authentication-flow.yaml`: проверка в политике регистрации.
- `auth/compose.yaml`: передача настройки.
- `web/src/auth/flow/flowClient.ts`: текст отказа.
- `example.env`, `README.md`, скиллы `setup-platform` и `deploy-platform`.

## Non-goals

- Экран управления списком, приглашения по ссылке.
- Отзыв доступа у зарегистрированных: это блокировка в Authentik.
- Роли по списку: все получают группу `screenwriters`.
- Ограничение входа: вход остаётся как есть, потому что без регистрации аккаунта нет.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `auth`: «Регистрация» открыта только почтам из настройки; добавляется требование к настройке.
- `web/workspace`: экран регистрации показывает отказ.

## Impact

- Реальные почты живут только в настройках сервера и не попадают в публичный репозиторий.
- Код API и токены не меняются.
- Change должен войти в первый релиз `deploy-on-release`.
