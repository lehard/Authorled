# Architecture
Целевая архитектура Соавтора. Текущий код — шаблон AgentOS; мастер-спека `openspec/specs/` описывает его как есть и обновляется через changes.

## Сервисы
Проект — монорепозиторий из четырёх модулей верхнего уровня (`agno/`, `web/`, `auth/`, `site/`) и общего корня (compose-файлы с общей PostgreSQL, `openspec/`, скрипты стека): модульный монолит бэкенда плюс фронтенд. Модули бэкенда живут в одном релизе и общаются через явные контракты; внутренности модуля другие модули не читают.
| Часть | Где в репозитории | Роль |
|---|---|---|
| Фронтенд | `web/` | Интерфейс писателя и админка (тонкий клиент) |
| Сайт продукта | `site/` | Статические страницы о продукте и заявка в бету; берёт токены из `web/`, заявку принимает маршрут ядра без токена `POST /api/v1/beta-requests` |
| Бэкенд (Agno) | `agno/` (`app/`, `agents/`, `db/`…) | Продуктовая логика, агент, данные, API |
| Модуль `auth` | `auth/`, `agno/app/auth/` | Полный Authentik: пользователи, вход, роли, токены; адаптер в коде Agno |
| Модуль биллинга | `agno/billing/` | Тарифы, подписки, журнал расхода и лимит соавтора; своя схема `billing` и свои миграции |
Фронтенд и бэкенд живут в одном репозитории (решение 2026-10-27), но собираются и деплоятся отдельно. Модуль `auth` — часть бэкенда: Authentik работает отдельными процессами (сервер, worker), но его конфигурация и релиз в этом репозитории. Связь только через контракты: OIDC/JWT (фронтенд и плагины ↔ Authentik, бэкенд проверяет токены), REST + SSE + AG-UI (web ↔ backend). См. ADR-001.

## Модуль `auth`
- Деплой-часть `auth/`: compose-фрагмент с закреплённой версией Authentik, blueprints (группы, OIDC, потоки входа, сервисные учётные записи), бренд, инициализация БД.
- Кодовая часть `agno/app/auth/`: проверка JWT в AgentOS, сопоставление групп и scopes, `Principal`, зависимости `current_principal` и `current_identity` (почта и имя, только для записи пользователя) для своих маршрутов, интерфейс `can_access_project`.
- Другие модули знают только `Principal` и интерфейс доступа к проекту; JWT, claims и Authentik вне `agno/app/auth/` не читаются.
- Данные Authentik — схема `authentik` в общей PostgreSQL с отдельной ролью; Agno — схема `ai`, данные продукта (ядро) — схема `authorled`, обе под несуперпользовательской ролью `agentos` без доступа к `authentik`.
- Контракт с бэкендом — claims и группы токена (спека `auth`, «Контракт токена»); при выносе Authentik уходит `auth/` и схема `authentik`, `agno/app/auth/` остаётся в бэкенде.

## Модуль биллинга
- Код — `agno/billing/`, единственный вход — `billing/__init__.py`: операции с простыми значениями, каждая в своей транзакции, без соединения с базой в сигнатурах. Готов к выносу в сервис: вызовы заменятся на HTTP, вызывающие не изменятся.
- Биллинг не импортирует ядро, слой приложения, агентов, команды и Agno; другие модули берут только `billing`, ядро биллинг не вызывает. Связывает их слой приложения: `GET /api/v1/me` выдаёт подписку, хуки соавтора находят пользователя ядра и зовут биллинг. Границу проверяет `scripts/check_billing_boundary.sh` в `validate.sh`.
- Данные — схема `billing` в общей базе под ролью `agentos`, пользователь ядра хранится значением, без внешних ключей в другие схемы; своя цепочка Alembic идёт после цепочки ядра (спека `billing/module`).

## Слои бэкенда
1. **Ядро** — своя доменная логика (`agno/core/`): истории, документы, текст сценария с ревизиями, рецензирование, файлы и импорт; после MVP — документы Д1–Д22, версии и статусы, чек-листы, граф связей, утверждения автора, журнал решений. Агенту доступно как инструменты, вызывающие ядро (функции Agno в процессе API, `agno/agents/coauthor_tools.py`; отдельного MCP-сервера ядра нет), нашим маршрутам — как обычный код.
2. **Агент и методология** — агент Agno с навыками этапов; Workflows для фиксированных процедур (пересмотр, импорт, проверка документа).
3. **Свои маршруты API** (`/api/v1/`, роутер в приложении AgentOS) — продуктовые действия без LLM: проекты, документы, правки автора, утверждение, файлы, поиск. См. ADR-002.

## Инварианты
1. Вся продуктовая логика — в бэкенде; отдельного бэкенда между фронтом и AgentOS нет. AgentOS — единый шлюз для всех клиентов, источник истины — бэкенд.
2. Агент меняет произведение только через ядро. Действия «утвердить документ» у агента нет: утверждает только автор, через наш маршрут.
3. Предложения агента не меняют текст автора напрямую — автор принимает или отклоняет. Предложения правок агент создаёт только инструментами ядра (якорь — сцена и точная цитата, метку в текст ставит браузер); принятие и отклонение — маршрут автора.
4. Данные Agno и данные произведения в PostgreSQL разделены: Agno — схема `ai`, ядро — схема `authorled`, биллинг — схема `billing`, у ядра и биллинга свои цепочки миграций Alembic (шаг `agentos-migrate` до API, сначала ядро). Изоляция Agno (`user_isolation`) защищает только его данные; доступ к произведению и роли в проекте бэкенд проверяет сам, изоляция — по проекту.
5. Хранение произведения: текст сценария — один документ редактора (JSON ProseMirror), сохраняется целиком с номером ревизии, расхождение ревизий — `409`. Прошлые состояния документов хранятся снимками полного содержимого, не диффами, а точка драфта хранит все его документы; драфт истории — это все связанные документы, драфты равноправны и независимы (решение 2026-11-05 отменяет решение lehard 2026-11-02, `business-intents/story-drafts-and-versions.md`); утверждение и его последствия для связанных документов (после MVP) — атомарно; векторный и полнотекстовый поиск — индекс поверх канона, пересобирается из него.
6. Агно-уровень (из шаблона): Agno владеет OS Manager, Company Manager, durable execution, lifecycle sandbox — не пересоздавать; общая БД через `get_postgres_db()` без аргументов; одна инстанция API; `RUNTIME_ENV=dev` не деплоится; невалидный sandbox падает, а не откатывается на сервер.

## Обязательные и запрещённые паттерны
- Поведение фреймворка сверять с пином Agno в `pyproject.toml`; отказы не обходить, compatibility-адаптеры не писать.
- Content-адаптеры знаний — с уникальными ID; второй адаптер с ID OS запрещён.
- Фронтенд не хранит своих данных и не содержит продуктовой логики.

## Ключевые интеграции
- Authentik (модуль `auth`): JWT с проверкой подписи по ключам Authentik; в AgentOS `authorization=True`, `user_isolation=True`. Приложение берёт ключи только из файла `JWT_JWKS_FILE` (выгружается модулем `auth`); загрузки по URL в Agno 3.1.10 нет.
- Фронтенд: Refine (каркас, роутинг, проекты, файлы, админка), CopilotKit (чат через AG-UI-интеграцию Agno), форк `@plotwell/editor` в `web/src/editor/` (редактор сценария; автосохранение отправляет на бэкенд весь текст с номером ревизии; комментарии и предложения агента — плагины-декорации, хранятся на бэкенде); дизайн-система — shadcn/ui на Tailwind CSS — ADR-004.
- Модели: только через LiteLLM; зарубежные LLM разрешены. Эмбеддинги, модерация, антивирус — в РФ или свои.
- Модели — DeepSeek (`deepseek-fast`, `deepseek-thinking`), эмбеддинги — один из псевдонимов, выбранный `EMBEDDINGS_MODEL` (GigaChat `Embeddings-2` или модели Cloud.ru Foundation Models, все 1024 измерения); всё через LiteLLM-прокси по псевдонимам — ADR-003.
- ClamAV — проверка загрузок до обработки: сервис `clamav` в compose, проверка в запросе загрузки (протокол `INSTREAM`), без него API не стартует.

## Очереди и события
- **Фоновые задачи и Workflows** — только durable-очередь Agno (`QueueConfig(durable=True)`): задачи и состояние в PostgreSQL, выполняет сам процесс AgentOS. Отдельного воркера (Celery, RQ и т.п.) нет. Сюда же наши задачи: пересчёт поискового индекса после правки, антивирус и разбор загрузок, импорт рукописи, пересмотр.
- **Redis — координация и события, не задачи и не истина** («Redis is optional coordination, never truth»):
  1. стримы и отмена ходов агента между репликами (`QueueConfig(redis=…)`): `/resume` и отмена на любой реплике;
  2. рассылка продуктовых событий фронтенду (pub/sub → SSE: документ утверждён, флаг «требует пересмотра», импорт завершён) на все вкладки и устройства автора — пишем сами.
- На старте (одна инстанция API) Redis не нужен: стрим в памяти, рассылка внутри процесса. При ≥2 репликах Redis обязателен. Закладываем сразу; включение — только конфигурацией, без переделки кода.
- Если Redis включён конфигурацией и недоступен — явная ошибка, без тихого отката на in-process.

## Где что лежит (шаблон)
Код бэкенда — в `agno/` (пути ниже — от него), скрипты всего стека — в корневом `scripts/`.
`app/main.py` — регистрация AgentOS; `app/interfaces.py` — MCP; `app/company.py`, `app/config.yaml`; `app/registry.py`; `app/settings.py` — модели; `app/sandbox.py`; `agents/`, `teams/`, `db/`, `evals/`, `scripts/` (только скрипты бэкенда). Детали — `openspec/specs/architecture/spec.md`.

## Ключевые решения
- Фронтенд и модульный монолит бэкенда (авторизация — модуль `auth`), связь только через стандартные контракты — ADR-001.
- Свои продуктовые маршруты — роутер в приложении AgentOS (не `base_app`), утверждение только маршрутом — ADR-002.
- Модели DeepSeek и эмбеддинги (GigaChat или Cloud.ru Foundation Models, выбор `EMBEDDINGS_MODEL`) через LiteLLM-прокси — ADR-003.
- Фронтенд: Refine, CopilotKit, форк `@plotwell/editor` на shadcn/ui — ADR-004.
- Писательские потоки по образцу STARC; партнёрство или своё — ADR-005.
