# Engineering Standards
Стек: Python `>=3.14`, Agno `3.1.10` (FastAPI/uvicorn), PostgreSQL 18 + pgvector, Alembic, pytest, Docker Compose. Линт/типы: ruff (line-length 120, E,F,I,UP), mypy + pydantic plugin.

## Общее
- Зависимости — в `agno/pyproject.toml`; `agno/requirements.txt` генерировать `./agno/scripts/generate_requirements.sh`; `uv.lock` не добавлять. После смены зависимостей пересобрать обе цели `agno/Dockerfile`. Окружение — `agno/.venv` (`./agno/scripts/venv_setup.sh`).
- Агент: стабильный ID, явные instructions/tools, `default_model()`, общая БД, history и datetime (скилл `create-agent`). Регистрация — `agno/app/main.py`; промпт — навык `agno/skills/<agent_id>/SKILL.md` по стандарту Anthropic Agent Skills (`name` = id агента, тело — промпт, в коде промпта нет); описания и быстрые подсказки — `agno/app/config.yaml`.
- Минимум абстракций и инфраструктуры — только под конкретную потребность. Перед правкой — читать исходник и `git status`, держаться scope.
- Без fallback: отсутствующий/невалидный ввод, конфиг или env — явная ошибка с понятным сообщением.

## Миграции
- Схема ядра — Alembic. Только вперёд; применённые миграции не редактируются.
- В проде миграции — отдельный шаг перед деплоем, не при старте сервиса.
- Таблицы Agno мигрирует Agno, отдельной задачей при обновлении пина. Схемы ядра и Agno не смешивать.
- Данные ядра — схема `authorled` в общей базе `ai`; владелец — роль `agentos`, схему создаёт `agno/db/init.sql`. Журнал версий Alembic — в схеме `authorled`; миграции не трогают `ai`, `authentik` и `public`.
- Миграции применяет одноразовый контейнер `agentos-migrate` под ролью `agentos` между `agentos-db-init` и `agentos-api`, в разработке и в проде одинаково. API миграции не запускает; упала миграция — API не стартует.
- У истории миграций одна голова (проверяет `./scripts/validate.sh`). Описание таблиц в коде совпадает со схемой в базе (проверяет pytest).
- Удаление записей ядра — мягкое: поле `deleted_at`, как корзина у историй. Жёсткое удаление — только явным действием (например, «Удалить навсегда»).
- Таблица `users` хранит только основные поля пользователя; настройки — в отдельной таблице профиля, группы и роли — в Authentik и токене.

## Стиль API (свои маршруты)
- Префикс `/api/v1/` — не пересекаться с маршрутами Agno. Роутер подключается `attach_api` к приложению из `agent_os.get_app()`, перед монтированием MCP; `base_app` не используется (ADR-002).
- Запросы и ответы — модели Pydantic. OpenAPI — контракт для фронтенда, TS-клиент генерируется из него.
- Ошибки — `application/problem+json` (RFC 9457), обработчики только для своих исключений; тело запроса проверяет сам маршрут, потому что ошибки проверки FastAPI идут через обработчик Agno. `401` отдаёт проверка токена Agno в своём формате.
- Время — UTC, ISO 8601. Идентификаторы — UUID.
- `Idempotency-Key` обязателен для утверждения и загрузки файлов.
- Каждый маршрут проекта проверяет доступ к проекту; маршрут без проверки не проходит ревью. Маршруты без проекта (`/api/v1/me`) работают только с записью владельца токена (`sub`), без идентификатора пользователя в адресе или теле.

## Методология
- SKILL.md и JSON-схемы шаблонов проверяются в CI: схемы валидны, ссылки между документами существуют.
- Изменения методологии ревьюит методист, не только разработчик.

## Запуск проверок
- формат/линт/типы: `./scripts/validate.sh` (тот же гейт в CI), автоформат `./scripts/format.sh`; `git diff --check`
- стенд: запускает, останавливает и сбрасывает только основная папка (`./scripts/dev.sh up|db|stop|reset-db`); из worktree остальные команды `dev.sh` пользуются работающим стендом и своими базами, `.env` worktree — ссылка на `.env` основной папки
- тесты: `./scripts/dev.sh test` — создаёт чистую тестовую базу в `agentos-db` (`ai_test`, в worktree `ai_test_<worktree>`), готовит её `init.sql`, применяет миграции и запускает `pytest` из `agno/tests/` под ролью `agentos`; моков базы нет
- миграции в разработке: `./scripts/dev.sh migrate` (на хосте, в базу рабочей копии: `ai`, в worktree `ai_dev_<worktree>`); новая миграция — `alembic revision` из `agno/` с осмысленным именем, проверка на чистой базе через `./scripts/dev.sh test`
- MCP без модели: `./scripts/mcp_check.sh`; поведение агента — `python -m evals`
- сборка: `docker compose up -d --build`; sandbox: `docker build --target sandbox --load -t agno-sandbox:local -f agno/Dockerfile .`

## Готово, когда
`./scripts/validate.sh`, `git diff --check` и `pytest` проходят; миграции применяются на чистой базе; изменения OpenAPI отражены в контракте для фронтенда; проверки и их ограничения записаны в `tmp/VERIFY.md` (static, deterministic, model, container, hosted — раздельно).
