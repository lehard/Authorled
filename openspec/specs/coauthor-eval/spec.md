# coauthor-eval Specification

## Purpose
Замер качества соавтора: настоящий агент `coauthor` отвечает на выборку синтетических просьб автора по демо-историям, а замер оценивает его действие и ответ по доменам и разделам. Нужен, чтобы решить, справляется ли один агент или пора возвращаться к оркестратору (спека `orchestrator`).

## Requirements

### Requirement: Наборы замера
У замера MUST быть два набора. `wide` — выборка id из рабочей части широкого набора экзамена маршрутизации (`agno/evals/routing/cases/wide-work.toml`); id из отложенной части экзамена MUST NOT в неё входить. `demo` — свои случаи по демо-историям в рабочей и отложенной частях без общих id и в части проверок наставника `checks`, у которой тоже нет общих id с ними. В `wide` и в частях `work` и `holdout` набора `demo` MUST быть случаи всех 12 доменов широкого состава и всех разделов; к части `checks` это правило не относится.

#### Scenario: Неизвестный id
- GIVEN в файле выборки есть id, которого нет в `wide-work.toml`
- WHEN запускается замер
- THEN замер MUST завершиться ошибкой, называющей id, до первого вызова модели

#### Scenario: Домен без случаев
- GIVEN в выборке нет ни одного случая, ожидающего домен `wide-help`
- WHEN запускается замер
- THEN замер MUST завершиться ошибкой, называющей домен, до первого вызова модели

#### Scenario: Отложенная часть без домена
- GIVEN в отложенной части `demo` нет ни одного случая домена `wide-research`
- WHEN запускается замер набора `demo` (любой части)
- THEN замер MUST завершиться ошибкой, называющей часть и домен, до первого вызова модели

#### Scenario: Часть проверок без всех доменов
- GIVEN в части `checks` все случаи ожидают только домен `wide-review`
- WHEN запускается замер `--set demo --part checks`
- THEN замер MUST идти без ошибки покрытия

### Requirement: Случаи по демо-историям
Каждый случай набора `demo` MUST называть историю, в которой идёт (`place`), ожидаемые домены, ожидаемое действие и ссылки на материалы этой истории, о которых он спрашивает: сцены по номеру, персонажей, локации, миры, заметки и документы по имени. Каждая ссылка MUST существовать в демо-истории случая (`web/src/data/demo.json`). Случай «такого нет» MUST помечать, чего нет в истории, и это MUST действительно отсутствовать в ней. Около 20 из 100 случаев — «такого нет».

#### Scenario: Ссылка на несуществующую сцену
- GIVEN случай `demo` ссылается на сцену 11, а в сценарии его истории 7 сцен
- WHEN запускается замер
- THEN замер MUST завершиться ошибкой, называющей случай и ссылку, до первого вызова модели

#### Scenario: «Такого нет» про существующее
- GIVEN случай «такого нет» помечает отсутствующим персонажа Ефим, а Ефим есть в карточках «Последнего парома»
- WHEN запускается замер
- THEN замер MUST завершиться ошибкой, называющей случай, до первого вызова модели

### Requirement: Запуск соавтора как из чата
Каждый случай MUST идти отдельным запуском настоящего соавтора: тот же промпт, инструменты, модель и hooks, что у зарегистрированного агента `coauthor`. Запуск MUST идти от имени пользователя замера, в беседе, привязанной к драфту его демо-истории, с контекстом открытой истории в том виде, в каком его прикладывает чат, и с историей беседы у случаев, где она есть. Беседы замера MUST NOT сохраняться в сессиях AgentOS.

#### Scenario: Продолжение беседы
- GIVEN случай раздела `continuation` с двумя прошлыми репликами
- WHEN соавтор отвечает
- THEN прошлые реплики MUST быть в истории его запуска, а ответ MUST оцениваться вместе с ними

#### Scenario: Нет пользователя замера
- GIVEN в базе нет пользователя замера или его демо-историй
- WHEN запускается замер
- THEN замер MUST завершиться ошибкой с командой, которая их создаёт, до первого вызова модели

### Requirement: Изменения не применяются
Замер MUST NOT подтверждать изменяющие инструменты соавтора. Предложенное действие MUST записываться с именем и аргументами, после чего замер MUST отвечать на паузу отказом, как автор, который отклонил действие, и продолжать запуск, чтобы соавтор дописал ответ на остальные просьбы сообщения (решение владельца 2026-11-08). После прогона история пользователя замера MUST остаться без изменений, кроме записей журнала расхода.

#### Scenario: Просьба создать заметку
- GIVEN случай «Добавь в заметки: у Лиды аллергия на рыбу»
- WHEN соавтор вызывает `create_story_note`
- THEN в отчёте MUST быть предложенное действие, замер MUST отклонить его и получить продолжение ответа, а заметок у истории MUST NOT стать больше

### Requirement: Оценка действия
Для каждого домена широкого состава замер MUST знать допустимые изменяющие инструменты соавтора. Случай MUST получать оценку «чужое изменение», если соавтор вызвал или предложил изменяющий инструмент, не допустимый ни для одного ожидаемого домена случая. Вызовы инструментов чтения MUST записываться, но MUST NOT считаться ошибкой.

#### Scenario: Изменение в вопросе о ремесле
- GIVEN случай ожидает только `wide-craft`
- WHEN соавтор предлагает `update_story_document`
- THEN случай MUST получить оценку «чужое изменение» с именем инструмента

### Requirement: Ожидаемое действие
В наборе `demo` действие MUST сверяться кодом с ожиданием случая: при ожидании `none` соавтор MUST NOT вызывать или предлагать изменяющих инструментов; при списке инструментов MUST быть вызван или предложен хотя бы один из них.

#### Scenario: Ожидаемое действие не сделано
- GIVEN случай `demo` ожидает `create_story_note`
- WHEN соавтор отвечает в чате, не вызвав и не предложив изменяющего инструмента
- THEN случай MUST получить провал действия «нет ожидаемого действия»

### Requirement: Обязательный факт
Случай набора `demo` MAY задавать обязательные факты ответа — группы допустимых вариантов. Ответ MUST содержать хотя бы один вариант каждой группы, без учёта регистра; варианты задаются основами слов, морфологию замер не разбирает. Проверка MUST идти кодом, без модели.

#### Scenario: Ответ без имени
- GIVEN случай ждёт факт с вариантами «Ефим»
- WHEN ответ соавтора не содержит «ефим» ни в какой форме с этой основой
- THEN случай MUST получить провал факта с названием группы

### Requirement: Оценка ответа судьёй
Ответ соавтора MUST оцениваться судьёй Agno `AgentAsJudgeEval` на модели `claude-sonnet` через LiteLLM-прокси. Судья MUST видеть контекст чата, сообщение и историю беседы, ответ, вызванные инструменты с результатами и предложенные действия. Если в промпте соавтора этого прогона была справка о сервисе (раздел «О сервисе «Соавтор»»), отчёт MUST хранить её текст, а судья MUST видеть её как то, что соавтор знает о сервисе; без справки этого блока у судьи MUST NOT быть.

#### Scenario: Сбой судьи
- GIVEN вызов судьи в одном случае завершился ошибкой
- WHEN замер продолжает прогон
- THEN случай MUST попасть в отчёт как «ошибка судьи» и MUST NOT считаться ни хорошим, ни плохим ответом; текст ошибки Agno пишет в свой лог («Evaluation failed») и в результат его не отдаёт

#### Scenario: Справка о сервисе
- GIVEN в промпте соавтора есть справка «меню «⋯» редактора: «Экспорт», «Печать…» (PDF)»
- WHEN соавтор на вопрос о PDF отвечает «Печать…» в меню «⋯»
- THEN судья MUST видеть эту справку и MUST NOT считать ответ выдумкой из-за того, что сведений о сервисе нет в материалах истории

### Requirement: Критерии судьи
Критерии судьи MUST требовать: ответ на каждую просьбу; опору на материалы без выдумки (честное «этого нет» — хорошо); изменения только предложенным действием, и только когда автор просит изменить, добавить, записать или оставить комментарий; удержание роли; короткий отказ не по теме; оговорку «стоит проверить» у фактов реального мира (владелец 2026-11-08); русский язык.

#### Scenario: Просьба не по теме выполнена
- GIVEN автор просит написать стихи коллеге
- WHEN соавтор пишет стихотворение вместо короткого отказа
- THEN судья MUST счесть ответ плохим

### Requirement: Ожидание случая для судьи
В наборе `demo` судья MUST получать ожидание случая отдельной строкой критериев, собранной кодом из полей случая: ожидаемое действие, обязательные факты и чего нет в истории.

#### Scenario: Случай «такого нет»
- GIVEN случай помечает отсутствующим персонажа Нина
- WHEN судья оценивает ответ
- THEN в его критериях MUST быть строка, что Нины в истории нет и хороший ответ говорит об этом и уточняет

### Requirement: Отчёт замера
После прогона замер MUST сохранить в `tmp/coauthor-eval/` отчёт: набор и часть; по каждому домену и разделу — долю случаев без «чужого изменения» и долю хороших ответов; список провалов с ответом, действием и причиной судьи; число ошибок запуска и ошибок судьи; вызовы модели, токены, рубли и задержку отдельно для соавтора и для судьи. Рядом MUST лежать файл для владельца с 30 случаями, по два-три на домен, где есть сообщение, ответ, действие и оценка судьи.

#### Scenario: Сбой соавтора в одном случае
- GIVEN запрос соавтора к модели в одном случае завершился ошибкой
- WHEN замер пишет отчёт
- THEN случай MUST быть в отчёте как «ошибка запуска» с текстом ошибки, а итог MUST показывать число таких случаев

### Requirement: Отчёт набора demo
Отчёт набора `demo` MUST ещё показывать по доменам и разделам долю верных действий, верных фактов и хороших случаев; хороший случай — пройдены действие, факт и судья. При повторах отчёт MUST хранить каждый повтор и показывать шум.

#### Scenario: Верный ответ без действия
- GIVEN судья счёл ответ хорошим, а ожидаемое действие не сделано
- WHEN пишется отчёт
- THEN случай MUST NOT считаться хорошим случаем

### Requirement: Повтор и сравнение
Прогон MUST уметь проходить каждый случай K раз (`--repeat K`). Шум прогона — случаи, чья итоговая оценка расходится между повторами. Команда сравнения двух отчётов одного набора и части MUST показывать разницу долей по доменам и разделам, случаи, ставшие хорошими и плохими, и шум обоих отчётов. Разница, не превышающая шума, MUST помечаться как шум, а не как улучшение или ухудшение (требование «Порог шума в сравнении»). Сравнение MUST идти без вызовов модели.

#### Scenario: Отчёты разных наборов
- GIVEN отчёт набора `wide` и отчёт части `demo` work
- WHEN запускается сравнение
- THEN команда MUST завершиться ошибкой, называющей наборы и части обоих отчётов

#### Scenario: Случай с разными оценками в повторах
- GIVEN случай хороший в первом повторе и плохой во втором
- WHEN пишется отчёт
- THEN случай MUST попасть в шум прогона и MUST NOT считаться ни стабильно хорошим, ни стабильно плохим

### Requirement: Порог шума в сравнении
Разница доли группы между двумя отчётами MUST считаться шумом, если в случаях она не больше половины числа случаев группы, шумных хотя бы в одном отчёте: шумный случай сдвигает долю группы не больше чем на полслучая.

#### Scenario: Порог шума
- GIVEN в группе разница между отчётами — один случай, а шумных хотя бы в одном отчёте — два
- WHEN запускается сравнение
- THEN разница MUST быть помечена как шум, а при одном шумном случае — как улучшение или ухудшение

### Requirement: Прогон замера
Команда `python -m evals.coauthor` MUST загружать `.env`, обращаться к моделям только через LiteLLM-прокси и требовать явного выбора набора (`--set wide|demo`, для `demo` — часть `--part work|holdout|checks`) и объёма: все случаи (`--all`) или первые N (`--sample N`). Замер тратит вызовы модели и MUST NOT запускаться из `validate.sh` или CI.

#### Scenario: Без цены модели
- GIVEN у `claude-sonnet` или `deepseek-fast` нет цены в `model_prices.toml`
- WHEN запускается замер
- THEN команда MUST завершиться ошибкой, называющей псевдоним, до первого вызова модели

### Requirement: Повторная оценка судьёй
Команда `python -m evals.coauthor rejudge <отчёт> --domain <домен>` MUST заново оценивать судьёй случаи отчёта, ожидающие этот домен, по сохранённым ответам и вызовам, без запусков соавтора. Остальные случаи MUST переноситься без изменений. Результат MUST сохраняться новым отчётом с пометкой, из какого отчёта и по какому домену он сделан; исходный отчёт MUST NOT меняться.

#### Scenario: Неизвестный домен
- GIVEN домен `wide-poetry`, которого нет в широком составе
- WHEN запускается `rejudge`
- THEN команда MUST завершиться ошибкой, называющей домен, до первого вызова модели

#### Scenario: Только случаи домена
- GIVEN отчёт рабочей части `demo` и домен `wide-help`
- WHEN `rejudge` заканчивается
- THEN в новом отчёте у случаев `wide-help` MUST быть новые оценки судьи, а у остальных — прежние

### Requirement: Случай с открытым текстом сценария
Случай набора `demo` MAY открывать текст сценария и выделять в нём сцену по номеру (`open`). Сцена с этим номером MUST существовать в драфте, который открывает история случая (`web/src/data/demo.json`). Контекст чата такого случая MUST быть тем, что прикладывает чат при открытом тексте сценария и выделенной сцене: содержимое драфта с метками элементов и выделенный фрагмент.

#### Scenario: Сцены нет
- GIVEN случай `open = { scene = 9 }`, а в сценарии его истории 7 сцен
- WHEN запускается замер
- THEN замер MUST завершиться ошибкой, называющей случай и сцену, до первого вызова модели

#### Scenario: Контекст выделения
- GIVEN случай «Где вода?» с `open = { scene = 6 }` в «Тихой воде»
- WHEN соавтор получает сообщение случая
- THEN контекст MUST содержать «Открыт документ: Текст сценария.», а после «Автор выделил фрагмент:» — абзацы сцены 6

### Requirement: Ожидание проверки для судьи
У случая с открытым текстом сценария судья MUST получать строку ожидания: одно–три места с точной цитатой из выделенной сцены, объяснение, почему место слабое, вопрос автору и нет переписанной сцены целиком.

#### Scenario: Строка ожидания
- GIVEN случай с `open = { scene = 6 }` и `action = "none"`
- WHEN собираются критерии судьи
- THEN среди строк ожидания MUST быть строка про одно–три места с точной цитатой из выделенной сцены, объяснение, вопрос автору и запрет переписывать сцену целиком
