# dev-workflow Specification

## Purpose
Процесс работы агентов-разработчиков в этом репозитории: одна длинная ветка `main`, отдельный worktree на сессию, полный цикл изменения OpenSpec в одной сессии и короткие хуки, которые напоминают об этом процессе.

## Requirements

### Requirement: Одна длинная ветка main
В репозитории MUST быть одна длинная ветка `main`; релизы MUST выходить только из неё. Основная папка репозитория MUST стоять на `main` и MUST NOT использоваться для правок и коммитов. Каждая сессия агента MUST работать в своём worktree под `.claude/worktrees/`, созданном от `origin/main`, в ветке с префиксом `claude/`, и MUST вливать работу в `main` только через PR.

#### Scenario: Новая сессия на изменение
- GIVEN владелец начинает работу над изменением OpenSpec
- WHEN сессия создаётся
- THEN она MUST работать в своём worktree от `origin/main` в ветке `claude/<имя>` и MUST NOT править файлы основной папки

#### Scenario: Работа другой сессии
- GIVEN в worktree или основной папке есть файлы без коммита, которые сделала не эта сессия
- WHEN сессия коммитит свою работу
- THEN она MUST коммитить только свои файлы по путям и MUST NOT откатывать, прятать или коммитить чужие

### Requirement: Изменение доводит одна сессия
Одно изменение OpenSpec MUST проходить apply, verify, archive и слияние в одной ветке и одном PR. Отдельные ветки и PR только для verify или archive MUST NOT создаваться. Проверка на сервере после релиза MUST идти отдельным PR от `origin/main`, потому что выполнима только после релиза.

#### Scenario: Архив в той же ветке
- GIVEN сессия выполнила все задачи изменения в ветке `claude/<имя>`
- WHEN изменение архивируется
- THEN архив и синхронизация спек MUST попасть в тот же PR, без ветки `claude/<имя>-archive`

#### Scenario: Проверка на сервере после релиза
- GIVEN изменение влито и выпущено релизом
- WHEN записывается проверка на сервере
- THEN она MUST идти маленьким отдельным PR от свежего `origin/main`

### Requirement: Verify и archive без команды владельца
Когда все задачи `tasks.md` изменения отмечены, сессия MUST сама запустить verify. Если у verify нет замечаний уровня CRITICAL, сессия MUST сама заархивировать изменение с синхронизацией спек. Propose, update и начало apply MUST по-прежнему запускать только владелец.

#### Scenario: Verify без критичных замечаний
- GIVEN все задачи изменения отмечены
- WHEN verify не нашёл замечаний CRITICAL
- THEN сессия MUST заархивировать изменение без отдельной команды владельца и назвать в отчёте замечания WARNING и SUGGESTION

#### Scenario: Критичное замечание
- GIVEN все задачи изменения отмечены
- WHEN verify нашёл замечание CRITICAL
- THEN сессия MUST остановиться, показать замечания владельцу и MUST NOT архивировать и вливать изменение

### Requirement: Слияние PR сессией
После архива сессия MUST запустить `./scripts/validate.sh`, `git diff --check` и тесты, которых требует изменение, закоммитить свои файлы, открыть PR в `main` и влить его. Если хоть одна проверка падает или ветка конфликтует с `origin/main`, сессия MUST остановиться и сообщить владельцу, MUST NOT вливать PR. Релиз сессия MUST NOT создавать без просьбы владельца.

#### Scenario: Проверки зелёные
- GIVEN изменение заархивировано, проверки прошли
- WHEN сессия заканчивает работу
- THEN PR MUST быть влит в `main`, а отчёт MUST назвать PR и выполненные проверки

#### Scenario: Проверка упала
- GIVEN `./scripts/validate.sh` вернул ненулевой код
- WHEN сессия заканчивает работу
- THEN PR MUST NOT быть влит, а сессия MUST назвать упавшую проверку

#### Scenario: Конфликт с main
- GIVEN после обновления от `origin/main` в ветке конфликт
- WHEN сессия готовит слияние
- THEN она MUST остановиться и спросить владельца, MUST NOT разрешать конфликт в чужих спеках по своему усмотрению

### Requirement: Хук при старте сессии
При старте сессии Claude Code в репозитории хук MUST предупредить, если сессия открыта в основной папке, а не в worktree, или основная папка стоит не на `main`. Хук MUST NOT менять ветки, файлы и worktree и MUST NOT обращаться к сети.

#### Scenario: Сессия в основной папке
- GIVEN сессия открыта в основной папке репозитория
- WHEN она стартует
- THEN сессия MUST получить предупреждение работать в worktree

#### Scenario: Сессия в worktree
- GIVEN сессия открыта в worktree под `.claude/worktrees/`, основная папка на `main`
- WHEN она стартует
- THEN хук MUST ничего не выводить

### Requirement: Хук при остановке сессии
При остановке хода хук MUST найти изменения OpenSpec, которые эта ветка добавила или изменила относительно `origin/main` и которые не в архиве. Если у такого изменения все задачи отмечены, хук MUST один раз вернуть сессии напоминание закончить verify и archive. Повторно в том же ходе (флаг `stop_hook_active`) хук MUST NOT блокировать остановку. Хук MUST NOT обращаться к сети и MUST NOT менять файлы.

#### Scenario: Законченное изменение без архива
- GIVEN ветка добавила изменение `openspec/changes/<имя>/`, все его задачи отмечены, архива нет
- WHEN сессия заканчивает ход
- THEN хук MUST вернуть напоминание с именем изменения

#### Scenario: Повторная остановка
- GIVEN хук уже вернул напоминание в этом ходе
- WHEN сессия снова заканчивает ход с `stop_hook_active`
- THEN хук MUST разрешить остановку

#### Scenario: Чужое изменение в main
- GIVEN в `openspec/changes/` есть незаархивированное изменение, которое эта ветка не трогала
- WHEN сессия заканчивает ход
- THEN хук MUST его не учитывать

#### Scenario: Задачи не закончены
- GIVEN у изменения ветки есть неотмеченная задача
- WHEN сессия заканчивает ход
- THEN хук MUST разрешить остановку без напоминания

#### Scenario: Сломанное состояние git
- GIVEN в worktree нет `origin/main` или `git` вернул ошибку
- WHEN хук выполняется
- THEN хук MUST вывести ошибку с причиной и MUST NOT молча считать, что изменений нет
