# Бизнес-интент: продление входа без гонки refresh token и выход на `/login` при закончившейся сессии

Статус: решения согласованы с владельцем 2026-11-01, change `token-refresh` реализован и архивирован 2026-11-01 (`openspec/changes/archive/2026-11-01-token-refresh/`); Safari и production не проверялись. Владелец: lehard. Обновлено: 2026-11-01.
Рамки: ADR-001, `openspec/context/05-security-and-compliance.md`, `openspec/context/07-anti-patterns.md` (п. 26 — без fallback), мастер-спеки `auth` («Вход фронтенда», «Конфигурация из blueprints») и `web/workspace` («Вход»); Authentik `2026.8.5`, `oidc-client-ts` `3.5.0`.

## Why

Владелец не смог войти 2026-11-01. Приложение показывало «Не удалось проверить вход» с ответом Authentik «The provided authorization grant or refresh token is invalid…», и «Попробовать снова» не помогало.

Лог Authentik: в 11:50:19 refresh token обменян успешно (200). Через 2 секунды тот же, уже использованный токен пришёл ещё раз и получил отказ с событием «Revoked refresh token was used» (подозрительный запрос). Дальше каждая попытка снова отправляла отозванный токен.

Как устроено у Authentik и у библиотеки входа:
- **Authentik** при каждом продлении выдаёт новый refresh token, а старый сразу отзывает (`refresh_token_threshold = seconds=0` по умолчанию). Повторное использование старого — `invalid_grant` и событие в журнале: так Authentik ловит украденные токены. Новый токен при этом остаётся рабочим.
- **`oidc-client-ts`** рассчитан на то, что продлевает сама библиотека, одним таймером (`automaticSilentRenew`), а приложение только читает токен. Одновременные вызовы `signinSilent()` библиотека не объединяет.

Где наши дыры:
1. `activeUser()` (`web/src/auth/userManager.ts`) сам вызывает `signinSilent()`, если токен истёк. Его зовут проверка входа, экран входа, меню и `/settings` (`/api/v1/me`), чат — и параллельно работает таймер библиотеки. После сна вкладки (Safari усыпляет фоновые) несколько вызовов отправляют один и тот же refresh token: первый получает новый, остальные — отказ. После change `user-cabinet` таких вызовов стало больше. То же случается с дублированной вкладкой: у неё копия токенов, и после продления в одной вкладке копия в другой мертва.
2. Отказ Authentik `invalid_grant` приложение показывает как сбой («Не удалось проверить вход») и по «Попробовать снова» отправляет тот же мёртвый токен — выхода из круга нет. Спека `web/workspace` («Вход») требует открывать `/login`, когда действующей сессии нет; сейчас код с ней расходится.

## What Changes

1. **Refresh token уходит в Authentik ровно один раз.** Приложение не продлевает токен само: продлевает только `oidc-client-ts`. Если токен истёк, все вызовы во вкладке ждут одного общего продления и получают его результат. Настройку Authentik не меняем: новый refresh token на каждое продление и обнаружение повторного использования остаются, как задумано в Authentik.
2. **Закончившаяся сессия ведёт на `/login`, а не на экран ошибки.** Если Authentik отказал в продлении (`invalid_grant`: токен отозван, истёк или использован повторно), токены вкладки удаляются, и открывается `/login` с возвратом на текущий адрес.
   - Если сессия самого Authentik ещё жива, `/login` по спеке берёт токены без формы — человек продолжает работу без кода.
   - Если сессии нет — обычный вход: почта и код.
3. **Экран «Не удалось проверить вход» остаётся только для настоящих сбоев:** Authentik недоступен, нет сети, ответ 5xx. Для них «Попробовать снова» по-прежнему повторяет запрос.
4. **Запросы к API во время отказа** (меню, `/settings`, чат) не показывают свою ошибку поверх: они ведут туда же, на `/login`.

## Scope

- `web/src/auth/userManager.ts`: одно общее продление на вкладку, без собственных вызовов `signinSilent()` из разных мест; различение отказа Authentik (`invalid_grant`) и сбоя связи или сервера.
- `web/src/auth/authProvider.ts` (`check`, `onError`), `web/src/app/RefineRoot.tsx` (`RequireAuth`): закончившаяся сессия → `/login?returnTo=…`, сбой → прежний экран с «Попробовать снова».
- Вызовы токена в `web/src/account/meApi.ts`, `web/src/screens/project/chat/api.ts`, `web/src/auth/LoginScreen.tsx` — через общий путь.
- Мастер-спеки: `web/workspace` («Вход» — продление и закончившаяся сессия), `auth` («Вход фронтенда» — refresh token используется один раз, обнаружение повторного использования Authentik остаётся включённым).
- Проверка: Playwright с ускоренным истечением токена и Mailpit; журнал событий Authentik; запись в `tmp/VERIFY.md`.

## Non-goals

- Изменение `refresh_token_threshold`, сроков жизни токенов (`access_token_validity`, `refresh_token_validity`) и других настроек провайдера в blueprints.
- Привязка токенов к браузеру (DPoP): Authentik и `oidc-client-ts` её поддерживают, это отдельное решение по безопасности.
- Общий вход между вкладками (перенос токенов из `sessionStorage` в `localStorage`, синхронизация вкладок): каждая вкладка держит свои токены, как сейчас.
- Продление на бэкенде или промежуточный бэкенд — запрещены спекой `auth`.
- Изменение экранов входа, кроме того, куда ведёт закончившаяся сессия.

## Constraints (из контекст-пака)

- Пользователи, вход и токены — только Authentik (ADR-001); фронтенд получает токены по OIDC без промежуточного бэкенда.
- Без fallback: отказ Authentik не маскируется повтором с тем же токеном или подстановкой старого; сбой связи — явная ошибка с причиной; отказ в продлении — явный выход на `/login`.
- Тексты на русском, экраны по дизайн-системе «Кабинета».
- Защиту Authentik от повторного использования refresh token не ослабляем.

## Acceptance criteria

- Токен истёк, вкладка просыпается, и одновременно запрашивают токен проверка входа, меню, `/settings` и чат: в Authentik ровно один обмен refresh token, ни одного события «Revoked refresh token was used», экран работает без перезагрузки.
- Дублированная вкладка после продления в соседней: при живой сессии Authentik — снова внутри без формы; без сессии — `/login` с почтой. Экрана «Не удалось проверить вход» нет.
- Refresh token отозван или истёк (например, после выхода в другой вкладке или отзыва в Authentik): `/login`, после входа — возврат на открытый адрес.
- Authentik остановлен: «Не удалось проверить вход» с причиной; после запуска Authentik «Попробовать снова» пускает внутрь.
- `./scripts/validate.sh` проходит.

## Risks

- **Сон вкладки дольше жизни access token (10 минут).** Таймер библиотеки не срабатывает во сне; при пробуждении продление идёт через общий путь. Это главный сценарий, который нужно проверить в Safari, а не только в Chromium.
- **Различение отказа и сбоя.** Если сбой связи примем за отказ, человек попадёт на `/login` без причины; если отказ за сбой — вернётся нынешняя ловушка. Различать по ответу Authentik (`invalid_grant` в теле ответа `400`), не по тексту.
- **Журнал Authentik.** Пока исправление не выкачено, повторные обмены будут давать события «подозрительный запрос»; после — их появление означает реальную проблему, и это стоит проверять.

## Open Questions

- Решено 2026-11-01: следуем устройству Authentik и `oidc-client-ts` — новый refresh token на каждое продление, продлевает только библиотека, отказ ведёт на `/login`.
- Нужно ли показывать на `/login` короткое пояснение «Сессия закончилась, войдите снова», когда формы всё же не избежать, — решить при проектировании экрана в design.
