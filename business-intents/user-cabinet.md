# Бизнес-интент: личный кабинет, этап 1 — страница настроек, `GET /me` и таблица профиля

Статус: решения согласованы с владельцем 2026-11-01, change `user-cabinet` реализован и архивирован 2026-11-01 (`openspec/changes/archive/2026-11-01-user-cabinet/`); production не проверялся. Владелец: lehard. Обновлено: 2026-11-01.
Рамки: ADR-001, ADR-002, ADR-006, `openspec/context/03-architecture.md`, `openspec/context/04-engineering-standards.md` («Миграции»), `openspec/context/05-security-and-compliance.md` (ПДн — только почта и имя, 152-ФЗ), `openspec/context/07-anti-patterns.md`, мастер-спеки `core/database` («Таблица пользователей»), `auth` («Контракт токена»), `web/workspace` («Вход», «Адреса экранов»), `web/design-system`; макет v1 `openspec/context/_raw/design/kabinet/` (экран `#settings`), макет v2 `openspec/context/_raw/design/kabinet-starc/` (меню аккаунта).

## Why

У пользователя нет своего места в продукте: в меню пользователя только имя, почта и «Выйти». Имя нельзя исправить после регистрации, тему выбрать негде — она хранится только в браузере (`authorled.theme`) и переключателя в интерфейсе нет. Запись в `authorled.users` есть только как таблица: её никто не создаёт, потому что `GET /me` отложен из интента `core-users-table` «в следующий интент».

Макет v1 содержит полную страницу настроек (внешний вид, редактор, соавтор, вход и безопасность, данные, аккаунт), макет v2 скрывает настройки на время MVP (`FLAGS.settings = false`, решение 2026-10-31). Кабинет открывает настройки, но только с тем, что уже работает; остальное — следующими этапами, когда для них появится основа.

## What Changes

1. **Страница `/settings`** по раскладке v1: лист «Кабинета», заголовок «Настройки», разделы слева (на узком экране — сверху), «Назад». Вход — пункт «Настройки» в меню пользователя (как в меню аккаунта v2).
2. **Раздел «Профиль»:**
   - имя — можно изменить; пустое имя — ошибка;
   - почта для входа — только чтение (смена почты — этап «Вход и безопасность»);
   - «Выйти» — как в меню пользователя.
3. **Раздел «Внешний вид»:** тема плитками-превью из v1 — «Утро», «Бумага», «Вечер у лампы» и «Как в системе». Выбор применяется сразу и сохраняется в аккаунте: на другом устройстве после входа та же тема. Браузер хранит тему только для первой отрисовки до ответа сервера; после ответа побеждает тема аккаунта.
4. **`GET /me`** (`/api/v1/me`) — первый свой маршрут (ADR-002), роутером в приложении AgentOS, без LLM:
   - после входа фронтенд вызывает его один раз; запрос создаёт запись в `authorled.users`, если её нет, иначе обновляет почту и `last_seen_at`;
   - имя берётся из токена только при создании записи; дальше главное — `users.display_name`, токен его не перезаписывает;
   - ответ: id, почта, имя и настройки профиля;
   - удалённый мягко аккаунт (`deleted_at`) получает явную ошибку, запись не воскрешается.
5. **`PATCH /me`** — меняет имя и тему; неизвестная тема или пустое имя — `422` с названием поля.
6. **Таблица профиля `authorled.user_settings`:** `user_id` (первичный ключ, ссылка на `users.id`), `theme` (пусто — «как в системе», иначе `light`, `sepia`, `dark`), `updated_at`. Явные колонки, не JSON: каждая следующая настройка добавляется своей миграцией и проверяется базой. Строка профиля создаётся вместе с записью пользователя.
7. **Меню пользователя** показывает имя из `/me`, а не из токена: после смены имени в кабинете меню показывает новое.
8. **Контракт токена:** в Access Token добавляются claims `email` и `name` (решено в интенте `core-users-table`); бэкенд берёт их только для записи пользователя, не для решений о доступе.

## Scope

- `agno/core/`: таблица `user_settings`, операции «получить или создать пользователя», «изменить имя и тему»; миграция `0002_user_settings`.
- `agno/app/`: маршруты `GET /api/v1/me` и `PATCH /api/v1/me` роутером в приложении AgentOS, пользователь — из `Principal` и claims токена (чтение claims — только в `agno/app/auth/`).
- `auth/blueprints/`: claims `email` и `name` в Access Token; `./scripts/check_auth_boundary.sh` продолжает проходить.
- `web/`: маршрут `/settings`, разделы «Профиль» и «Внешний вид», пункт «Настройки» в меню пользователя, загрузка `/me` после входа, тема из аккаунта.
- Мастер-спеки: `core/database` (таблица профиля), `auth` («Контракт токена»), `web/workspace` («Адреса экранов», кабинет), `web/design-system` (откуда берётся тема), новое требование к API `/me` (`api`).
- Тесты: pytest ядра на чистой базе (создание, повтор без дубля, имя не перезаписывается токеном, удалённый аккаунт, неверная тема); проверка страницы в трёх темах и на 375 px; запись в `tmp/VERIFY.md`.

## Non-goals

Следующие этапы кабинета — отдельные интенты:

- **Соавтор** (v1: «Сколько замечать», обращение на «вы» или «ты», язык) — когда промпт агента начнёт читать эти настройки; хранить настройки, которые ни на что не влияют, не будем.
- **Вход и безопасность** (смена почты через код, пароль — задать, сменить, убрать; где выполнен вход; «Выйти на всех других») — потоки Authentik, отдельный интент.
- **Данные** (выгрузить всё архивом, удалить аккаунт со словом «удалить») — когда истории будут храниться в базе, а не в данных примера.
- **Письмо** (цель слов, кольцо, статистика) — после хранения сцен.

Не берём из v1 и сейчас не планируем: шрифт, размер текста и ширину листа, сценарный шаблон, проверку орфографии, язык, имя автора для титульного листа (титул у каждой истории свой). Обещание «тексты не используются для обучения моделей» не показываем без отдельного решения владельца (тексты идут во внешнюю модель).

Не меняем имя в Authentik: бэкенд не получает права администратора Authentik ради имени.

## Constraints (из контекст-пака)

- Пользователи, вход и роли — Authentik; бэкенд своих паролей не хранит (ADR-001). Группы и роли в таблицы ядра не копируются.
- Свои HTTP-маршруты — только действия продукта без LLM, через `base_app` (ADR-002).
- Схема `authorled`: миграции Alembic только вперёд, одна голова; Agno и Authentik не трогаем.
- ПДн — только почта и имя, хранятся в РФ (152-ФЗ).
- Экраны — по дизайн-системе «Кабинета», цвета только из токенов, тексты на русском.
- Без fallback: нет claim `email` или `name` при создании записи — явная ошибка с названием claim; ответ `/me` не пришёл — экран ошибки, а не интерфейс со старым именем; неизвестная тема в ответе — ошибка.

## Acceptance criteria

- Первый вход нового пользователя создаёт одну запись в `authorled.users` и одну в `authorled.user_settings`; повторные входы не создают дублей и обновляют `last_seen_at`.
- Меню пользователя → «Настройки» открывает `/settings`; на 375 px страница без горизонтальной прокрутки.
- Смена имени сохраняется, видна в меню сразу и после перезагрузки; пустое имя — ошибка на русском.
- Новое имя не возвращается к имени из Authentik при следующем входе.
- Выбор темы применяется сразу; после входа в другом браузере тема та же; «Как в системе» следует настройке системы.
- Удалённый мягко аккаунт не получает данных `/me` и не создаётся заново.
- Запрос без токена или с чужим токеном — `401`.
- pytest ядра и `./scripts/validate.sh` проходят.

## Risks

- **Мигание темы при входе на новом устройстве:** до ответа `/me` браузер показывает системную или сохранённую тему. Допустимо: одна смена при первом входе.
- **Имя расходится с Authentik:** в письмах Authentik и в его интерфейсе остаётся имя с регистрации. Для пользователя письма содержат только код; заметно лишь администратору.
- **Claims в Access Token:** почта и имя попадают в каждый токен. Это ПДн уже известные бэкенду; длина токена растёт незначительно.
- **Данные примера:** истории остаются в `fixtures`, а `/me` ходит в настоящий API — первый экран, которому нужен запущенный API. Локальный запуск фронтенда без API покажет ошибку на `/settings` и в меню.
