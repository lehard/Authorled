# Бизнес-интент: деплой проверяет, что Caddy может прочитать сертификат УЦ админки

Статус: владелец попросил интент 2026-11-10 после сбоя выкладки `v0.3.13` и запустил по нему `/opsx:propose` и `/opsx:apply`; change `admin-ca-permissions` реализован, проверен и архивирован 2026-11-10 (`openspec/changes/archive/2026-11-10-admin-ca-permissions/`); выкладка с новой проверкой — следующим релизом. Владелец: lehard. Обновлено: 2026-11-10.
Рамки: мастер-спека `runtime` («Обратный прокси», сценарий «Нет сертификата удостоверяющего центра»); архив `2026-11-09-admin-mtls`; `deploy/deploy.sh`, README (настройка сервера и «Admin interface»), скилл `deploy-platform`, `scripts/admin_cert.sh`.

## Why

Релиз `v0.3.13` (2026-11-10) выложил код и контейнеры, а шаг «Deploy on the server» упал на последнем действии, `systemctl reload caddy`. Caddy не прочитал `/etc/authorled/admin-client-ca.pem`: `permission denied`. Сам файл открыт на чтение (`root:root 0644`, как велят README и скилл), но каталог `/etc/authorled` по README создаётся как `root:deploy 0750`, а Caddy работает под пользователем `caddy`, который не входит в группу `deploy` и не может войти в каталог.

Проверка деплоя смотрит только, что файл существует (`[[ -f … ]]` в `deploy.sh`), и запускается под пользователем `deploy`, которому каталог открыт. `caddy validate` в деплое тоже проходит. Поэтому сбой виден только после смены кода и контейнеров: сервер оказался на новом коде со старой конфигурацией Caddy, `admin.soavtor.app` не отвечал, проверки адресов, сайта и админки пропустились.

Сервер починен вручную с согласия владельца 2026-11-10: `chmod 751 /etc/authorled`, `systemctl reload caddy`, повторный запуск задания деплоя прошёл все шаги. В репозитории ошибка осталась: новый сервер по README повторит тот же сбой.

## What Changes

1. **Проверка до изменений.** `deploy/deploy.sh` в предварительных проверках (там же, где проверка наличия файла) завершается ошибкой, если пользователь вне группы `deploy` не может прочитать сертификат: у каталога `/etc/authorled` нет права `x` для остальных или у файла нет права `r` для остальных. Сообщение называет файл и команду исправления (`chmod 751 /etc/authorled`, `chmod 644 /etc/authorled/admin-client-ca.pem`). Проверка по правам (`stat`), без `sudo`: у `deploy` есть только `sudo systemctl reload caddy`.
2. **Права каталога в README.** Настройка сервера создаёт `/etc/authorled` с `chmod 751` вместо `750`, с пояснением: Caddy читает оттуда сертификат УЦ, а `authorled.env` и его копии закрыты своими правами `640`.
3. **Документы о сертификате.** README («Admin interface», «Renewal and loss»), скилл `deploy-platform` (шаг 2 включения админки) и подсказка `scripts/admin_cert.sh` говорят, что Caddy читает файл под своим пользователем и каталогу нужен `751`.
4. **Спека.** В `runtime` — сценарий: сертификат есть, но Caddy его не прочитает → деплой завершается ошибкой с именем файла до запуска контейнеров.

Путь файла не меняется: на сервере всё уже настроено, перенос в `/etc/caddy/` потребовал бы правки сервера, Caddyfile и документов без выгоды.

## Scope

- `deploy/deploy.sh`: проверка прав каталога и файла сертификата.
- `README.md`: команды настройки `/etc/authorled` и абзацы о сертификате.
- `.agents/skills/deploy-platform/SKILL.md`, `scripts/admin_cert.sh` (текст подсказки).
- Мастер-спека `runtime`: сценарий проверки прав.
- Проверка: `deploy.sh` на копии с подменёнными путями (каталог `750`, файл `600`, верные права) и `validate.sh`; на сервере — следующий релиз.

## Non-goals

- Перенос сертификата в другой каталог или смена пути в `Caddyfile`.
- Добавление `caddy` в группу `deploy`: тогда Caddy читал бы `authorled.env` с секретами.
- Перестановка шагов деплоя (перезагрузка Caddy до смены кода) и проверка конфигурации от имени `caddy` через `sudo`.
- Изменения на сервере: они уже сделаны 2026-11-10.

## Constraints (из контекст-пака)

- Без fallback: нет прав — деплой останавливается с понятной ошибкой до изменений, а не чинит права сам.
- У пользователя `deploy` нет `sudo`, кроме `systemctl reload caddy`; проверка не должна требовать большего.
- Секреты в `/etc/authorled/authorled.env` остаются недоступными пользователю `caddy` и остальным.

## Acceptance criteria

- Каталог `0750` или файл без права чтения для остальных: `deploy.sh` завершается кодом 1 с именем файла и командой исправления до копии базы и смены кода.
- Каталог `0751` и файл `0644`: проверка проходит, как сейчас на сервере.
- По README новый сервер настраивается так, что первая выкладка с админкой проходит без ручной правки прав.
- Следующий релиз проходит все шаги деплоя.

## Risks

- `751` открывает другим пользователям сервера проход в каталог (без списка файлов). Файлы с секретами закрыты правами `640`; новый файл в каталоге надо создавать с правами не шире `640`, если он не для Caddy. Это пишется в README рядом с командой.
