# Бизнес-интент: деплой на сервер по релизу GitHub

Статус: решения согласованы с владельцем 2026-11-06; OpenSpec change `deploy-on-release` создан 2026-11-06 (`openspec/changes/deploy-on-release/`), код написан, работы на сервере и первый релиз впереди. Владелец: lehard. Обновлено: 2026-11-06.
Рамки: `README.md` («Deploy in production», «Module auth»), `.agents/skills/deploy-platform/SKILL.md`, мастер-спека `auth` («Вход фронтенда»), `compose.prod.yaml`.

## Why

Продукт выходит на тестирование на своём сервере. Выкладка должна идти сама из GitHub, без ручных шагов на сервере, но только когда владелец решил выпустить версию: не каждый пуш в `main` готов к показу (владелец, 2026-11-06).

Сейчас в репозитории нет ни деплоя, ни описания того, как выкладывать фронтенд и какой обратный прокси ему нужен.

## What Changes

1. **Запуск по релизу.** Workflow GitHub Actions запускается, когда публикуется релиз с тегом на коммите из `main`, например `v0.1.0`. Обычные пуши в `main` на сервер не уходят. Тег не из `main` останавливает деплой с ошибкой.
2. **Проверка и сборка.** Для тега проходит та же проверка, что в `validate.yml`. Фронтенд собирается в GitHub Actions с настройками продакшена и отправляется на сервер. Node на сервере не нужен.
3. **Доступ к серверу.** Workflow подключается по SSH отдельным пользователем `deploy`. Его ключ, адрес сервера и отпечаток ключа хоста лежат в секретах GitHub. Одновременно идёт только один деплой.
4. **Шаги на сервере.** Резервная копия базы, затем переключение кода на тег релиза и `docker compose -f compose.yaml -f compose.prod.yaml up -d --build`. Настройки берутся из файла на сервере, вне репозитория. Хранятся последние 10 копий базы.
5. **Обратный прокси в репозитории.** Настройка Caddy хранится в репозитории и обновляется при деплое. Домен продукта отдаёт фронтенд, ведёт `/os/` на API без этого префикса, а `/api/v3/flows/executor/`, `/flows/-/cancel/` и `/application/o/revoke/` на Authentik. Домен Authentik ведёт на Authentik.
6. **Проверка после деплоя.** Публичный `/health` отвечает успехом, а `/agents` без токена отказывает. Если проверка не прошла, запуск в GitHub становится красным. Автоматического отката нет.
7. **Откат вручную.** Запуск того же workflow вручную с тегом прошлого релиза. Если у нового релиза были миграции, база дополнительно восстанавливается из копии.
8. **Доверенный прокси Authentik.** `AUTHENTIK_LISTEN__TRUSTED_PROXY_CIDRS` передаётся в контейнеры Authentik: README велит её задать, а `auth/compose.yaml` её не передаёт.
9. **Чистые данные.** Деплой не загружает демо-контент и не создаёт пользователей разработки. Новые пользователи начинают с пустого списка историй (владелец, 2026-11-06).
10. **Документация.** README описывает выпуск релиза, откат, настройки сервера и выкладку фронтенда.

## Scope

- `.github/workflows/`: новый workflow деплоя.
- Скрипт деплоя и настройка Caddy в репозитории.
- `auth/compose.yaml`, `compose.prod.yaml`: передача настройки доверенного прокси.
- `README.md`, `.agents/skills/deploy-platform/SKILL.md`, `example.env`.
- На сервере разово: пользователь `deploy`, каталоги, файл настроек. Настройки GitHub: секреты и переменные сборки.

## Non-goals

- Деплой на каждый пуш, стенд staging, несколько серверов.
- Деплой без простоя.
- Автоматический откат.
- Отдельный ручной путь первого деплоя: первая выкладка идёт первым релизом.
- Мониторинг, алерты, копии базы вне сервера.
- Готовые образы в реестре: образы собираются на сервере.

## Constraints (из контекст-пака)

- Один экземпляр API, постоянный PostgreSQL, проверка токенов включена, `RUNTIME_ENV=dev` на сервере запрещён.
- Миграции только вперёд, поэтому копия базы делается до `up`. Если копия не удалась, деплой останавливается.
- Нет запасных путей: отсутствующая настройка, секрет или сбой шага останавливают деплой с понятной ошибкой.
- Секреты не попадают в логи Actions и в репозиторий. Репозиторий публичный: адрес сервера, почты пользователей и значения настроек в него не коммитятся.
- Порты контейнеров остаются на loopback, наружу смотрит только Caddy.
- Сборка продакшена не содержит быстрых кнопок входа и пароля пользователей разработки.

## Acceptance criteria

- Публикация релиза с тегом из `main` выкладывает эту версию на сервер без действий на сервере.
- Пуш в `main` без релиза сервер не меняет.
- Релиз с тегом не из `main` останавливается с ошибкой, сервер не меняется.
- Перед `up` появляется новая копия базы; сбой копии останавливает деплой.
- Сайт открывается по HTTPS на домене продукта, вход проходит через свои экраны, чат с соавтором работает.
- Публичный `/health` успешен, `/agents` без токена отказывает.
- Сбой проверки делает запуск красным.
- Ручной запуск с тегом прошлого релиза возвращает эту версию.
- После первого релиза на сервере нет демо-историй и пользователей разработки.
- В собранном фронтенде нет кнопок «Войти как Сценарист» и «Войти как Редактор».
- `./scripts/validate.sh` проходит.

## Risks

- **Сила ключа деплоя.** Пользователь в группе `docker` почти равен root. Ключ хранится только в секретах GitHub, и публиковать релизы может только владелец.
- **Публичный репозиторий.** Workflow не должен запускаться из чужих форков и pull request.
- **Простой.** На время пересборки сайт может быть недоступен. Для тестирования это приемлемо.
- **Место на диске.** Образы, кэш сборки и копии базы растут, нужна очистка старого кэша при деплое.
- **Откат с миграциями.** Восстановление из копии теряет данные, созданные после неё.

## Open Questions

- Работает ли вход MCP для внешних чат-приложений с `AGENTOS_URL`, в котором есть путь `/os`. Проверяется на первом деплое. Если нет, API получит отдельный поддомен.
- SMTP для кодов входа и открытый порт 587 владелец готовит отдельно. Без них стек не стартует.
