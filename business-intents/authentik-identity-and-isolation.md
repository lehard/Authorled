# Бизнес-интент: модуль авторизации `auth` — полный Authentik внутри проекта, проверка JWT и изоляция данных авторов

Статус: change `auth-module` предложен 2026-10-26 (`openspec/changes/auth-module/`), ждёт согласования перед `/opsx:apply`. Имя change — `auth-module` (заменяет `authentik-jwt` из `openspec/TODO.md`; при создании change обновить строку в TODO). Владелец: lehard. Обновлено: 2026-10-26.
Рамки: `openspec/context/ADR/ADR-001-three-services.md` (уже обновлён под модуль `auth`), `openspec/context/03-architecture.md`, `openspec/context/05-security-and-compliance.md`, ADR-002.

## Why

Данные авторов — критически важный актив. Сценарист А не должен иметь технической возможности увидеть или изменить проект сценариста Б.

Agno не хранит пользователей, пароли и роли, поэтому нужен доверенный Identity Provider. Нужен полный функционал Authentik, а не урезанный: свой интерфейс входа, профиль, сброс пароля, 2FA/MFA, админка, группы, потоки, сервисные учётные записи.

Проект строится как модульный монолит. Authentik нельзя встроить в процесс приложения: это самостоятельный продукт из сервера, worker и PostgreSQL. Поэтому авторизация становится модулем проекта на уровне репозитория и деплоя: код, конфигурация и релиз лежат в этом репозитории, а работает модуль отдельными процессами. Остальные модули не знают ни про Authentik, ни про JWT и работают только с контрактом модуля.

## What Changes

Модуль `auth` состоит из двух частей и одного контракта.

1. **Деплой-часть (`modules/auth/`)** — Authentik целиком, всё как код:
   - фрагмент compose: контейнеры сервера и worker Authentik с закреплённой версией образа;
   - blueprints Authentik: группы (`screenwriters`, `editors`, `admins`), OIDC-приложение и провайдер для фронтенда, потоки входа с 2FA/MFA, сервисные учётные записи плагинов. Ручная настройка через UI не является источником истины;
   - оформление под продукт (бренд, тема страниц входа и профиля);
   - инициализация БД: схема `authentik` и отдельная роль (см. «Хранение»).
2. **Кодовая часть (`app/auth/`)** — тонкий адаптер на стороне Agno:
   - настройка проверки JWT Authentik в AgentOS (`authorization=True` в `prd`): ключи, `sub` как `user_id`, источник scopes, `iss` и `aud`;
   - сопоставление групп Authentik и scopes AgentOS;
   - объект `Principal` (`user_id`, группы, scopes) и FastAPI-зависимость `current_principal` для маршрутов из `base_app` (ADR-002);
   - интерфейс проверки доступа к проекту, `can_access_project(principal, project_id)`: контракт задаёт модуль, хранение ролей в проекте — в ядре (отдельный change).
3. **Контракт модуля для остальных модулей:**
   - единственный вход — `Principal` и интерфейс доступа к проекту;
   - вне `app/auth/` JWT и claims Authentik не читаются, импортов Authentik нет;
   - вне `modules/auth/` не лежит настройка Authentik.
4. **Вход пользователей:**
   - фронтенды (веб, мобильное, десктоп) подключаются к Authentik по OIDC, а не к Agno;
   - «Войти» перенаправляет на страницу входа Authentik, после входа возвращает в UI с Access Token;
   - UI передаёт токен в запросах к API Agno; промежуточного бэкенда нет (ADR-001).
5. **Интерфейс Authentik** (вход, профиль, сброс пароля, админка) публикуется на домене продукта за обратным прокси; админка доступна только группе `admins`.
6. **Рубежи защиты в Agno:**
   - первый: подпись токена; подделанный, просроченный или без токена — `401` до любой бизнес-логики;
   - второй: scopes на маршрутах и агентах; нет нужного scope — `403` до запуска LLM;
   - третий: `user_isolation=True` — Agno сам фильтрует свои данные (сессии, память) по `user_id` из токена.

## Хранение

- Отдельную базу не разворачиваем. Authentik пишет в общую базу проекта в схему `authentik` (`AUTHENTIK_POSTGRESQL__DEFAULT_SCHEMA=authentik`). Agno и PgVector остаются в схеме `ai`.
- Схема создаётся до первого запуска Authentik; сменить её после старта нельзя.
- Для Authentik заводится отдельная роль, у которой `search_path` содержит только `authentik` и нет прав на схему `ai`. Обратная изоляция не обеспечивается: загрузочный пользователь `ai` — суперпользователь, отдельная роль для Agno — отдельный change.
- Бэкап и восстановление общие для обеих схем.

## Scope

- Модуль `modules/auth/` и `app/auth/` с контрактом выше.
- Проверка JWT и изоляция данных Agno; подтверждение на двух пользователях.
- Сопоставление групп Authentik и scopes; сервисные учётные записи плагинов (Stark, IDE) с жёстко ограниченными правами.
- Схема `authentik` в общей БД, отдельная роль, инициализация.
- Публикация интерфейса Authentik на домене продукта.
- Authentik в локальной разработке: сервисы модуля в `compose.yaml` и команды `scripts/dev.sh`.
- Описание входа фронтенда как контракта для `authorled-web`.
- Правки `example.env`, `compose.yaml`, `compose.prod.yaml`, README, `.agents/skills/deploy-platform/SKILL.md`, мастер-спек и контекст-пака.
- Проверка: два тестовых пользователя, токены разных групп, `401`/`403`/изоляция, состав таблиц по схемам; запись в `tmp/VERIFY.md`.

## Non-goals

- Встраивание Authentik в процесс Agno: он остаётся отдельными процессами.
- Свой экран входа, свои пароли, регистрация и сброс пароля в бэкенде: этим владеет Authentik.
- Отдельная база или отдельный экземпляр PostgreSQL для Authentik.
- Роли в проекте (автор, соавтор, редактор) и проверка доступа к произведению: модуль задаёт интерфейс, реализация — отдельный change ядра. Изоляция Agno защищает только данные Agno (`03-architecture.md`, п. 4; анти-паттерн 11).
- Реализация OIDC-клиента во фронтенде: код живёт в `authorled-web`.
- Высокая доступность Authentik и несколько реплик (одна инстанция, как у API).
- Отдельный журнал безопасности (вне MVP, `05-security-and-compliance.md`).
- Обновление пина Agno.

## Constraints (из контекст-пака)

- Пользователи, вход, роли и токены — только Authentik; бэкенд проверяет JWT по подписи через ключи Authentik и своих паролей не хранит.
- Токен идёт напрямую в AgentOS: промежуточного бэкенда нет (инвариант 1).
- Agno владеет проверкой авторизации и изоляцией; модуль их настраивает и использует, не пересоздаёт и не обходит.
- В `prd` без ключа проверки JWT приложение не стартует (`JWT_JWKS_FILE`); обхода проверки нет ни в `prd`, ни в `dev` (решение владельца 2026-10-26: авторизация включена при любом `RUNTIME_ENV`).
- ПДн (152-ФЗ) хранятся и обрабатываются в РФ; касается и Authentik.
- Без fallback: нет ключа, неверный `iss`/`aud`, нет нужного claim, нет схемы или роли БД — явный отказ, а не подстановка значения.
- Версия образа Authentik закреплена; секреты (Client Secret, `AUTHENTIK_SECRET_KEY`, пароли ролей БД) не попадают в код и коммиты.
- Данные Agno и данные произведения в PostgreSQL разделены, данные Authentik — в своей схеме.

## Acceptance criteria

- Запрос без токена, с неверной подписью или просроченным токеном — `401`, LLM не вызывается.
- Токен без нужного scope на защищённый маршрут или агента — `403`, LLM не вызывается.
- Токен группы `editors` получает доступ к ресурсу, закрытому для `screenwriters`; токен `screenwriters` — нет.
- Два пользователя создают сессии: каждый видит только свои; чужой `session_id` не отдаётся.
- `user_id` в контексте агента и в записях БД Agno равен `sub` токена.
- Пользователь проходит вход с 2FA в интерфейсе Authentik на домене продукта и получает рабочий токен; админка Authentik недоступна не-админам.
- Состав БД после первого запуска: таблицы Authentik только в схеме `authentik`, в `public` и `ai` их нет; роль Authentik не читает схему `ai`.
- Конфигурация Authentik воспроизводится с нуля из blueprints на пустой схеме без ручных шагов в UI (кроме создания первого админа, если blueprints это не покрывают).
- Сервисная учётная запись плагина выполняет только разрешённые ей операции.
- В `prd` без ключа проверки JWT приложение не запускается.
- Вне `app/auth/` нет чтения claims JWT и импортов Authentik (проверяется поиском по коду).

## Risks

- **Источник ключей.** В Agno 3.1.10 JWT-middleware берёт ключи из статического ключа или файла JWKS (приложение использует только `JWT_JWKS_FILE`); загрузки по URL нет. Ключи Authentik придётся выгружать в файл при деплое и обновлять при ротации. Решение — в design change.
- **Алгоритм подписи.** Токены должны подписываться ключом Authentik (RS256 с публикацией JWKS), а не секретом клиента; проверить настройку провайдера.
- **Формат claim'ов.** Agno по умолчанию читает scopes из claim `scopes`, а Authentik отдаёт группы в `groups`; нужен property mapping в Authentik (в blueprints) или `scopes_claim` в middleware. Проверить на пине.
- **Аудитория.** `aud` токенов фронтенда и сервисных учётных записей должен совпасть с ожиданием AgentOS; проверить на пине.
- **Общая база.** Документация Authentik не описывает совместное использование базы с другими приложениями: схема и `search_path` поддерживаются, но гарантии под такой сценарий нет. Проверка состава таблиц входит в приёмку.
- **Общие бэкапы и миграции.** Обновление Authentik запускает его миграции в общей базе; откат затрагивает обе схемы. Обновлять версию отдельным change с бэкапом.
- **Поверхность админки.** Административный интерфейс Authentik публикуется на домене продукта; ограничить его группой `admins` и, при возможности, сетью.
- **Ресурсы.** Authentik — сервер и worker сверх API и PostgreSQL; учесть в размере хоста.
- **Изоляция неполная.** `user_isolation` охватывает только данные Agno; данные произведения защищает проверка доступа к проекту (отдельный change).
- **Сдвиг решения ADR-001.** Authentik переезжает из отдельного репозитория `authorled-auth` в этот; ADR-001, `03-architecture.md` и `05-security-and-compliance.md` уже обновлены (2026-10-26); мастер-спеки обновятся дельтами change.

## Open Questions

- Состав групп и scopes: какие группы существуют и какие маршруты и агентов видит каждая? Пример `finance:read` из исходного текста иллюстративный: такого агента в системе нет.
- Версия Authentik: какой тег закрепляем.
- Обратный прокси и домены: кто терминирует TLS в `compose.prod.yaml`, где публикуется Authentik (поддомен или путь).
- Решено 2026-10-26: Authentik нужен в локальной разработке и поднимается в `compose.yaml`; авторизация включена и в `dev` (условие `runtime_env != "dev"` в `app/main.py` удаляется).
- Выгрузка ключей Authentik в `JWT_JWKS_FILE`: шаг деплоя, скрипт или пример команды, как избежать устаревших ключей.
- Срок жизни Access Token и refresh; токены сервисных учётных записей: срок, scopes, кто выпускает и отзывает.
- Где хранятся роли в проекте и как они соотносятся с группами Authentik (общий доступ к маршрутам против доступа к проекту).
- Репозиторий `authorled-auth`: архивировать или использовать как источник стартовой конфигурации.

## Изменения относительно исходной формулировки

Исходный текст сверен с кодом, Agno 3.1.10 и документацией Authentik; в этой редакции:
- Authentik больше не отдельный сервис и репозиторий `authorled-auth`, а модуль проекта: деплой-часть `modules/auth/` и кодовая часть `app/auth/`; добавлены границы и контракт модуля.
- Хранение: общая база, схема `authentik`, отдельная роль, а не отдельная БД.
- «`AuthMiddleware` обращается к `/.well-known/openid-configuration`» → в пине ключи из файла JWKS (`JWT_JWKS_FILE`), загрузки по URL нет.
- «`groups` автоматически попадают в запрос» → по умолчанию читается claim `scopes`, группы сопоставляются явно.
- «Разработчик не может случайно показать чужие данные» → верно для данных Agno; данные произведения защищает проверка доступа к проекту.
- Пример агента `FinancialAnalyzer` и scope `finance:read` помечен иллюстративным.
- Добавлены: имя change, Non-goals, критерии приёмки, интерфейс доступа к проекту, правило «без fallback».

## Capabilities

### New Capabilities
- `auth`: модуль авторизации — деплой-часть (`modules/auth/`), адаптер `app/auth/`, контракт `Principal` и доступа к проекту, схема `authentik` в общей БД.

### Modified Capabilities
- `runtime`: условия старта в `prd` — ключ проверки JWT Authentik; сервисы Authentik в compose, схема и роль БД.
- `architecture`: принцип модульного монолита, границы модуля `auth`; состав сервисов.
- `overview`, `integrations`: Authentik как часть деплоя проекта.
- `api/identity`: доступ к `/users*` и сервисным учётным записям под токены Authentik.
- `api/sessions`, `api/memory`: изоляция по `user_id` из токена.

## Impact

- Новые: `modules/auth/` (compose-фрагмент, blueprints, бренд, инициализация БД), `app/auth/`.
- Изменяются: `app/main.py`, `example.env`, `compose.yaml`, `compose.prod.yaml`, `scripts/dev.sh`, README, `.agents/skills/deploy-platform/SKILL.md`, `.agents/skills/setup-platform/SKILL.md`.
- Контекст-пак: ADR-001 (Authentik — модуль репозитория, остаётся отдельным процессом, граница — OIDC/JWT; новый статус или ADR-005), `03-architecture.md` (таблица сервисов, принцип модульного монолита), `05-security-and-compliance.md`, `openspec/TODO.md` (закрыть пункт «Авторизация»).
- Дельты мастер-спек из списка Capabilities.
- Зависимости: фронтенд (`authorled-web`) получает контракт входа; ядро получает интерфейс доступа к проекту.
