# Бизнес-интент: вход через Authentik, проверка JWT и изоляция данных авторов

Статус: интент для `/opsx:propose`, имя change — `authentik-jwt` (см. `openspec/TODO.md`). Запускать после появления сервиса `authorled-auth`. Владелец: lehard. Обновлено: 2026-10-26.
Рамки: `openspec/context/ADR/ADR-001-three-services.md`, `openspec/context/03-architecture.md`, `openspec/context/05-security-and-compliance.md`.

## Why

В системе для разработки сценариев данные авторов — критически важный актив. Сценарист А не должен иметь технической возможности увидеть или изменить проект сценариста Б.

Agno не хранит пользователей, пароли и роли, поэтому нужен внешний доверенный источник истины (Identity Provider). Им становится Authentik: он разрабатывается и разворачивается отдельно от Agno (сервис `authorled-auth`, ADR-001) и берёт на себя всё взаимодействие с пользователем. Бэкенд (Agno) — только проверяющая сторона (Relying Party): доверяет подписи токена Authentik и сам ничего не знает о паролях.

## What Changes

Связка трёх слоёв: Authentik выдаёт токены, Agno проверяет их и применяет права, фронтенды живут за входом через Authentik.

1. **Authentik (Identity Provider)** — настраивается вне этого репозитория:
   - запуск в Docker/Kubernetes;
   - пользователи и группы (например, `screenwriters`, `editors`, `admins`);
   - приложение с провайдером OpenID Connect (OIDC): даёт Client ID и Client Secret для фронтендов;
   - потоки входа (flows): логин и пароль плюс 2FA/MFA.
2. **Agno, первый рубеж — проверка токена.** Запрос от UI приходит с `Authorization: Bearer <JWT>`, выданным Authentik:
   - подпись проверяется по публичным ключам Authentik; подделанный или просроченный токен — `401` до любой бизнес-логики;
   - из токена берутся `user_id` (`sub`) и права (группы/scopes) и передаются внутрь запроса к агенту.
3. **Agno, второй рубеж — права и изоляция:**
   - права: инструменты и маршруты привязаны к scopes; Authentik выдаёт scope только нужной группе. Нет scope в токене — `403` до запуска LLM. Пример: агент с требованием `finance:read` доступен только группе `editors`;
   - изоляция данных (`user_isolation=True`): Agno сам добавляет `WHERE user_id = <id из токена>` к запросам своих данных (сессии, память); код приложения не может случайно показать чужое.
4. **Интеграция UI (веб, мобильное, десктоп):**
   - фронтенды подключаются к Authentik, а не к Agno;
   - «Войти» перенаправляет на страницу входа Authentik, после входа Authentik возвращает пользователя в UI с Access Token;
   - UI передаёт токен в запросах к API Agno.
5. **Сервисные учётные записи:** плагины (Stark, IDE) работают через Service Accounts Authentik с жёстко ограниченными правами.

Итоговая цепочка: пользователь вводит пароль в Authentik → Agno проверяет подпись токена → `user_id` и права из токена попадают в контекст запроса и в `SessionState` → Agno не отдаёт чужие данные Agno на уровне БД.

## Scope

- Включение и настройка проверки JWT Authentik в AgentOS (`authorization=True` в `prd`): ключи, `sub` как `user_id`, источник scopes, проверка `aud`/`iss`.
- Сопоставление групп Authentik и scopes AgentOS: какая группа какие маршруты и агентов видит.
- Подтверждение `user_isolation=True` для данных Agno; проверка на двух разных пользователях.
- Сервисные учётные записи для плагинов: набор scopes, срок жизни токена.
- Описание подключения фронтенда (OIDC-вход, передача Bearer-токена) как контракта для `authorled-web`.
- Обновление `example.env`, `compose.prod.yaml`, README, мастер-спек и контекст-пака под фактическую конфигурацию.
- Проверка: два тестовых пользователя, токены с разными группами, `401`/`403`/изоляция; запись в `tmp/VERIFY.md`.

## Non-goals

- Развёртывание и настройка самого Authentik (пользователи, группы, потоки, провайдер) — отдельный сервис `authorled-auth`, не этот репозиторий.
- Хранение паролей, регистрация и сброс пароля в бэкенде.
- Доступ к произведению и роли в проекте: изоляция Agno защищает только данные Agno; доступ к проекту бэкенд проверяет сам, изоляция по проекту (`03-architecture.md`, п. 4; анти-паттерн 11) — отдельный change ядра.
- Реализация экрана входа и OIDC-клиента во фронтенде: код живёт в `authorled-web`.
- Отдельный журнал безопасности и мониторинг (вне MVP, `05-security-and-compliance.md`).
- Обновление пина Agno.

## Constraints (из контекст-пака)

- Пользователи, вход, роли и токены — только Authentik; бэкенд проверяет JWT по подписи через JWKS, своих паролей не хранит.
- Фронтенд не проходит через промежуточный бэкенд: токен идёт напрямую в AgentOS (ADR-001).
- В `prd` без ключа проверки JWT приложение не стартует; ни в `prd`, ни в `dev` не добавлять обход проверки.
- Данные Agno и данные произведения разделены; `user_isolation` не заменяет проверку доступа к проекту.
- ПДн (152-ФЗ) хранятся и обрабатываются в РФ — касается и Authentik.
- Без fallback: нет ключа, неверный `iss`/`aud`, нет нужного claim — явный отказ, а не подстановка значения по умолчанию.
- Секреты (Client Secret, ключи) не попадают в код и коммиты.

## Acceptance criteria

- Запрос без токена, с токеном с неверной подписью или просроченным — `401`, LLM не вызывается.
- Токен без нужного scope на защищённый маршрут или агента — `403`, LLM не вызывается.
- Токен группы `editors` получает доступ к ресурсу, закрытому для `screenwriters`; токен `screenwriters` — нет.
- Два пользователя создают сессии: каждый видит только свои; чужой `session_id` не отдаётся.
- `user_id` в контексте агента и в записях БД Agno равен `sub` токена.
- Сервисная учётная запись плагина может только разрешённые ей операции.
- В `prd` без ключа проверки JWT (`JWT_VERIFICATION_KEY` или `JWT_JWKS_FILE`) приложение не запускается.
- Ротация ключа Authentik не приводит к тихому принятию старых токенов: после обновления набора ключей токены со старой подписью отклоняются.

## Risks

- **Источник ключей.** В Agno 3.1.10 JWT-middleware берёт ключи из статического `JWT_VERIFICATION_KEY` или файла `JWT_JWKS_FILE`; загрузки по URL (`/.well-known/openid-configuration`, JWKS URL) в пине нет. Ротацию ключей Authentik придётся делать обновлением файла. Решение — в design change.
- **Формат claim'ов.** Agno по умолчанию читает scopes из claim `scopes`, а Authentik отдаёт группы в `groups`; нужна настройка property mapping в Authentik или `scopes_claim` в middleware. Проверить на пине.
- **Аудитория и издатель.** Токены фронтенда и сервисных учётных записей должны иметь `aud`, совпадающий с AgentOS; проверить, как это настраивается на пине.
- **Изоляция неполная.** `user_isolation` охватывает только данные Agno; данные произведения защищает проверка доступа к проекту (отдельный change). Не выдавать изоляцию Agno за полную защиту.
- **Зависимость от готовности `authorled-auth`.** Без работающего Authentik проверить цепочку нельзя; до тех пор можно проверять только на одноразовом ключе (как в runtime-спеке).

## Open Questions

- Состав групп и scopes: какие группы существуют (`screenwriters`, `editors`, `admins`) и какие маршруты и агентов видит каждая? Пример `finance:read` в исходном тексте иллюстративный: агента `FinancialAnalyzer` в системе нет.
- Источник ключей в `prd`: файл JWKS с ручной ротацией приемлем или нужна загрузка по URL (потребует решения вне пина Agno)?
- Токены сервисных учётных записей плагинов: срок жизни, набор scopes, кто выпускает и отзывает.
- Срок жизни Access Token и refresh на стороне фронтенда.
- Как соотносятся роли Authentik и роли в проекте (автор, соавтор, редактор): первые выдают общий доступ к маршрутам, вторые — доступ к конкретному проекту?

## Изменения относительно исходной формулировки

Исходный текст сверен с кодом и Agno 3.1.10; в этой редакции:
- «`AuthMiddleware` обращается к `/.well-known/openid-configuration` и берёт публичные ключи» → в пине ключи берутся из `JWT_VERIFICATION_KEY` или `JWT_JWKS_FILE`, загрузки по URL нет (см. Risks).
- «`groups` (scopes/roles) автоматически попадают в запрос» → по умолчанию читается claim `scopes`, группы Authentik нужно сопоставить явно (см. Risks).
- «Разработчик не может случайно показать чужие данные» → верно только для данных Agno; данные произведения защищает проверка доступа к проекту (`03-architecture.md`, п. 4).
- Пример агента `FinancialAnalyzer` и scope `finance:read` помечен иллюстративным.
- Добавлено: имя change, Non-goals, критерии приёмки и отказ без fallback.
