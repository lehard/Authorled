# Бизнес-интент: схема данных продукта `authorled`, миграции Alembic и таблица пользователей

Статус: решения согласованы с владельцем 2026-11-01; change `core-users-table` реализован и архивирован 2026-11-01 (`openspec/changes/archive/2026-11-01-core-users-table/`); production не проверялся. Владелец: lehard. Обновлено: 2026-11-01.
Рамки: `openspec/context/03-architecture.md` (инварианты 4 и 6), `openspec/context/04-engineering-standards.md` («Миграции», «Запуск проверок»), `openspec/context/05-security-and-compliance.md`, `openspec/context/07-anti-patterns.md` (п. 15, 22, 25, 26), ADR-001, ADR-002, мастер-спеки `architecture` («Подключение к БД») и `auth` («Контракт токена»).

## Why

У продукта пока нет своих таблиц. В общей базе `ai` есть только схема `ai` (Agno) и схема `authentik`. Истории, драфты, комментарии, роли в проекте и личный кабинет будут ссылаться на пользователя, поэтому первым нужен способ хранить данные продукта и сама запись пользователя.

Миграций в проекте тоже нет, хотя стандарт требует Alembic для схемы ядра. Без них каждую следующую таблицу пришлось бы создавать вручную.

## What Changes

1. **Схема `authorled`** в общей базе `ai` для данных продукта (ядра):
   - владелец — роль `agentos`, без прав суперпользователя;
   - схему создаёт идемпотентный шаг инициализации `agno/db/init.sql`, как схему `ai`;
   - таблицы ядра не смешиваются с таблицами Agno (`ai`) и Authentik (`authentik`).
2. **Миграции Alembic** для схемы `authorled`:
   - только вперёд, применённые миграции не правятся, у истории одна голова;
   - журнал версий Alembic хранится в схеме `authorled`; миграции не трогают `ai`, `authentik` и `public`.
3. **Отдельный шаг миграций** — одноразовый контейнер `agentos-migrate` под ролью `agentos`:
   - запускается между `agentos-db-init` и `agentos-api`, в разработке и в production одинаково;
   - API миграции не запускает; если миграция упала, API не стартует.
4. **Таблица `authorled.users`** только с основными полями:

   | Поле | Тип | Смысл |
   |---|---|---|
   | `id` | `uuid`, первичный ключ, создаёт база | наш идентификатор, на него ссылаются таблицы продукта |
   | `auth_subject` | `text`, уникальный, не пустой | claim `sub` токена Authentik — связь с Authentik |
   | `email` | `text`, не пустой | почта для показа (копия из Authentik) |
   | `display_name` | `text`, не пустой | имя в интерфейсе |
   | `created_at` | `timestamptz`, обязательное | когда создан |
   | `updated_at` | `timestamptz`, обязательное | когда изменён |
   | `last_seen_at` | `timestamptz`, обязательное | последний запрос пользователя |
   | `deleted_at` | `timestamptz`, пустое у действующего | мягкое удаление аккаунта |

5. **Тесты ядра на pytest** с настоящим PostgreSQL:
   - миграции применяются на чистой базе и повторно без изменений;
   - работают уникальность `auth_subject` и запрет пустых полей;
   - описание таблиц в коде совпадает со схемой в базе.
6. **Команды разработки**: `./scripts/dev.sh migrate` и `./scripts/dev.sh test` (чистая база `ai_test` в `agentos-db`); проверка одной головы миграций в `./scripts/validate.sh`.

## Scope

- `agno/db/init.sql`: схема `authorled` с владельцем `agentos`.
- `agno/core/`: описание таблиц ядра, пока одна таблица `users`.
- `agno/migrations/`, `agno/alembic.ini`: окружение Alembic и первая миграция.
- `agno/compose.yaml`, `compose.prod.yaml`: сервис `agentos-migrate`; API ждёт его успешного завершения.
- `scripts/dev.sh`, `scripts/validate.sh`: команды и проверка из п. 6.
- `agno/tests/`: pytest на чистой базе.
- `agno/pyproject.toml`, `agno/requirements.txt`: `alembic` в зависимостях, `pytest` в dev-зависимостях; пересборка обоих таргетов `agno/Dockerfile`.
- Мастер-спеки: новая спека хранения данных продукта, дельта `architecture` («Подключение к БД»: роль `agentos` владеет и схемой `authorled`).
- Документация: `AGENTS.md`/`CLAUDE.md` (где что лежит), README, deploy-скилл (шаг миграций). Стандарт `04-engineering-standards.md` уже дополнен 2026-11-01.
- Проверка: миграции на чистой и на существующей базе, `docker compose up` с упавшей миграцией, запись в `tmp/VERIFY.md`.

## Non-goals

- Создание и обновление записи пользователя и запрос `GET /me` — следующий интент (решение принято, см. Open Questions). Там же — расширение контракта токена claims `email` и `name` и первый свой маршрут через `base_app` (ADR-002).
- Профиль и настройки пользователя (тема, настройки чата и агента) — отдельная таблица профиля в интенте личного кабинета, со ссылкой на `users.id`.
- Группы, роли и права в схеме `authorled`: их источник — Authentik и токен.
- Роли в проекте и реализация `can_access_project` — с таблицами проектов.
- Поведение удаления аккаунта: в этом интенте есть только поле `deleted_at`.
- Свои маршруты API, изменения фронтенда.
- Обновление пина Agno.

## Constraints (из контекст-пака)

- Одна база, `get_postgres_db()` без аргументов; второй базы нет (анти-паттерн 25). Схемы ядра и Agno не смешиваются.
- Миграции не запускаются при старте сервиса и не правятся после применения (анти-паттерн 15).
- API и миграции работают под ролью `agentos` без суперпользователя и без доступа к схеме `authentik`.
- Без fallback: нет переменной подключения, нет схемы или упала миграция — явная ошибка, называющая причину.
- Тесты ядра — только на реальном PostgreSQL, без моков базы (анти-паттерн 22).
- ПДн в MVP — только email и имя; хранятся в РФ (152-ФЗ). В логи не пишутся, только идентификаторы.
- Вне `agno/app/auth/` claims токена не читаются: заполнять `auth_subject`, `email` и `display_name` будет код, получающий их через `Principal` (следующий интент).

## Acceptance criteria

- На чистой базе `docker compose up -d --build` создаёт схему `authorled` с владельцем `agentos`, применяет миграции и запускает API.
- Повторный `docker compose up` проходит без изменений в схеме `authorled`.
- Миграция с ошибкой останавливает `agentos-migrate` с ненулевым кодом, и `agentos-api` не стартует.
- После миграций в схеме `authorled` есть `users` с полями из таблицы выше и журнал версий Alembic; в `ai`, `authentik` и `public` ничего не изменилось.
- Вставка второго пользователя с тем же `auth_subject` и вставка с пустыми `auth_subject`, `email` или `display_name` отклоняются базой.
- `./scripts/dev.sh test` проходит на чистой базе `ai_test`; `./scripts/validate.sh` падает при двух головах миграций.
- Существующая локальная база (с данными Agno и Authentik) после обновления продолжает работать: сессии, знания и вход сохраняются.

## Risks

- **Первое ядро задаёт шаблон.** Раскладка `agno/core/` и `agno/migrations/` станет образцом для всех следующих таблиц; стоит согласовать её до кода.
- **Миграции под ролью `agentos`.** Права роли достаточно для своей схемы, но если миграции понадобится расширение PostgreSQL, его придётся ставить в `init.sql` под загрузочным пользователем.
- **Порядок в production.** Контейнер миграций запускается перед API на каждом деплое; долгая миграция задержит старт API. Для MVP приемлемо, большие миграции — отдельным решением.
- **Копии email и имени.** Они могут отставать от Authentik до следующего обновления записи; источником правды остаётся Authentik.
- **Удаление по 152-ФЗ.** Мягкое удаление сохраняет ПДн; порядок окончательного удаления — вопрос к ИБ (TODO в `05-security-and-compliance.md`).

## Open Questions

- Решено 2026-11-01: данные продукта — отдельная схема `authorled`; миграции — Alembic.
- Решено 2026-11-01: в `users` только основные поля; настройки — в будущей таблице профиля, связанной с `users`.
- Решено 2026-11-01: миграции в production — тот же одноразовый контейнер `agentos-migrate` перед API.
- Решено 2026-11-01: запись пользователя создаётся и обновляется явным запросом `GET /me` после входа, а не на каждом запросе (следующий интент).
- Решено 2026-11-01: удаление аккаунта мягкое, как корзина у историй (`deleted_at`).
- Срок окончательного удаления данных удалённого аккаунта (152-ФЗ) — к ИБ.
- Отношение `authorled.users` к каталогу пользователей Agno (`user_directory=True`, маршруты `/users*`): что из них остаётся видно и кому (связано с TODO по auth в `openspec/TODO.md`).
