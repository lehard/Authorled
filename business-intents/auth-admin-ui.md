# Бизнес-интент: настройки входа меняются в админке Authentik без релиза

Статус: решения согласованы с владельцем 2026-11-09; change `auth-admin-ui` реализован и архивирован 2026-11-09 (`openspec/changes/archive/2026-11-09-auth-admin-ui/`); список почт на проде перенесён в атрибут до релиза. Владелец: lehard. Обновлено: 2026-11-09.
Рамки: мастер-спека `auth` («Конфигурация из blueprints», «Интерфейс Authentik», «Регистрация», «Контракт токена»), `auth/blueprints/`, `auth/compose.yaml`; связанные решения: `business-intents/test-access-allowlist.md`, `business-intents/open-sign-up.md`.

## Why

У модуля авторизации есть своя админка: Authentik на `https://auth.soavtor.app/if/admin/`. Владелец хочет менять в ней настройки входа и регистрации без релиза (владелец, 2026-11-09). Сейчас это не работает по двум причинам.

- **Правки из админки откатываются.** Почти все объекты Authentik объявлены в blueprints со значениями (`attrs`): потоки входа и регистрации, их шаги, бренд, провайдер, группы. Когда файл blueprint меняется в релизе, Authentik применяет его заново и возвращает значения из репозитория. Что именно перетрёт следующий релиз, из админки не видно.
- **Список приглашённых живёт в окружении.** Кто может зарегистрироваться, задаёт `AUTH_ALLOWED_EMAILS` в `/etc/authorled/authorled.env`. Чтобы пустить нового бета-тестера, нужно править файл на сервере и перезапускать Authentik. Заявки в бету приходят с сайта, поэтому это самая частая правка.

Вход в админку уже работает: администратор `akadmin`, пароль из `AUTHENTIK_BOOTSTRAP_PASSWORD`, код на `AUTHENTIK_BOOTSTRAP_EMAIL` (проверено владельцем 2026-11-09).

## What Changes

1. **Два владельца настроек.** Каждый объект в blueprints относится либо к репозиторию, либо к админке.
   - **Репозиторий** (blueprint применяет значения при каждом изменении файла, правка в админке не держится). Сюда входит то, на что опирается код продукта:
     - имена групп `screenwriters`, `editors`, `admins`, `plugins` и `is_superuser` у `admins` (контракт токена, `GROUP_SCOPES`);
     - OIDC-провайдер и приложение: `client_id`, адреса возврата и выхода, тип клиента, grant types, ключ подписи, `sub_mode`, scopes, сроки токенов, slug `authorled`;
     - поток выхода;
     - состав и порядок шагов потоков входа и регистрации, поля регистрации, правило «пароль спрашивается, только если он задан» и проверки регистрации, потому что веб-фронтенд проходит эти шаги своими экранами;
     - срок кода 10 минут и шаблон письма с кодом, потому что этот срок написан в письме и на экране;
     - привязка потока входа к бренду `AUTH_BRAND_DOMAIN`;
     - сервисные учётные записи и их токены.
   - **Админка** (blueprint создаёт объект на пустой схеме и больше его не меняет, `state: created`):
     - заголовок бренда и заголовки потоков;
     - тема письма с кодом;
     - число неудачных попыток ввода пароля до сброса входа.
   - Пользователи, их группы и пароли, как и сейчас, живут только в админке.
2. **Список приглашённых в админке.** Список разрешённых почт хранится в атрибуте `allowed_emails` группы `screenwriters`: это список строк, сравнение без учёта регистра, значение `["*"]` открывает регистрацию всем. Blueprint объявляет группу только по имени и атрибут не задаёт, поэтому релиз его не перетирает. Если атрибута нет или он не список строк, регистрация отказывает с понятным сообщением и пишет причину в журнал Authentik. Значения по умолчанию нет. Переменная `AUTH_ALLOWED_EMAILS` удаляется из `auth/compose.yaml`, `example.env`, README и скиллов. Перед релизом владелец переносит в атрибут текущий список с сервера.
3. **Вход в админку.** Администрирует `akadmin`. Личные аккаунты в группу `admins` не добавляются: члены этой группы получают ещё и административные права в API AgentOS.
4. **Памятка в README.** Новый раздел «Админка Authentik»: адрес, как войти, что можно менять в админке, что принадлежит репозиторию и откатится, как открыть регистрацию новому тестеру.

## Scope

- `auth/blueprints/` (`state: created` у объектов админки, группа `screenwriters` без атрибута, правило регистрации читает атрибут группы).
- `auth/compose.yaml`, `example.env`, README, `.agents/skills/deploy-platform` и `.agents/skills/setup-platform` (удаление `AUTH_ALLOWED_EMAILS`, раздел про админку).
- Требования мастер-спеки `auth`: «Конфигурация из blueprints» (кто владеет какой настройкой), «Регистрация» (список из атрибута группы вместо окружения), «Интерфейс Authentik» (как администрировать).
- Локальная разработка: `./scripts/dev.sh auth-users` или blueprint из `auth/blueprints-dev/` задаёт `allowed_emails` для локальных тестовых почт, чтобы регистрацию можно было проверить без ручных шагов.

## Non-goals

- Своя админка в веб-фронтенде продукта.
- Приглашения Authentik (одноразовые ссылки) вместо списка почт.
- Ограничение доступа к админке по IP или отдельный домен для неё.
- Управление в админке тем, что принадлежит репозиторию (контракт токена, шаги потоков, провайдер).
- Синхронизация правок из админки обратно в репозиторий и отчёт о расхождениях.
- Смена SMTP и других настроек `AUTHENTIK_*` из окружения.

## Constraints (из контекст-пака)

- Настройки Authentik живут только в `auth/` (мастер-спека `auth`, «Граница модуля»).
- Конфигурация воспроизводится на пустой схеме без ручных шагов, кроме создания первого администратора. Заполнение `allowed_emails` на пустой схеме становится вторым ручным шагом, пока регистрацию никому не открыли: это нужно записать в спеке явно.
- Нет запасных значений: отсутствующий или неверный атрибут даёт явный отказ, а не открытую или закрытую регистрацию молча.
- Секреты не попадают в blueprints, код и чат.
- Пользователей пока нет, кроме тестеров: переход можно сделать одним релизом.

## Acceptance criteria

- Владелец меняет в админке заголовок бренда, тему письма или число попыток пароля. После релиза, который меняет файл этого blueprint, значение остаётся.
- Правка в админке объекта из репозитория (например, адреса возврата провайдера) после такого релиза возвращается к значению из репозитория. README об этом предупреждает.
- Владелец добавляет почту в `allowed_emails` группы `screenwriters`, и человек с этой почтой сразу может зарегистрироваться, без перезапуска и релиза.
- Почта не из списка получает «Регистрация сейчас доступна только по приглашению.».
- Без атрибута `allowed_emails` регистрация отказывает, а в журнале Authentik видна причина.
- `["*"]` открывает регистрацию всем, сравнение почт без учёта регистра.
- На пустой схеме blueprints применяются без ошибок, вход, регистрация (после заполнения атрибута) и выход работают как сейчас.
- `AUTH_ALLOWED_EMAILS` нигде не упоминается, кроме истории в `business-intents/` и архиве OpenSpec.
- `./scripts/validate.sh` и `./scripts/auth_check.sh` проходят.

## Risks

- `state: created` действует только на создание. Объекты, которые уже есть на проде, после релиза не изменятся, а будущие правки этих полей в репозитории до прода не дойдут. Это осознанный обмен: такие поля дальше меняются только в админке.
- Если перед релизом не перенести список почт в атрибут, регистрация на проде закроется для всех до заполнения атрибута. Уже зарегистрированные входят как раньше.
- Ошибка в админке в объекте админки (например, пустой заголовок потока) не ловится проверками репозитория. Повторить настройку из репозитория можно, только удалив объект, чтобы blueprint создал его заново.
- Один администратор `akadmin`: если потерять его пароль и доступ к почте кодов, восстановление идёт через `ak` на сервере.

## Open Questions

- Нужен ли второй администратор на случай, если `akadmin` потеряет доступ к почте кодов. Сейчас решено: не нужен.
