# Бизнес-интент: инструменты соавтора описаны так, как их проверяет ядро

Статус: решения согласованы с владельцем 2026-11-08 («Да, записать»); change `coauthor-tool-contracts` спланирован 2026-11-08 (`openspec/changes/coauthor-tool-contracts/`), не реализован. Решено при `/opsx:propose`: пояснения полей — в ядре; около 60 просьб; замер в `agno/evals/coauthor/` после архива `coauthor-quality-eval`, прогон «до» на нынешнем коде. Группы 2–3 закоммичены (`d2aa94a`), замер выполнен 2026-11-09 (итог ниже). Владелец: lehard. Обновлено: 2026-11-09.
Рамки: мастер-спеки `api/agents` («Инструменты соавтора», «Действия соавтора»), `api/stories` («Виды документов и их поля»), `openspec/context/07-anti-patterns.md` (п. 23 — свои наборы в evals только по решению владельца, п. 26 — без fallback), ADR-003 (модели только через LiteLLM). Связан с `business-intents/coauthor-actions.md`, `coauthor-refusal-text.md`, `coauthor-quality-eval.md`.

## Why

На проде (v0.3.6, `app.soavtor.app`, 2026-11-08) владелец попросил: «Создай ужасного персонажа Василия, который бомж и дикий шизанутый». Соавтор показал карточку «Создать персонажа „Василий“». После «Разрешить» ядро отказало четыре раза подряд: «Поле «speech»: неверное значение», затем «fear», «age», «Поля «character» нет у документа этого вида». С пятой попытки персонаж создан, но весь профиль (внешность, страх, речь, цель) лёг в короткое описание `summary`: поля профиля остались пустыми.

Трассы прода (`ai.agno_spans`, `create_story_document`, 2026-11-08 19:38:20–19:39:06) показывают причины:

1. **Схема требует объект вместо строки.** Параметр `fields: dict[str, Any]` в `agno/agents/coauthor_tools.py` Agno 3.1.10 превращает в JSON Schema, где значение каждого поля — пустой объект (`"type": "object", "properties": {}`). Модель послушно передала `"speech": {"value": "Рваная речь…"}`. Ядро (`core/fields.py`, строгая проверка строк) отказало.
2. **Имена полей модели не сообщаются.** В описании инструмента — только «как в read_story_document». Модель выдумала `character`, `appearance`, `motivation`, `notes`; у персонажа есть `personality`, `body`, `dress`, `longGoal`.
3. **Роль — свободная строка.** Ещё два отказа на проде: `role: "паромщица"` и `role: "villain"`.
4. **Ядро называет только первую ошибку и не говорит, чего ждёт.** Модель исправляла по одному полю за ход, а в конце сдалась и переложила всё в `summary`.

Всего на проде 8 вызовов `create_story_document`, 6 из них получили отказ. `update_story_document` устроен так же. В `coauthor-refusal-text` выбор роли с первой попытки был вынесен в non-goals как поведение модели; теперь видно, что причина в контракте инструмента, поэтому это решение пересматривается.

Готовящийся замер `coauthor-quality-eval` такие ошибки не увидит: он останавливает запуск на паузе перед изменением и не продолжает, а ошибка в аргументах видна только после «Разрешить».

## What Changes

1. **Схема инструментов документа.** В `create_story_document` и `update_story_document`:
   - значения полей профиля — строки (`dict[str, str]`, у правки — строка или null, null убирает поле);
   - роль — перечисление `main`, `secondary`, `episodic`;
   - описание параметра `fields` перечисляет поля каждого вида с короткими русскими пояснениями и собирается из `core/fields.py`, чтобы не расходиться с ядром (у `gender` — допустимые значения).
2. **Отказ ядра по полям.** Перечисляет все неверные поля сразу; для неверного значения пишет, чего ждёт («ожидается строка», допустимые значения); для неизвестного поля называет допустимые поля этого вида. Формат отказа остаётся строкой «Отказ: …», как сейчас (чат его уже показывает).
3. **Промпт соавтора.** После отказа исправить вызов по причине, а не выбрасывать данные: сведения профиля кладутся в поля профиля, а не в `summary`.
4. **Замер действий соавтора.** Около 60 естественных просьб на все изменяющие инструменты (персонаж, локация, мир, правка поля и роли, заметка, комментарий; разговорные формулировки, опечатки, просьбы без явного «создай»), написанных Claude в формате наборов экзамена маршрутизации. Настоящий соавтор работает в режиме `auto` на одноразовой копии демо-историй в локальной базе, ядро применяет изменения. Проверка кодом, без судьи:
   - ядро ни разу не отказало из-за аргументов;
   - соавтор исправлял вызов не больше одного раза;
   - сведения легли в нужные поля, а не в `summary`;
   - без просьбы автора ничего не изменено.
   Прогон до исправления и после; результат — в `tmp/VERIFY.md`.

## Scope

- `agno/agents/coauthor_tools.py`: типы и описания параметров инструментов документа.
- `agno/core/fields.py` (и при необходимости `core/documents.py`): текст отказа со всеми полями; пояснения полей для описания инструмента.
- `agno/skills/coauthor/SKILL.md`: правило про исправление после отказа.
- Набор и запуск замера действий в `agno/evals/coauthor/` поверх запускателя `coauthor-quality-eval`; README замера.
- pytest ядра на отказ со всеми полями и на схему инструментов (без вызовов модели).
- Спеки `api/agents` и `api/stories`: контракт полей в инструментах и текст отказа.

## Non-goals

- Отдельные инструменты на каждый вид документа (`create_character` и т. п.): число инструментов растёт, а проблему решает схема.
- Менять `coauthor-quality-eval` (пауза без продолжения остаётся там как есть) и его выборку.
- Оркестратор и домены.
- Судья для замера действий: проверка детерминированная.
- Регрессионный набор в CI.
- Исправлять уже созданного на проде «Василия»: пользователей нет, это демо-данные владельца.

## Constraints

- Без fallback: ядро не приводит объекты к строкам и не угадывает имена полей; неверный вызов — явный отказ с причиной (07-anti-patterns, п. 26).
- Схема собирается средствами Agno 3.1.10 (`Function.from_callable` по типам), без адаптеров; список инструментов остаётся статическим.
- Модели только через LiteLLM, соавтор — на `deepseek-fast`, как в продукте.
- Замер только на локальной базе и демо-историях; на сервере — только чтение трасс.
- Свой набор и проверка кодом — по решению владельца (п. 23), как у экзамена маршрутизации.

## Acceptance criteria

- В схеме `create_story_document` и `update_story_document` значения полей — строки, роль — перечисление, поля каждого вида перечислены с пояснениями.
- Отказ ядра по полям называет все неверные поля и ожидаемое значение одним сообщением.
- На просьбе владельца про Василия соавтор создаёт персонажа с заполненными полями профиля с первой попытки (локально, повтор 5 раз).
- Замер действий: доля вызовов без отказа ядра — до исправления и после; после исправления отказов из-за аргументов нет или каждый разобран в `tmp/VERIFY.md`.

## Risks

- **Длинное описание полей** (у персонажа их больше 30) удорожает каждый запрос. → Пояснения по 2–4 слова; цену запроса сравнить до и после.
- **DeepSeek может игнорировать схему** и всё равно передавать лишнее. → Это покажет замер; подробный отказ даёт исправиться за один ход.
- **Пересечение с `coauthor-quality-eval`**, который ведёт другая сессия. → Замер действий начинается после того, как готов его запускатель; общие файлы не правим параллельно.

## Open Questions

1. **Где хранить русские пояснения полей.** Рекомендую в ядре (`core/fields.py`) рядом с именами полей: ядро — источник правды для инструментов. Подписи на экране остаются в `web/src/data/profiles.ts`; расхождение между ними допустимо.
2. **Число просьб в замере действий.** Рекомендую около 60; ориентир — около 60 ₽ на DeepSeek за два прогона (прикидка от бюджета `coauthor-quality-eval`, не замер).

## Итог (2026-11-09)

Замер действий, 64 просьбы, deepseek-fast, локально; «до» на `99881c1`, «после» на `d2aa94a`, код замера один и тот же.

- Прошли: 30 → 59 из 64 (47% → 92%). Без отказа ядра: 43 → 56. Поля профиля заполнены: 6 → 35 из 38 документов.
- Отказы: 29 → 9. Неверный тип значения: 10 → 0. Поле не этого вида: 13 → 3. Роль не передана: 2 → 1. Цитата не найдена в комментариях (вне этой правки): 4 → 5. Все отказы «после» по аргументам исправлены следующей попыткой.
- Попыток на создание документа: 1.78 → 1.15. Цена на просьбу: 0.17 → 0.19 ₽ (описание полей длиннее), вызовов модели 251 → 199.
- «Василий», 5 повторов: профиль в полях во всех пяти, с первой попытки в четырёх; в пятом выдуманное поле, исправлено по отказу со второй попытки.
- Остались: роль у локации и персонажа не названа обязательной в описании инструмента (один отказ); заметки истории не изолированы между просьбами и прогонами (перед «после» восстановлены вручную, порядок набора исправлен).

- Доработки 2026-11-09 (`07886bc` и восстановление заметок перед каждой просьбой), повторный прогон: прошли 63 из 64, без отказа 60, поля 37 из 38, отказов 4 (по роли 0; три выдуманных поля мира и персонажа, все исправлены второй попыткой; одна цитата). Единственный провал — работа персонажа в описании вместо `job`.
